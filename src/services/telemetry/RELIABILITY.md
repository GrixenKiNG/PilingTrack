# Контракт надёжности телеметрии без оборудования

База проверки: `064e2402dfddaa1a0b4ce6842fa1f113eec4b65e`, задача F от 23.10.2026.
Это контракт существующего режима best effort, а не обещание пригодности для
расчёта топлива, оплаты или допуска техники. Физические датчики не проверялись.

## Два разных значения «принято»

| Вход | Подтверждение | Что гарантировано к этому моменту |
| --- | --- | --- |
| `POST /api/telemetry`, `/batch`, сервис `ingestTelemetry` | `buffered-*`, счётчик `ingested` | Запись передана буферу текущего процесса. Запись в PostgreSQL может ещё отсутствовать. При пороговом flush она может уже существовать; сам ACK этого не доказывает. |
| Sampling того же сервиса | `sampled-out-*`, разность размера пачки и `ingested` | Событие сознательно отброшено и записываться не будет. |
| Device `POST`/`PATCH /api/telemetry/ingest` | HTTP 202, `accepted` | `createMany` уже завершён. Этот маршрут обходит RAM-буфер и sampling; 202 здесь не означает RAM-очередь. Проверено чтением маршрута, не HTTP-прогоном. |

`buffered-*` — синтетический идентификатор подтверждения, не ID строки БД и не
ключ идемпотентности. Ошибка flush логируется, записи возвращаются в RAM,
а сам `flush()` может завершиться без исключения. Только подтверждённая запись
в БД означает сохранение; число `ingested` этого не заменяет.

## Потеря, порядок, переполнение

- Допустимый технический режим сейчас: потеря любой ещё не записанной выборки
  при аварийном завершении. Количественный бизнес-бюджет потери не утверждён;
  нельзя называть его нулевым или ограниченным фиксированным процентом.
- Значения по умолчанию: порог flush 500, период 5 с, batch 200. Это не верхняя
  граница задержки: таймер зависит от event loop, БД и повторных попыток.
- При OPEN и достижении порога выбрасываются старейшие
  `ceil(maxBufferSize * 0.25)` записей. Счётчик `dropped` учитывает это, но не
  потерю RAM при аварии и не sampling. По размеру буфера нельзя восстановить
  общий объём потерь.
- Порог 500 не следует объявлять строгим глобальным лимитом памяти: буферы
  принадлежат процессам, текущая пачка уже может быть вне буфера, а одновременно
  пришедшие вызовы и повторное помещение неуспешной пачки меняют его размер.
- `shutdown()` пытается flush; SIGKILL и авария такую попытку не выполняют.
  Даже вызов shutdown не гарантирует успех при недоступной БД. Тест проверяет
  явный shutdown при исправной БД, а не доставку сигнала оркестратором.
- Глобальный порядок доставки и хранения не гарантируется. Внутри flush данные
  группируются по организации. SQL без `ORDER BY` не задаёт порядок чтения.
  Пользовательские часы не исправляются: прошлые и будущие даты сохраняются.

## Дедупликация и накопительные счётчики

**Факт:** повторы сохраняются. В `TelemetryRecord` нет отдельного `deviceId`
и уникального ключа `(deviceId, ts)`; `metadata.deviceId` — произвольные данные,
не аутентифицированная идентичность. Отправка одинаковых записей последовательно
и из двух процессов даёт по две строки. Нельзя обещать ни exactly once, ни
at least once для RAM-пути.

**Целевое решение до подключения датчиков:** аутентифицированный стабильный
идентификатор устройства, время события с явно заданной точностью и атомарная
идемпотентность в БД. Если один пакет содержит несколько сигналов на одну дату,
пара `(deviceId, ts)` описывает пакет, а ключ строки должен различать тип сигнала
либо порядковый номер. Нужно отдельно решить поведение при двух разных значениях
с одним ключом. Удаление повторов по RAM-набору не решит перезапуск и несколько
процессов. Изменение схемы запрещено заданием, реализации здесь нет.

`fuel_total: 1000 → 5` сохраняется как исходная последовательность. Падение может
быть сбросом, заменой датчика, переполнением счётчика или нарушением порядка;
приёмник не должен молча превращать его в положительный расход или удалять
измерение. Для потребителя это разрыв эпохи/недостаточное качество до отдельной
обработки сброса. Текущая аналитика использует max−min: риск ложных 995 л при
таком разрыве остаётся в аналитике; по границам F её код не менялся.

Sampling, лимит 1000 записей/с и circuit breaker сервиса локальны процессу;
добавление реплик не создаёт общий предел или согласованное восстановление.
Тест двух процессов доказывает независимость буферов и повторную запись,
а не фактическую пропускную способность 2000 записей/с.

## Воспроизведение на одноразовом PostgreSQL

В Git Bash из корня отдельного worktree:

```bash
bash src/services/telemetry/__tests__/run-reliability-disposable.sh
```

Скрипт использует только `test-db-up.sh`/`test-db-down.sh`, создаёт клиент Prisma
через конфиг интеграций без dotenv, запускает node:test с реальными процессами
через tsx. Родитель проверяет БД owner-ролью; сервисы в дочерних процессах пишут
через app-роль и штатный tenant context. Нужны Docker и установленные зависимости.
URL не печатаются и не сохраняются. Без disposable URL/имени контейнера тест
завершается ошибкой, а не молчаливым skip.

| Случай | Ожидание текущего контракта | Проверенный факт | Вывод |
| --- | --- | --- | --- |
| ACK до flush | RAM, затем PostgreSQL | buffered=1, строк 0; после flush строк 1 | ACK не равен durable write |
| SIGKILL с непустым буфером и новый процесс | Не восстановится | Строк 0, новый буфер пуст | Допустимая техническая потеря; бизнес-допуск ещё требует решения |
| Явный shutdown | Попытка flush | 1 строка при исправной БД | Успешный штатный путь, не гарантия при аварии |
| OPEN, maxBufferSize=4, четыре записи | Drop старейшей 1/4 | dropped=1, persisted values=[2,3,4] после reset | Предохранитель открыт fault injection; реальный отказ PostgreSQL этим не моделируется |
| Один deviceId и ts дважды | Пока нет дедупликации | 2 строки | Целевой контракт идемпотентности не выполнен |
| fuel_total 1000→5 | Сохранить сырой разрыв | [1000,5] в БД | Обработку эпохи должен учитывать потребитель |
| Часы 2026→2036→2000 | Сохранить исходные даты | Все три даты сохранены | Нужна явная политика допустимого сдвига часов, сейчас её нет |
| Два живых процесса, один event | Два независимых буфера | Разные PID, по одной записи RAM; затем 2 строки | Нет межпроцессной дедупликации |

Все эти тесты характеризуют текущий контракт. Зелёный результат теста дубликата
не означает реализованную защиту от дублей: он закрепляет известный разрыв.

## Следующее решение владельца

Для инженерных и учётных данных рекомендуемый целевой допуск — **не терять
подтверждённое сохранение**, хранить исходное событие и качество измерения;
для частой диагностической вибрации sampling допустим по отдельной политике.
Вариант durable приёмника (БД либо Redis с подтверждаемой персистентностью),
общая идемпотентность и политика времени требуют отдельного проекта и проверки
восстановления. Переход на Redis сам по себе гарантией доставки не является.
