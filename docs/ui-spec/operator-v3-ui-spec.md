# PilingTrack — спецификация интерфейса модуля «Смена оператора»

**Адрес:** `/operator/v3`  
**Редакция:** 1.1  
**Дата:** 26 августа 2026 года  
**Статус:** целевая спецификация интерфейса для реализации  
**Основа:** концепция «Маршрут» с обязательным блоком «Допуск»  
**Главный источник требований:** `docs/product/operator-shift-readiness-specification-2.0-final.md`

## 1. Назначение

Экран `/operator/v3` проводит оператора через полную смену на одной установке и в каждый момент отвечает на четыре вопроса:

1. На какой установке и объекте я работаю?
2. Можно ли сейчас выполнять работу?
3. Что я обязан сделать следующим?
4. Как немедленно сообщить об опасности или неисправности?

Интерфейс не повторяет внутреннее устройство системы и не предлагает оператору самостоятельно определять техническую готовность. Система собирает доказательства, проверяет правила и показывает объяснимое решение.

Основная формула экрана:

> **Один текущий шаг → одно главное действие → подтверждённый сервером результат → следующий шаг.**

## 2. Границы модуля

Модуль включает:

- выбор назначенной установки;
- получение установки и сведений предыдущей смены;
- подтверждение допуска оператора;
- проверку до работы;
- проверку рабочей зоны;
- ввод начальных моточасов и обязательную подготовку;
- показ решения о технической готовности;
- начало работы;
- производственные записи;
- перерыв и простой;
- дефекты, опасные события и безопасную остановку;
- разрешённое оператору обслуживание;
- проверку после работ;
- подтверждение автоматически сформированного отчёта;
- передачу установки и закрытие смены;
- журнал текущей смены;
- сведения об установке;
- работу при временной потере связи в разрешённых пределах.

Модуль не включает административное редактирование установок, правил, шаблонов проверок, документов, назначений и регламентов. Оператор видит только сведения и допустимые действия.

## 3. Терминология интерфейса

Во всех заголовках, кнопках, уведомлениях, подписях, подсказках и сообщениях применяются русские термины.

| Использовать | Не использовать в пользовательском интерфейсе |
|---|---|
| Смена | внутреннее название состояния |
| Этап смены | состояние машины состояний |
| Техническая готовность | балл готовности |
| Работа разрешена | положительный вердикт |
| Работа разрешена с замечаниями | предупреждающий вердикт |
| Работа запрещена | отрицательный вердикт |
| Недостаточно данных | неизвестный вердикт |
| Препятствие | блокирующая ошибка |
| Замечание | предупреждение на английском языке |
| Проверка | чек-лист |
| Доказательство | техническое имя источника |
| Работа без связи | офлайн-режим |
| Все данные переданы | синхронизировано |
| Есть данные для отправки | ожидает синхронизации |
| Обнаружено противоречие | конфликт синхронизации |
| Журнал смены | лента событий |

Технические адреса запросов и внутренние значения могут использоваться только в документации разработчиков, журналах диагностики с ограниченным доступом и автоматических испытаниях.

## 4. Принципы интерфейса

1. **Один главный призыв.** На основном экране одновременно показывается только одна заполненная акцентным цветом кнопка, продвигающая текущий этап.
2. **Безопасность доступна всегда.** Действия «Сообщить о дефекте», «Опасное событие» и «Добавить фотографию» доступны до начала, во время и после работы.
3. **Допуск является решением, а не шкалой.** Проценты и баллы готовности запрещены.
4. **Причина важнее цвета.** Любой запрет сопровождается объяснением и допустимым следующим действием.
5. **Сервер подтверждает переход.** Экран меняет этап только после подтверждённого ответа либо после помещения разрешённой команды в защищённую очередь отправки.
6. **Объект не выбирается повторно.** Он определяется назначением установки. Оператор выбирает только из назначенных ему установок.
7. **Нет скрытых переходов.** Получение установки, начало смены, завершение работ, передача и закрытие требуют явного подтверждения.
8. **Введённые данные сохраняются.** Закрытие формы, сворачивание приложения и потеря связи не должны уничтожать подтверждённые локальные данные.
9. **Критическое событие прерывает маршрут.** Оно открывает сценарий безопасной остановки, а не становится восьмым этапом.
10. **История видима.** Оператор может открыть журнал текущей смены, не покидая модуль.

## 5. Информационная архитектура

### 5.1. Постоянная верхняя область

Содержит:

- название установки;
- модель установки;
- объект;
- тип и время смены;
- краткое состояние связи;
- кнопку «Сведения об установке»;
- решение о возможности продолжать текущий этап: «Можно продолжать», «Есть замечания», «Действие запрещено», «Проверяем данные».

На телефоне сведения занимают не более двух строк. На настольном экране справа дополнительно показываются моточасы, время с начала смены и ближайшее обслуживание.

### 5.2. Карточка текущего шага

Главная область экрана содержит:

- «Этап N из 7»;
- короткий глагольный заголовок;
- одно предложение о цели;
- необходимые входные сведения;
- препятствия или замечания;
- одно главное действие;
- при необходимости — ссылку «Почему это требуется?».

Главная кнопка закрепляется внизу области просмотра на телефоне. Она не перекрывает постоянные действия безопасности и системные сообщения.

### 5.3. Маршрут смены

Маршрут показывает семь этапов:

1. Допуск оператора.
2. Получение установки.
3. Проверки до работы.
4. Подготовка и допуск к работе.
5. Работа.
6. Завершение смены.
7. Передача установки.

Состояния этапа:

- завершён — знак подтверждения и подпись;
- текущий — выделение рамкой и текст «Сейчас»;
- доступен для просмотра — обычная подпись;
- ещё недоступен — приглушённая подпись и объяснение при открытии;
- требует внимания — знак предупреждения и количество незавершённых действий.

Нажатие завершённого этапа открывает только просмотр его доказательств. Повторное редактирование выполняется отдельным исправляющим действием при наличии полномочия.

### 5.4. Постоянные действия безопасности

Вне зависимости от этапа доступны:

- **Сообщить о дефекте**;
- **Опасное событие**;
- **Добавить фотографию**.

На телефоне они открываются кнопкой «Безопасность» в постоянной нижней панели. При раскрытии первые два действия имеют текст и знак, фотография — третьим пунктом. При состоянии «требуется безопасная остановка» панель раскрыта автоматически.

На настольном экране эти три действия находятся в постоянной правой колонке. Красный цвет применяется только для опасного события и подтверждения безопасной остановки, а не для обычного дефекта.

### 5.5. Дополнительные разделы

- «Журнал смены» — хронологические события с состоянием отправки.
- «Сведения об установке» — модель, моточасы, открытые дефекты, обслуживание, документы и назначения.
- «Помощь» — правила безопасного действия и связь с ответственными лицами.

Открытие дополнительных разделов не меняет этап смены.

## 6. Компоновка телефона

Целевые размеры: ширина от 320 до 480 точек, высота от 568 точек.

Порядок сверху вниз:

1. верхняя область установки и связи;
2. компактное решение «можно продолжать / действие запрещено»;
3. карточка текущего шага;
4. раскрываемые причины и доказательства;
5. компактный маршрут из семи отрезков;
6. постоянная нижняя область главного действия;
7. кнопка безопасности, не перекрываемая главным действием.

Требования:

- основная колонка занимает всю доступную ширину;
- минимальная область нажатия — 48 × 48 точек;
- горизонтальная прокрутка запрещена;
- важные сведения видны без бокового жеста;
- формы открываются полноэкранным слоем или нижней панелью, если она полностью помещает главное действие;
- клавиатура не перекрывает поле и кнопку подтверждения;
- при возвращении из камеры оператор попадает в ту же форму;
- длинный маршрут не вытесняет текущий шаг: по умолчанию он свёрнут до полосы прогресса и подписей «Допуск — Работа — Передача».

## 7. Компоновка настольного экрана

Целевые размеры: ширина от 1024 точек.

Используется сетка из трёх зон:

- левая колонка 240–280 точек — маршрут смены и завершённые этапы;
- центральная колонка 560–760 точек — текущий шаг и главное действие;
- правая колонка 280–360 точек — техническая готовность, связь, безопасность и краткий журнал.

При ширине от 768 до 1023 точек правая колонка переносится под центральную, маршрут остаётся слева. Ни одна зона не дублирует главное действие.

На настольном экране оператор не получает административное меню. Глобальная оболочка приложения сохраняется, но навигация роли оператора ограничивается его рабочими разделами.

## 8. Общие состояния экрана

### 8.1. Первичная загрузка

- показывается каркас верхней области, карточки шага и маршрута;
- постоянные действия безопасности доступны после получения личности и назначений;
- текст «Загружаем текущую смену» читается программой экранного доступа;
- через две секунды без ответа показывается «Загрузка занимает больше времени»;
- повторная загрузка не создаёт команды и не меняет этап.

### 8.2. Обновление после действия

- текст и введённые значения остаются видимыми;
- главная кнопка блокируется и показывает конкретное действие: «Сохраняем», «Начинаем смену», «Передаём установку»;
- повторное нажатие не создаёт вторую запись;
- после ответа карточка обновляется по новому серверному состоянию;
- подтверждение показывается в области сообщений и объявляется программе экранного доступа.

### 8.3. Ошибка загрузки

Показываются:

- заголовок «Не удалось загрузить смену»;
- безопасное понятное описание;
- кнопка «Повторить»;
- состояние последней успешной загрузки, если оно есть, с отметкой времени;
- ссылка «Сообщить о проблеме», если личность и установка уже известны.

Сообщение «Смена недоступна» без причины запрещено.

### 8.4. Ошибка команды

Серверная причина переводится в пользовательский текст и действие:

| Причина | Сообщение | Следующее действие |
|---|---|---|
| версия состояния устарела | «Смена изменилась на другом устройстве» | «Обновить состояние» |
| команда уже выполнена | «Действие уже сохранено» | открыть подтверждённый результат |
| нет полномочия | конкретная причина ограничения | «Обратиться к ответственному» при наличии контакта |
| обязательное условие не выполнено | название условия | перейти к требуемому шагу |
| установка занята другой сменой | имя или должность ответственного без лишних личных данных | «Обновить» |
| ошибка сервера | «Не удалось выполнить действие. Данные не потеряны» | «Повторить» |

### 8.5. Работа без связи

В верхней области постоянно показывается одно из состояний:

- «Все данные переданы»;
- «Есть данные для отправки: N»;
- «Отправляем данные»;
- «Нет связи»;
- «Обнаружено противоречие»;
- «Срок разрешённой работы без связи истёк».

Правила:

- локально разрешённое действие подтверждается текстом «Сохранено на устройстве»;
- рядом указывается количество непереданных действий;
- оператор может открыть очередь и увидеть каждую запись;
- опасное событие и дефект сохраняются на устройстве даже без разрешения продолжать производство;
- начало смены, возобновление после критической остановки, передача и закрытие запрещаются без действующего ограниченного разрешения и необходимых серверных фактов;
- истечение разрешения не удаляет данные, но меняет главное действие на безопасно допустимое;
- после восстановления связи переход этапа выполняется только после подтверждения сервера;
- противоречие не предлагается «перезаписать» оператору. Экран сохраняет обе версии и сообщает, кому передано рассмотрение.

Интерфейс показывает срок действия ограниченного разрешения, установку, смену и точный перечень разрешённых без связи действий. Надпись «Нет связи» сама по себе не означает разрешение продолжать работу. Без действующего разрешения производственная запись, начало смены, возобновление, передача и закрытие недоступны; дефект, опасное событие и фотография сохраняются на устройстве.

### 8.6. Нет назначенной установки

Карточка показывает:

- «Установка не назначена»;
- пояснение «Для начала смены ответственному сотруднику необходимо назначить установку и объект»;
- контакт ответственного, если доступен;
- действие «Обновить».

Создать смену на чужой или произвольной установке невозможно.

### 8.7. Смена на другом устройстве

Если сервер сообщает об активной смене оператора или установки:

- показываются установка, время начала и последнее устройство, если это разрешено;
- предлагается «Продолжить существующую смену» после повторной проверки личности;
- новая смена не создаётся;
- при невозможности продолжения показывается конкретный порядок обращения.

## 9. Семь фаз маршрута

### 9.1. Фаза 1 — допуск оператора

**Цель:** подтвердить личность, назначение, квалификацию и документы.

**Экран показывает:**

- имя оператора;
- назначенные установки;
- действующие документы и квалификации в свёрнутом виде;
- препятствия и замечания по документам;
- необходимость повторного подтверждения личности;
- объект каждой назначенной установки.

**Главное действие:**

- «Подтвердить личность», если это требуется политикой;
- иначе «Выбрать установку».

**Положительный исход:** личность и допуск подтверждены, оператор переходит к получению выбранной установки.

**Отказ:** показывается конкретный документ, срок или несовместимая смена. Кнопка продолжения отсутствует; доступны обновление и обращение к ответственному.

**Серверный эффект:** проверка текущего пользователя, организации, роли, квалификации, документов, назначения и конфликтующих активных смен. Выбор установки сам по себе не считается её получением.

### 9.2. Фаза 2 — получение установки

**Цель:** осознанно принять конкретную установку и сведения предыдущей смены.

**Экран показывает:**

- фотографию, название и модель;
- объект;
- предыдущего оператора;
- сведения передачи или честную причину её отсутствия;
- последние моточасы и источник показания;
- топливо при наличии;
- открытые замечания и дефекты;
- последнее и следующее обслуживание;
- ограничения следующей смены.

**Главное действие:** «Принять установку».

Если назначено несколько установок, сначала показывается выбор. Если предыдущей передачи нет, перед подтверждением показывается отдельное предупреждение и разрешённый порядок получения без передачи. Автоматическое принятие запрещено.

**Серверный эффект:**

- при отсутствии смены создаётся смена для выбранной назначенной установки;
- при наличии входящей передачи выполняется её принятие;
- фиксируются оператор, установка, время, местоположение и точность, устройство, состояние, моточасы, топливо и связь с передачей;
- возвращаются новая версия смены и допустимые действия.

**Ограничение текущего v2, которое запрещено переносить:** получение без входящей передачи и факт подтверждения не могут храниться только в памяти вкладки.

### 9.3. Фаза 3 — проверки до работы

**Цель:** собрать доказательства состояния установки и рабочей зоны.

Фаза состоит из последовательных коротких групп:

1. установка;
2. рабочее оборудование;
3. защитные системы;
4. рабочая зона;
5. показания и условия.

Для каждого пункта доступны только результаты:

- «В норме»;
- «Есть замечание»;
- «Неисправность»;
- «Не применяется».

Для замечания и неисправности интерфейс раскрывает требуемые описание и фотографию. Для «Не применяется» требуется причина, если она не определена правилом.

**Главное действие:** «Сохранить группу» или на последней группе «Завершить проверку».

Прогресс показывается числом «Выполнено X из Y», но не как процент готовности. После возвращения оператор продолжает с первого незавершённого пункта.

**Серверный эффект:** создаётся или открывается проверка текущей смены, ответы сохраняются с версией шаблона и доказательствами, завершение проверки создаёт неизменяемое событие и запускает расчёт технической готовности. Рабочая зона сохраняется на сервере, а не в памяти страницы.

### 9.4. Фаза 4 — подготовка и допуск к работе

**Цель:** выполнить оставшиеся действия и получить объяснимое решение о возможности начала работы.

Карточка «Допуск» показывает одно из четырёх решений:

- «Работа разрешена»;
- «Работа разрешена с замечаниями»;
- «Работа запрещена»;
- «Недостаточно данных».

Ни балл, ни процент не показываются.

Под решением выводятся условия:

- документы оператора;
- получение установки;
- проверка до работы;
- рабочая зона;
- моточасы;
- обслуживание;
- открытые дефекты;
- защитные системы.

Для каждого условия показываются знак, русский результат, время и источник. Нажатие открывает цепочку «условие → доказательство → правило → результат → следующее действие».

**Главное действие зависит от решения:**

- «Начать смену» — при актуальном разрешении;
- «Начать смену с замечаниями» — при разрешении с замечаниями, после просмотра замечаний;
- действие устранения первого препятствия — при запрете;
- «Обновить данные» — при устаревшей оценке;
- «Повторить расчёт» — при ошибке расчёта.

«Запросить разрешение диспетчера» не является обычным действием. Оно показывается только для препятствия, которое правила разрешают обойти, и содержит причину, срок и ограничения исключения.

**Серверный эффект:** сервер заново проверяет полномочия, назначение, версию состояния, обязательные проверки, документы, обслуживание, дефекты и актуальность решения; при успехе фиксирует начало, моточасы, топливо, местоположение, версии правил и проверки, оценку готовности и фактическое время.

### 9.5. Фаза 5 — работа

**Цель:** выполнять производственное задание и фиксировать события без ухода из смены.

Экран показывает:

- «Смена активна»;
- время с начала смены;
- текущие моточасы;
- объём выполненной работы;
- длительность текущего перерыва или простоя;
- решение о возможности продолжать работу;
- состояние связи.

**Главное действие:** «Записать выполненную работу».

Форма производственной записи содержит только допустимые объектом значения: сваю, пикет, тип, глубину, время, координаты, результат и комментарий. Автоматически полученные значения подписываются источником; изменение требует причины.

Дополнительные действия фазы:

- «Начать перерыв» / «Завершить перерыв»;
- «Начать простой» / «Завершить простой»;
- «Разрешённое обслуживание»;
- «Завершить производственные работы»;
- постоянные действия безопасности.

Одновременно может существовать только один активный интервал перерыва или простоя. Для простоя обязательны причина и категория. Если простой связан с дефектом или обслуживанием, связь выбирается из существующих записей.

**Серверный эффект:** каждая запись сохраняется в текущей смене с уникальным ключом повторной отправки, фактическим временем, устройством и ожидаемой версией. Производственная запись обновляет черновик отчёта, но не отправляет его. Критический дефект или опасное событие запускает новую оценку и может включить безопасную остановку.

### 9.6. Прерывание — безопасная остановка

Это не отдельная фаза, а обязательный прерывающий сценарий.

При критическом событии поверх текущей фазы показываются:

- заголовок «Требуется безопасная остановка»;
- конкретная последовательность действий для вида установки;
- признаки и источник требования;
- запрет производственных записей;
- главное действие «Подтвердить безопасную остановку».

После подтверждения экран показывает «Работа остановлена» и ожидаемые действия механика или другого ответственного. Возобновление возможно только после устранения, независимой проверки при необходимости и новой актуальной оценки с разрешением.

**Серверный эффект:** фиксируются опасное событие, требование остановки, фактическое подтверждение остановки, связанные доказательства и запрет возобновления. Запись о завершении ремонта сама по себе запрет не снимает.

### 9.7. Фаза 6 — завершение смены

**Цель:** завершить производственную часть, проверить состояние установки после работы и подтвердить отчёт.

Последовательность внутри фазы:

1. подтвердить завершение производственных работ;
2. снять конечные моточасы и топливо;
3. выполнить проверку после работ, если она предусмотрена шаблоном;
4. выполнить обязательное ежесменное обслуживание;
5. просмотреть автоматически сформированный отчёт;
6. добавить только отсутствующие пояснения;
7. подтвердить отчёт.

**Главное действие:** действие первого незавершённого подпункта. На итоговом экране — «Подтвердить отчёт».

Система сравнивает одинаковые пункты проверок до и после работы. Ухудшения показываются отдельным блоком и автоматически включаются в передачу. Если проверка после работ не предусмотрена опубликованным шаблоном, интерфейс честно сообщает «Проверка после работ не требуется» и не создаёт тупик.

**Серверный эффект:** сохраняются конечные показания, проверка после работ, обслуживание и подтверждение отчёта. Отчёт собирается из событий смены. Его подтверждение является отдельной командой и не закрывает смену.

### 9.8. Фаза 7 — передача установки

**Цель:** передать ответственному актуальное состояние установки и закрыть смену.

Экран показывает:

- принимающего оператора, если он назначен;
- начальные и конечные моточасы;
- топливо;
- выполненную работу и простои;
- новые замечания;
- открытые дефекты;
- выполненное обслуживание;
- ухудшения после работы;
- ограничения следующей смены;
- итоговое пояснение передачи.

**Главное действие:** «Передать установку».

После отправки показывается состояние «Ожидается принятие». Передавший не может принять собственную передачу. После принятия или разрешённого закрытия без принимающего сервер возвращает закрытую смену, экран показывает итог и обычное навигационное действие «Вернуться к сменам». Навигационная кнопка не закрывает смену и не имитирует деловой эффект.

Закрытие без принимающего доступно только пользователю с отдельным полномочием; обычному оператору показывается назначенный порядок обращения.

**Серверный эффект:** создаётся передача со снимком состояния, затем отдельная команда принимающего фиксирует принятие. Смена закрывается только после обязательных проверок, обслуживания, подтверждённого отчёта и разрешённого завершения передачи.

## 10. Формы постоянных действий

### 10.1. Дефект

Поля:

- узел установки;
- описание наблюдаемого состояния;
- наблюдаемые признаки: утечка, потеря давления, отказ защитной системы, дым, запах, необычный шум, самопроизвольное движение, аварийная остановка, другое;
- фотография по правилу;
- подтверждение фактической остановки, если она уже выполнена;
- время возникновения, если отличается от времени ввода.

Оператор не отвечает на вопрос «Можно ли работать?» и не выбирает критичность. Её определяет правило по наблюдаемым признакам. Это заменяет опасное упрощение v2, где оператор вручную выбирает «Да, стою» и тем самым назначает критичность.

После сохранения показываются классификация системы, требуемое действие и адресаты уведомления.

### 10.2. Опасное событие

Поля:

- категория;
- что произошло;
- есть ли пострадавшие;
- применена ли аварийная остановка;
- текущее безопасное состояние;
- фотографии и другие обязательные доказательства;
- местоположение и время;
- связь с дефектом при наличии.

Форма никогда не требует завершить загрузку фотографии перед показом инструкции безопасной остановки.

### 10.3. Фотография

Перед съёмкой оператор выбирает назначение: установка, рабочая зона, проверка, дефект, опасное событие, обслуживание или передача. Если фотография вызвана из конкретной формы, назначение заполняется автоматически.

Показываются предварительный просмотр, дата, состояние сохранения и действие «Переснять». Закрытие до сохранения требует предупреждения.

### 10.4. Разрешённое обслуживание

Показываются только разрешённые оператору операции из действующей версии регламента: осмотр, очистка, контроль уровней, дозаправка, предусмотренная смазка и внешний контроль соединений. Ремонтные действия механика оператору не предлагаются.

## 12. Договор состояния интерфейса

Единый ответ для экрана должен содержать как минимум:

- пользователя и подтверждение личности;
- назначения;
- текущую установку и объект;
- смену, её этап, рабочий режим и версию;
- семь этапов с состояниями и доказательствами;
- текущее решение о технической готовности;
- состояние оценки и время расчёта;
- условия, препятствия, замечания и действия устранения;
- допустимые следующие действия;
- проверки до и после работы;
- рабочую зону;
- начальные и последние моточасы с источником;
- активные перерыв, простой или обслуживание;
- объём работ;
- открытые дефекты и опасные события;
- отчёт и передачу;
- состояние обмена, очередь и срок разрешённой работы без связи;
- контакты ответственных в пределах полномочий.

Текущий `/api/operator/shift` является полезной основой, но не покрывает целевой договор полностью: в нём отсутствуют серверно сохранённое получение без передачи, рабочая зона, отдельный рабочий режим, состояние обмена, доказательства условий, опасные события, обслуживание и полный итог передачи.

## 13. Реальные серверные эффекты и переходный договор

### 13.1. Уже существующие взаимодействия, которые следует переиспользовать

| Действие | Текущий запрос | Фактический эффект |
|---|---|---|
| загрузить смену | `GET /api/operator/shift` | возвращает назначения, установку, смену, готовность, осмотры, отчёт, моточасы, передачу и допуск оператора |
| открыть смену | `POST /api/readiness/shifts` | создаёт смену на назначенной установке |
| запросить принятие | `POST /api/readiness/shifts/{смена}/request-acceptance` | переводит плановую смену к подтверждению получения |
| начать смену | `POST /api/readiness/shifts/{смена}/start` | повторно проверяет условия и фиксирует начало |
| принять передачу | `POST /api/readiness/handovers/{передача}/accept` | фиксирует другого принимающего пользователя |
| передать установку | `POST /api/readiness/shifts/{смена}/handover` | создаёт передачу и переводит смену в ожидание принятия |
| создать проверку | `POST /api/inspections` | создаёт проверку до или после работы для текущей смены |
| сохранить проверку | `PUT /api/inspections/{проверка}` | сохраняет ответы проверки |
| завершить проверку | `POST /api/inspections/{проверка}/complete` | закрывает проверку и создаёт основания для пересчёта готовности |
| создать дефект | `POST /api/readiness/defects` | создаёт доменный дефект, видимый контуру готовности и механику |
| получить черновик отчёта | `GET /api/reports/edit` | возвращает текущий отчёт объекта и даты |
| сохранить или подтвердить отчёт | `POST /api/reports/upsert` | сохраняет производственные строки и простои либо подтверждает отчёт |

Критические команды смены обязаны передавать уникальный ключ повторной отправки и ожидаемую версию. Один и тот же ключ с тем же содержимым возвращает прежний результат; с другим содержимым — отклоняется.

### 13.2. Недостающие серверные возможности для полного v3

До признания модуля полноценным необходимы серверные команды или подтверждённые эквиваленты:

- сохранить получение установки без входящей передачи;
- сохранить проверку рабочей зоны;
- записать начальные и конечные моточасы в контексте смены;
- получить объяснимую цепочку условий и доказательств готовности;
- начать и завершить перерыв;
- начать и завершить простой отдельными временными событиями, а не только числом часов в отчёте;
- зарегистрировать производственное действие с фактическим временем и местоположением;
- зарегистрировать опасное событие;
- подтвердить безопасную остановку;
- зарегистрировать разрешённое обслуживание;
- проверить устранение дефекта;
- возобновить работу после новой оценки;
- начать завершение производственных работ;
- подтвердить итоговый отчёт, связанный именно со сменой;
- закрыть смену после принятия передачи;
- получить и отправить очередь работы без связи;
- зарегистрировать исправляющее событие.

Интерфейс не должен имитировать успех недостающей команды локальным переключателем. До появления команды действие либо честно помечается недоступным в испытательной сборке, либо реализуется вертикально вместе с серверным эффектом.

### 13.3. Запрет фиктивных действий

Каждый интерактивный элемент относится к одному проверяемому типу: серверная команда, серверное чтение, локальный черновик, действие устройства либо навигация. Кнопка запрещена, если её обработчик только показывает уведомление об успехе, меняет фазу в памяти или подменяет отсутствующий серверный эффект. Для серверной команды обязательны доказательства: запрос, успешный ответ, ровно одна деловая запись, результат в повторном чтении и тот же результат после обновления страницы. Для локального черновика показывается только «Черновик сохранён на устройстве», а не деловой успех.

## 14. Правила главного действия

1. На экране только одна кнопка главного действия.
2. Текст начинается с глагола и описывает конкретный эффект: «Принять установку», а не «Продолжить».
3. Заблокированная кнопка не является единственным объяснением: рядом указывается причина и доступное действие.
4. Если первое препятствие устранимо оператором, главным становится действие устранения.
5. Если препятствие устраняет другая роль, главное действие — «Обновить состояние» после сообщения, кому передана задача; обращение к ответственному показывается отдельно.
6. При действующем простое главным становится «Завершить простой»; при перерыве — «Завершить перерыв».
7. При требовании остановки любая производственная кнопка скрывается, главное действие — «Подтвердить безопасную остановку».
8. При несохранённой форме главное действие относится к форме, а не к этапу.
9. При отправке кнопка сохраняет ширину и подпись действия, добавляя состояние выполнения.
10. После успеха фокус перемещается на заголовок нового шага.

## 15. Цвет, знаки и визуальная иерархия

- основной рабочий цвет — глубокий синий или зелёный с подтверждённой контрастностью;
- разрешение — зелёный, знак подтверждения и текст;
- замечание — янтарный, знак предупреждения и текст;
- запрет — красный, знак запрета и текст;
- неизвестное или расчёт — нейтральный синий или серый, знак ожидания и текст;
- работа без связи — тёмный янтарный, знак отсутствия связи и текст;
- завершённая смена — нейтральный спокойный цвет без праздничной анимации, мешающей чтению итогов.

Красный цвет не используется для отмены, обычного закрытия формы или некритичного дефекта. Цвет никогда не является единственным носителем смысла.

## 16. Доступность

Обязательные требования:

- соответствие не ниже двойного уровня А стандарта доступности веб-содержимого в части контраста, клавиатуры, подписей и сообщений;
- минимальная область нажатия 48 × 48 точек;
- видимый указатель фокуса;
- логичный порядок фокуса сверху вниз;
- полное управление клавиатурой без мыши;
- заголовок каждого слоя получает фокус при открытии;
- модальное окно удерживает фокус и возвращает его вызвавшей кнопке;
- все поля имеют постоянные видимые подписи;
- ошибки связываются с полем и объявляются программой экранного доступа;
- состояния отправки и изменения этапа объявляются через область сообщений;
- фотографии имеют осмысленное описание или пометку «Доказательство без текстового описания»;
- знаки состояния имеют текстовый эквивалент;
- увеличенный до 200 процентов текст не обрезает команды;
- ориентация экрана не ограничивается;
- таймер смены не является единственным источником времени;
- действие не зависит только от долгого нажатия, перетаскивания или жеста;
- движение и анимация отключаются при системном предпочтении уменьшенного движения;
- автофокус не вызывает неожиданное открытие клавиатуры при загрузке.

## 17. Защита от ошибочных действий

Повторное подтверждение требуется для:

- начала смены с замечаниями;
- сообщения об опасном событии;
- подтверждения безопасной остановки;
- завершения производственных работ;
- передачи установки;
- запроса разрешённого исключения.

Подтверждение не формулируется как абстрактное «Вы уверены?». Оно повторяет результат: «После подтверждения производственные записи будут закрыты, и начнётся проверка после работ».

Для обычных частых записей — производственной работы, фотографии и некритичного замечания — лишнее подтверждение не требуется. После сохранения доступно исправляющее действие, если оно разрешено.

## 18. Журнал смены

Журнал строится по времени возникновения, при этом отдельно показывает время получения сервером. Каждая запись содержит:

- русское название действия;
- автора;
- фактическое время;
- состояние передачи;
- связанную установку и этап;
- краткий итог;
- ссылку на доказательства;
- связь с исправляющим событием.

Фильтры: «Все», «Работа», «Проверки», «Простои», «Дефекты», «Безопасность», «Обслуживание», «Передача».

Запись без связи помечается «Сохранено на устройстве». Поздняя запись не переставляет молча историческое решение; рядом показывается «Получено позже» и ссылка на ретроспективную оценку.

## 19. Сведения об установке

Раздел содержит:

- название, модель и фотографию;
- объект и назначение;
- текущие и последние подтверждённые моточасы с источником;
- топливо при наличии;
- открытые дефекты и ограничения;
- последнее и следующее обслуживание;
- документы установки;
- рабочее оборудование;
- историю передач текущей смены.

Все сведения доступны для просмотра. Редактирование административных полей отсутствует.

## 20. Телеметрия интерфейса без личных данных

Для оценки работоспособности фиксируются:

- время открытия текущего шага;
- время выполнения каждой фазы;
- количество отказов команд по типу причины;
- повторы отправки;
- размер и возраст очереди;
- доля незавершённых форм;
- возвраты к предыдущему этапу для просмотра;
- случаи начала безопасной остановки;
- время от препятствия до следующей актуальной оценки.

В диагностические события не включаются фотографии, свободные комментарии, документы, личные коды и полные сведения о местоположении.

## 21. Критерии браузерной приёмки

Сборка и ответы запросов не заменяют проверку в браузере. Каждый сценарий проходит под настоящей ролью оператора и с серверной проверкой результата.

### 21.1. Телефон

Проверить размеры 320 × 568, 360 × 800, 390 × 844 и 430 × 932:

- нет горизонтальной прокрутки;
- заголовок установки, решение и главное действие видимы и не перекрываются;
- области нажатия не меньше 48 × 48 точек;
- нижняя панель не перекрывает последнее поле;
- экранная клавиатура не скрывает подтверждение;
- камера возвращает в исходную форму;
- маршрут читаем при увеличении текста до 200 процентов;
- все семь фаз проходятся без перезагрузки страницы;
- постоянные действия безопасности доступны на каждой фазе;
- при безопасной остановке производственное действие исчезает;
- история и очередь открываются и закрываются с возвратом фокуса;
- нет ошибок и необработанных предупреждений в консоли браузера.

### 21.2. Настольный экран

Проверить размеры 1024 × 768, 1366 × 768, 1440 × 900 и 1920 × 1080:

- три зоны не накладываются;
- главное действие остаётся единственным акцентным;
- маршрут, текущий шаг и техническая готовность читаются одновременно;
- весь сценарий управляется клавиатурой;
- увеличение до 200 процентов переводит экран в промежуточную компоновку без потери действий;
- административные команды не появляются у оператора;
- нет ошибок и необработанных предупреждений в консоли.

### 21.3. Семь обязательных сквозных сценариев

1. **Обычная смена:** вход → выбор → получение → проверка → рабочая зона → моточасы → разрешение → начало → работа → завершение → проверка после работ → отчёт → передача → принятие → закрытие.
2. **Замечания без запрета:** замечание в проверке → обязательное доказательство → «Работа разрешена с замечаниями» → осознанный пуск → замечание попадает в журнал и передачу.
3. **Критический дефект до пуска:** признаки дефекта → фотография → «Работа запрещена» → механик устраняет → другой уполномоченный проверяет → новая оценка → разрешение.
4. **Опасное событие во время работы:** запись события → инструкция → безопасная остановка → производственные действия заблокированы → устранение → повторная оценка → возобновление.
5. **Потеря связи:** разрешённые записи сохраняются на устройстве → счётчик очереди растёт → перезапуск не теряет записи → связь восстанавливается → сервер принимает каждую запись один раз → этап совпадает с сервером.
6. **Противоречие:** второе устройство изменяет смену → устаревшая команда отклоняется → показывается понятное сообщение → обе версии сохранены → оператор не может молча перезаписать сервер.
7. **Передача без принимающего:** обычный оператор не видит полномочия закрытия → ответственному отправлено уведомление → уполномоченный закрывает с причиной → оператор видит итог.

### 21.4. Проверка серверных эффектов

После каждого действия проверяется не только экран, но и авторитетное состояние:

- создана ровно одна деловая запись;
- организация и установка совпадают с назначением;
- версия состояния увеличена ожидаемо;
- записаны автор, устройство, фактическое и серверное время;
- ключ повторной отправки сохранён;
- создано событие аудита;
- решение о готовности ссылается на использованные доказательства;
- повтор запроса не создаёт дубликат;
- обновление страницы восстанавливает тот же этап;
- другой оператор не видит и не изменяет чужую смену;
- закрытая смена не изменяется обычной командой.
- отказ сервера не переводит интерфейс на следующую фазу;
- двойное нажатие и повтор после потери ответа создают одну запись;
- повторная загрузка и второй настоящий сеанс видят одно авторитетное состояние;
- каждая кнопка с деловым смыслом создаёт ожидаемый запрос, а не только уведомление.

### 21.5. Ошибки и работа без связи

Проверить:

- медленный ответ более двух секунд;
- отсутствие ответа;
- ответ с ошибкой полномочия;
- устаревшую версию;
- повтор команды;
- разрыв связи до отправки, во время отправки и после серверного сохранения до получения ответа;
- перезапуск вкладки с непереданными данными;
- истечение разрешения работы без связи;
- изменение часов устройства;
- неуспешную загрузку одной фотографии при успешном сохранении события;
- позднее событие, влияющее на прошлый интервал;
- отзыв устройства.

### 21.6. Доступность

Проверить клавиатурой и программой экранного доступа:

- порядок заголовков;
- названия всех кнопок без опоры на пиктограмму;
- связь ошибок с полями;
- объявление загрузки, успеха, ошибки и смены этапа;
- удержание и возврат фокуса в формах;
- различимость состояний без цвета;
- режим высокой контрастности;
- уменьшенное движение;
- масштаб 200 процентов.

## 22. Условия готовности интерфейса к выпуску

Выпуск `/operator/v3` запрещён, если выполняется хотя бы одно условие:

- какая-либо из семи фаз существует только в памяти вкладки;
- оператор вручную назначает критичность или решение о готовности;
- на основном экране одновременно присутствуют два главных акцентных действия;
- дефект, опасное событие или фотография недоступны на какой-либо фазе;
- готовность показана баллом или процентом;
- запрет не объясняет причину и следующее действие;
- обновление страницы теряет подтверждённое действие;
- повтор команды создаёт дубликат;
- смена может начаться по клиентскому решению без серверной проверки;
- работа без связи разрешается без срока, области и подписанного серверного разрешения;
- критическое событие не закрывает производственные действия;
- завершение ремонта автоматически снимает препятствие;
- передавший принимает собственную передачу;
- пользовательские термины не на русском языке;
- не пройдены реальные браузерные сценарии на телефоне и настольном экране;
- не подтверждена изоляция организаций и назначений;
- в консоли браузера остаются ошибки основного сценария;
- недостающий серверный эффект имитируется локальным переключателем.

## 23. Отличия от `/operator/v2`

### 23.1. Граница использования прототипов

Прототип «Маршрут» задаёт иерархию экрана, а прототип «Допуск» — объяснимую проверку условий. Они не являются доказательством работоспособности. Из них запрещено переносить баллы и проценты готовности, переход фаз по локальному счётчику и фиктивные уведомления об открытии камеры, звонка, дефекта или отчёта. Реализация сохраняет композицию прототипов, но получает этап, решение и допустимые действия только из серверного договора.

В v3 сохраняются полезные реальные взаимодействия v2: единый экран, выбор назначенной установки, осмотры, производственные записи, дефект, простой, отчёт и передача.

Обязательные изменения:

- восемь экранных шагов v2 приводятся к семи продуктовым фазам;
- «Рабочая зона» становится серверно сохранённой частью фазы проверок;
- получение без передачи сохраняется на сервере;
- «Допуск» показывает решение и доказательства без процентов;
- главное действие одно; служебные действия уходят во вторичный уровень;
- дефект, опасное событие и фотография доступны постоянно;
- оператор сообщает наблюдаемые признаки, а не выбирает критичность;
- простой становится временным интервалом, а не только строкой с количеством часов в отчёте;
- добавляются опасное событие, безопасная остановка, обслуживание, возобновление и очередь отправки;
- сервер возвращает допустимые следующие действия, чтобы клиент не расходился с доменными правилами;
- закрытый экран не утверждает «смена успешно завершена», пока передача лишь ожидает принятия.

## 24. Рекомендуемая последовательность реализации

1. Утвердить единый серверный договор состояния экрана и причины отказа.
2. Реализовать вертикальный путь «допуск → получение → проверка → готовность → начало» без локальных подмен.
3. Реализовать рабочий экран, производственные записи, перерыв и простой.
4. Реализовать дефект, опасное событие и безопасную остановку.
5. Реализовать устранение, повторную оценку и возобновление.
6. Реализовать завершение, проверку после работ, отчёт, передачу и закрытие.
7. Добавить защищённое локальное хранение и отправку для каждого уже работающего вертикального пути.
8. Провести браузерную приёмку под настоящими ролями на телефоне и настольном экране.

## 25. Открытые риски

1. Текущий договор `/api/operator/shift` отдаёт только часть целевых пяти контуров состояния.
2. Получение установки без входящей передачи и рабочая зона в v2 не сохраняются на сервере.
3. Текущий дефект v2 позволяет оператору вручную назначить критичность; это противоречит продуктовой модели.
4. Простой сейчас сохраняется как длительность в отчёте, а не как проверяемый интервал начала и окончания.
5. Нет подтверждённого сквозного договора опасного события и безопасной остановки.
6. Нет подтверждённого клиентского контура защищённой работы без связи и разрешения противоречий.
7. Текущая готовность содержит балл; v3 не должен показывать его и должен получать объяснимые условия и доказательства.
8. Отчёт v2 ищется по объекту и дате; целевой отчёт должен быть однозначно связан со сменой.
9. До проверки под настоящим оператором нельзя считать доказанными границы назначений и все пользовательские переходы.
10. Переход от существующих состояний смены к семи пользовательским фазам должен иметь единый серверный договор, иначе клиентская логика снова станет вторым источником истины.

## 26. Итоговое решение

`/operator/v3` должен быть не новой оболочкой над v2, а единым рабочим местом оператора:

- «Маршрут» определяет, что делать сейчас;
- «Допуск» объясняет, можно ли выполнять действие;
- постоянные действия безопасности доступны всегда;
- сервер подтверждает каждый существенный переход;
- работа без связи ограничена и наблюдаема;
- весь жизненный цикл смены проходит в одном модуле на телефоне и настольном экране.

Критерий качества прост: после обновления страницы, смены устройства или восстановления связи оператор и сервер должны видеть один и тот же этап, одно и то же решение и одну и ту же неизменяемую историю действий.
