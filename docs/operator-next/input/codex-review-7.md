**Новые дефекты**

- **[важно] `ef9a8fd4`, `src/components/piling/operator-next/operator-next-app.tsx:224` — маркер прежней пары переживает переход к непрочитанной паре, хотя её память уже заменяется.**

  В показанном `reload` возможна последовательность:

  1. Пара А успешно загружена: маркер равен А.
  2. Переход к Б, чтение Б отказывает: память становится пустой памятью Б, маркер остаётся А.
  3. Возврат к А, чтение А тоже отказывает: память становится пустой памятью А, маркер по-прежнему А.
  4. Следующее чтение А успешно, но `wasLoaded === true` и текущая память уже принадлежит А. Поэтому `setDrafts` возвращает пустую память, игнорируя прочитанный документ.

  Следовательно, показанная логика может перестать восстанавливать доступный документ. Если автосохранение разрешается по совпадению маркера и пары, на шаге 3 оно также может записать пустую память поверх документа.

  **Как исправить:** отдельно отслеживать смену активной пары и при каждом переходе инвалидировать признак загрузки до обработки чтения. Отказ повторного чтения *неизменной* пары должен сохранять маркер. Добавить тест А → Б с отказом → А с отказом → успешное чтение А, проверяющий весь документ и запрет преждевременной записи.

  **Нужно проверить:** нет ли вне фрагмента обязательного сброса `draftsLoadedRef` при каждом изменении пользователя **или смены**; также нужен полный код автосохранения. Такой сброс может исключить сценарий в приложении.

  **Уверенность: средняя** — поведение показанного `reload` однозначно, достижимость без внешнего сброса и перезапись документа зависят от непоказанного кода.

Обычный переход А→Б с первым отказом чтения Б сам по себе не помечает Б загруженной. Обнаруженный риск связан именно с возвратом к сохранившемуся старому ключу.
