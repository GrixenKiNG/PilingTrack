# J7: пять сирот ReportAnalytics — резервная копия и репетиция

## Граница выполненной работы

`scripts/cleanup-report-analytics-orphans.cjs` работает **только** с собственным
`codex-pg-<12 hex>`: обязательны ownership label `pilingtrack.codex.test-db=1`,
работающий контейнер, единственный опубликованный `127.0.0.1:port`, совпадающий
с `INTEGRATION_DATABASE_URL_OWNER`, база `codex_test`, существующий владелец `piling`.
Скрипт не загружает `.env`, не выбирает общий контейнер и не подключается к production.
Реальные пять строк из общей локальной базы **не удалены**. Наличие этих строк в
production не проверено. W12 содержит снимок локальной БД от 06.10.2026 19:29 UTC.

Это разовая чистка пяти явных ключей, а не общее удаление сирот. Планировщик,
rebuild и обработчик удаления отчёта не менялись. Следовательно, этот скрипт
не гарантирует, что новые сироты никогда не появятся. Строки `ReportVersion` и
`ReportAudit`, включая найденные Hermes 71+71, не входят в задание и не удаляются.

## Репетиция на собственном Postgres

Использовать только переменные, уже выданные `scripts/test-db-up.sh` для своего
контейнера; не подставлять адрес общей или боевой БД. По умолчанию — dry-run,
в том числе если выбранных строк нет:

```bash
node scripts/cleanup-report-analytics-orphans.cjs --container "$INTEGRATION_DB_CONTAINER"
node scripts/cleanup-report-analytics-orphans.cjs --container "$INTEGRATION_DB_CONTAINER" --apply --backup "<абсолютный путь>/j7-before.json"
node scripts/cleanup-report-analytics-orphans.cjs --container "$INTEGRATION_DB_CONTAINER" --restore "<абсолютный путь>/j7-before.json"
```

`--apply` требует ровно пять строк организации `orion` и отсутствие живого
`Report` с любым из этих ключей **во всех организациях**. Для этого нужна уже
существующая owner-роль с глобальным чтением. Скрипт не отключает RLS и триггеры.
Входящий FK на `ReportAnalytics` или включённый пользовательский триггер вызывает
отказ, даже если кажется безвредным. Блокировки `Report` и `ReportAnalytics`
удерживаются до commit/rollback; ожидание ограничено тремя секундами.

Бэкап содержит все столбцы пяти строк, описание столбцов и SHA-256 содержимого.
Файл создаётся исключительно через `wx`, синхронизируется и повторно проверяется
**до DELETE**. Уже существующий файл, относительный путь, расширение кроме `.json`
или компонент пути `.env*` запрещены. Запись в существующий файл/симлинк не допускается.
Защитите каталог резервных копий: режим `0600` сам по себе не гарантирует ACL Windows.
SHA-256 обнаруживает повреждение; это не цифровая подпись и не защита от намеренной
подмены файла вместе с его checksum.

DELETE ограничен одновременно организацией, явными ключами и `NOT EXISTS Report`.
`RETURNING` должен точно совпасть с бэкапом; после удаления известные ключи должны
отсутствовать. Восстановление требует прежнюю схему и отсутствие всех ключей/id и
живых отчётов; вставляет все столбцы без `ON CONFLICT`. Повторное восстановление
отказывается и откатывает транзакцию. Бэкап после применения сохраняется.

Ошибка до commit оставляет строки нетронутыми; неполный файл после ошибки записи
не считается бэкапом. Если процесс оборвался при commit и подтверждение потеряно,
результат неопределён: сначала заново проверить пять ключей и бэкап, не повторять
применение или восстановление вслепую.

Проверка на own Postgres использует существующий файл тестов:

```bash
npx --no-install vitest run --config vitest.integration.config.ts tests/integration/disposable-scripts.spec.ts
```

Без own DB переменных тесты Postgres пропускаются; это не проверка чистки в БД.
Тесты создают отдельные фикстуры, доказывают сохранение неизвестной шестой сироты,
живой проекции и другого tenant, точное восстановление, отказ при живом отчёте
другой организации, FK/триггере, недостаточном наборе, существующем бэкапе и его
повреждении. После проверки удаляются только собственные фикстуры.

## Владельцу: настоящая база, отдельное решение

Репетиционный скрипт сознательно откажет на `pilingtrack-postgres` и production.
Не снимайте этот барьер для запуска на настоящих данных. Перед самостоятельной
чисткой владелец/DBA должен согласовать целевую БД и именно пять ключей ниже,
повторить каталоговую проверку FK/триггеров, сделать полный бэкап БД с проверенным
восстановлением, а затем сохранить полный снимок выбранных строк под блокировкой.
Нельзя считать старые числа W12 актуальными и нельзя использовать отсутствие
строк через tenant-scoped RLS как доказательство отсутствия отчётов.

Проверки для утверждённой owner-сессии, только чтение:

```sql
SELECT current_database(), current_user, rolsuper, rolbypassrls
FROM pg_roles WHERE rolname = current_user;
SELECT conname, conrelid::regclass
FROM pg_constraint
WHERE contype = 'f' AND confrelid = 'public."ReportAnalytics"'::regclass;
SELECT tgname, tgenabled
FROM pg_trigger
WHERE tgrelid = 'public."ReportAnalytics"'::regclass
  AND NOT tgisinternal AND tgenabled <> 'D';

SELECT to_jsonb(a) FROM public."ReportAnalytics" a
WHERE "tenantId" = 'orion' AND "reportId" IN (
  '00fc064e-924e-4456-b8d2-79ed2c69bf97',
  '5bf66128-a0d3-403c-8361-13e30c84cd9d',
  '880c6af8-b6df-4820-80a1-b9607b3e2ce3',
  '174f9e42-20d3-44d5-af7c-d6c59b4c97ad',
  'operator-v3-bfc41098-0efc-4f4f-ac02-be5d6d7c9369'
) ORDER BY "reportId";
SELECT "reportId", "tenantId" FROM public."Report"
WHERE "reportId" IN (
  '00fc064e-924e-4456-b8d2-79ed2c69bf97',
  '5bf66128-a0d3-403c-8361-13e30c84cd9d',
  '880c6af8-b6df-4820-80a1-b9607b3e2ce3',
  '174f9e42-20d3-44d5-af7c-d6c59b4c97ad',
  'operator-v3-bfc41098-0efc-4f4f-ac02-be5d6d7c9369'
);
```

Ожидается пять аналитических строк, ноль живых отчётов и отсутствие входящих FK/
включённых пользовательских триггеров. Любое отличие требует нового разбора.
Самостоятельное удаление владельцем должно повторять эти проверки **в одной
транзакции под блокировками**, сохранять полный бэкап до DELETE, проверять именно
пять `RETURNING` строк и завершающие счётчики. Не выполнять широкий DELETE всех
сирот. Команд удаления настоящих данных в этом runbook нет: сначала отдельное
разрешение владельца, актуальная инвентаризация и бэкап.
