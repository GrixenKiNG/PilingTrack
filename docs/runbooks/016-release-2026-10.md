2. На машине сборки: Docker доступен, дерево чистое, текущая ветка main, HEAD **точно** равен origin/main после fetch. Зафиксировать полный RELEASE_SHA и короткий SHA. Проверить git diff --check. Не запускать deploy из ночной ветки.

```bash
git status --short
git branch --show-current
git fetch origin main
git rev-parse HEAD
git rev-parse origin/main
```

3. На сервере вручную проверить диск (`df -h /`, `df -i /`) и `docker system df`. Нужен запас для готовых app/workers и сохранённого откатного набора; если места недостаточно — остановиться, не удалять тома или образы вслепую. Сборка на VPS не нужна. Сборка app и workers локально последовательно.
4. Зафиксировать текущий серверный OLD_SHA и фактические image IDs app/workers, тегнуть их `pilingtrack-app:$ROLLBACK` и `pilingtrack-workers:$ROLLBACK` (уникальный `<old-sha>-<date>`). Проверить, что оба откатных тега разрешаются в прежние IDs. deploy-prod.sh делает это автоматически, но оператор проверяет результат до переключения. При миграциях сохранить и migrate. До принятия релиза не удалять этот набор.
5. Проверить свежесть резервной копии/успешную репетицию восстановления по ранбукам 013/015. RPO/RTO этим потоком не задавались; при необходимости решение принимает владелец.
6. Проверить postgres, pgbouncer, redis (state), redis-cache, minio: уже работающие зависимости должны быть здоровы. Не перезапускать DB/Redis ради этого релиза. У всех app/worker процессов REDIS_URL должен вести в один state Redis с `noeviction`, REDIS_URL_CACHE — только кэш. Не выводить URL/пароли/всё окружение на экран.

## 2. Миграции, сборка и smoke

Сравнить **фактический** OLD_SHA с RELEASE_SHA:

```bash
git diff --name-only --diff-filter=A "$OLD_SHA..$RELEASE_SHA" -- 'prisma/migrations/**'
```

Для проверенного диапазона a803e61c..ночная ветка новых миграций нет. Это не заменяет сверку фактической версии на сервере. Если появились миграции: сначала разобрать SQL/данные, выполнить репетицию на копии по 008/015, локально пересобрать **migrate** вместе с app/workers. Иначе stale migrate-image ложно пишет «No pending migrations». Не использовать migrate reset/dev/db push.

Запустить workers smoke **на точном теге SHA**, без SKIP_WORKERS_SMOKE. deploy-prod.sh собирает workers и выполняет этот smoke до первого SSH:

```bash
bash scripts/smoke-workers-image.sh "pilingtrack-workers:$SHA"
```

Он подтверждает загрузку runner/start/Arming без сети; не доказывает реальные Redis/DB/Telegram/S3 задания.

Для app выполнить проверку артефактов runner (контейнер одноразовый, без сети):

```bash
docker run --rm --name codex-release-app-artifact --network none --entrypoint node \
  "pilingtrack-app:$SHA" -e 'const fs=require("fs"); for(const p of ["server.js",".next/static","src/generated/postgres-client/client.js"]) if(!fs.existsSync(p)) throw new Error("Missing "+p); require("./src/generated/postgres-client/client.js"); console.log("app artifacts OK")'
```

Это проверка состава образа, не пользовательский workflow. До переключения отдельно проверить запуск app и login/API на изолированном стенде с тестовой БД; не подключать smoke к production. Все контейнеры/сеть стенда удалить, сохранить exit/logs. На сервер отправлять уже готовые теги SHA, не собирать образы там.

## 3. Окно остановки: безопасная смена поколения I02

Rolling-update для этого релиза запрещён: старый leader использует cache Redis, новый — state Redis. Два независимых lease могут дать двух лидеров. App по умолчанию содержит embedded outbox/projection, поэтому заменить надо **app и workers вместе**, даже при запросе app-only или workers-only.

1. Согласовать короткое окно недоступности. До переключения отключить автозапуск и остановить **все** старые standalone workers, systemd/pm2, внешние compose-проекты и реплики на других хостах. Проверить PID/контейнеры, дождаться конца операций. Одна отметка health и один Redis-ключ этого не доказывают. Внешние процессы helper не обнаруживает — эту часть подтверждает оператор.
2. После этой проверки на машине сборки запустить новый режим:

```bash
WORKER_GENERATION_EXTERNAL_STOPPED=1 bash scripts/deploy-prod.sh --replace-worker-generation app workers
```

Скрипт последовательно проверит main/origin/main, соберёт и проверит workers, соберёт остальные образы, сохранит rollback, передаст образы, сверит git SHA на сервере и переключит теги. При миграциях сам добавит migrate.
3. Helper сначала проверяет все старые реплики, дедлайны, отсутствие one-off, однородность image/restart и RUNNING без мутаций. Затем snapshot imageIDs/restart/replica count, restart=no непосредственно перед STOP, inspect state/exit/OOM, shutdown logs и отсутствие RUNNING. Только затем START/force-recreate с ожиданием health. Порядок STOP → VERIFY → START; при ошибке — возврат старого поколения, см. ниже.
4. Compose timeout 30с. Старый unified worker имеет внутренний WORKER_SHUTDOWN_TIMEOUT_MS=8000 по умолчанию. Compose timeout должен превышать фактический внутренний дедлайн минимум на 5с; helper проверяет это. Большой compose timeout **не увеличивает** 8000мс внутри процесса. App exit0/143 без OOM допускается; workers только exit0. Exit1/137/OOM, workers143, ошибки shutdown/drain или недоступные журналы блокируют START. Не обходить отказ обычным `docker compose up`.
5. При отказе helper восстанавливает прежнее поколение; проверить RECOVERED, фактические образы/политики/реплики и сохранить диагностику. OUTAGE требует ручной проверки. Не удалять lease/не делать FLUSHALL; TTL30s не заменяет завершение старого процесса.
6. В этом проекте app/workers не имеют env_file. Если владелец меняет shutdown deadline для будущих остановок, переменную надо добавить в workers `environment:` (например `WORKER_SHUTDOWN_TIMEOUT_MS=${WORKER_SHUTDOWN_TIMEOUT_MS:-8000}`), и согласовать compose grace/timeout. Для текущих старых контейнеров поздно установленная переменная не действует. Compose в этом потоке не изменён.

## 4. Проверки после переключения

Выполнять отдельно, записать время/exit/ожидаемый SHA:

```bash
docker compose ps app workers
node scripts/prod-smoke.mjs --url https://orionpiling.ru --sha "$SHA"
curl --fail --silent --show-error https://orionpiling.ru/api/health/deep
```

Требуется совпадение APP_VERSION в health, app/workers healthy, database/redis `ok`, schedulers `ok` без stale, storage `ok` (degraded требует отдельной проверки функции хранения). Не принимать один HTTP 200: deep-health допускает degraded. Прочитать ограниченный участок журналов app/workers со времени переключения: нет MODULE_NOT_FOUND, ошибок outbox/projection/PDF/shutdown. Не печатать полное окружение или секреты.

Если были миграции — отдельно проверить migrate logs и `_prisma_migrations`: новая запись finished_at без rolled_back_at; именно ожидаемая миграция, а не «No pending». В этом диапазоне миграций не добавлялось.

**Один лидер на ресурс.** В state Redis проверить `pilingtrack:leader:outbox-worker` и `pilingtrack:leader:projection-worker`, owner и PTTL. Для Redis CLI пароль берётся внутри контейнера из существующего окружения, не из аргумента `-a`:

```bash
docker compose exec -T redis sh -lc 'export REDISCLI_AUTH="$REDIS_PASSWORD"; redis-cli GET pilingtrack:leader:outbox-worker; redis-cli PTTL pilingtrack:leader:outbox-worker; redis-cli GET pilingtrack:leader:projection-worker; redis-cli PTTL pilingtrack:leader:projection-worker'
```

Сопоставить полный owner (os.hostname/PID/UUID) с nodeId в workers health/логах и workers `/health` (`leader`) / логами embedded app. Повторить через интервалы renewal (10с); все исполнители должны использовать один state Redis. В старом cache Redis прежние ключи должны истечь; не удалять их принудительно. Redis GET сам по себе не доказывает отсутствие старого лидера в другом инстансе: доказательство — полный stop-барьер, отсутствие старых процессов и сопоставление всех исполнителей. Проверить controlled takeover standby на стенде; на production — только по отдельному согласованному шагу, не убивать процессы внезапно. Lease не DB fencing, поэтому проверка завершения in-flight операций обязательна.

**Outbox/проекции.** Зафиксировать unpublished/unprojected/attempts≥3/DLQ по ранбуку 008. При обычной работе backlog уменьшается; новые постоянные ошибки — отказ релиза. Для безопасного тестового объекта проверить: черновик не увеличивает производственные KPI, отправка увеличивает, rebuild не меняет итог. История и статус черновика остаются доступны.

**Telegram и алерты.** В административном интерфейсе отправить согласованное тестовое уведомление, подтвердить получение в каждом включённом чате. Проверить тестовый Alertmanager firing/resolved и его успешную доставку, настройки webhook/systemAlerts, счётчики попыток/ошибок уведомлений; секреты не выводить. При частичном отказе webhook возвращает 503, OutboxEvent сохраняет telegramDeliveredChatIds, повтор не пишет в уже подтверждённый чат. Published=true требует доставки в рабочие чаты: постоянный401/403/известный chat400 отключает сломанный канал с причиной в настройках; timeout/429/5xx остаются retry. Повтор после DLQ создаёт новую попытку, сохраняя прежнюю историю. Никаких искусственных аварийных рабочих происшествий/дефектов. Настройка бота и настройки алертов должны быть разрешены владельцем; заглушка fetch из D2 не является production доказательством доставки.

## 5. Очистка временных PDF: сначала dry-run

По умолчанию выключена. Только после принятия релиза и проверки правильного storage-бэкенда владелец добавляет в **workers.environment:**

```yaml
      - PDF_TEMP_CLEANUP_ENABLED=${PDF_TEMP_CLEANUP_ENABLED:-false}
      - PDF_TEMP_CLEANUP_DRY_RUN=${PDF_TEMP_CLEANUP_DRY_RUN:-true}
```

Одного значения в хостовом .env недостаточно: app/workers не имеют env_file. Этот scheduler живёт в unified workers; в app эти флаги для данной функции не нужны. Флаги/compose этим потоком не включались/не менялись. Локальные storage/pdf-results контейнера не общие с app; если PDF хранится локально, проверить доступ worker к тому самому каталогу. Для production с S3 проверить используемые endpoint/bucket без публикации реквизитов.

1. Владелец задаёт ENABLED=true, DRY_RUN=true и заменяет app/workers тем же барьером D1. После старта первая проверка через 60с, дальше раз в сутки.
2. Прочитать `Temporary PDF cleanup plan`: backend, dryRun=true, retentionDays=30, count, keys. `Temporary PDF cleanup complete`: deleted=0. Сверить несколько кандидатов вручную. Разрешены только UUIDv4 `.pdf` в `pdf-results/`, строго старше 30 дней; в local режиме дополнительно сигнатура %PDF-, обычный файл, без links. Media-фото и вложения другого префикса не кандидаты. Старые не-UUID названия намеренно не очищаются.
3. Только после просмотра плана владелец отдельно разрешает DRY_RUN=false (ENABLED=true) и повторяет безопасную смену поколения. Перед удалением снова пишется план; type/mtime/age повторно проверяются. В S3 проверяется MIME/LastModified.
4. Отключение: ENABLED=false, снова применить безопасную смену поколения. Удалённые временные результаты не восстанавливаются откатом образа; сохранность фото/вложений подтверждается отдельно. Массовую очистку иных файлов или Media этим механизмом не выполнять.

## 6. Откат

Не повторять rolling-up. Сохранить диагностику и остановить все внешние новые исполнители/их автозапуск. Сверить наличие обоих откатных тегов и source/compose предыдущей версии; в проверенном диапазоне схема не менялась. Если релиз включает более позднюю миграцию, заранее проверить совместимость старого кода — не откатывать DB вслепую.

После ручного подтверждения внешнего барьера на сервере оператор переключает теги и вызывает **тот же** barrier helper (сохранить доступную копию helper перед возвратом git к старому SHA, где его ещё нет):

```bash
docker tag "pilingtrack-app:$ROLLBACK" pilingtrack-app:latest
docker tag "pilingtrack-workers:$ROLLBACK" pilingtrack-workers:latest
WORKER_GENERATION_EXTERNAL_STOPPED=1 bash scripts/replace-worker-generation.sh app workers
```

Порядок снова STOP→VERIFY→START; при сомнении остановиться. Затем повторить health/deep-health/версию, одного лидера, outbox и Telegram. Старое поколение может хранить lease в cache Redis — барьер обязателен и при откате. Compose/worktree должны соответствовать откатному коду/настройкам, образы именно сохранённому тегу; не пересобирать случайную ветку и не удалять тома. Helper автоматически возвращает прежнее поколение при отказе переключения; ручной откат принятого релиза остаётся отдельной процедурой. Документ не является журналом production-выполнения.
## Уточнение барьера после релиза 03.10 (E0a/F1)

Next standalone app штатно завершается по SIGTERM с exit 143; helper принимает его только для service=app при exited и OOM=false. Для workers по-прежнему требуется exit 0; killed/OOM/ошибки drain запрещают новое поколение. Встроенные workers app также проверяются по журналам shutdown.

При отказе после STOP helper автоматически возвращает прежние контейнеры и restart-политики; если force-recreate удалил ID — запускает сохранённые immutable imageIDs с прежним числом реплик и restart, используя текущий compose. Перед возвратом частично поднятое новое поколение останавливается и проверяется отсутствие RUNNING. Exit остаётся1: RECOVERED означает восстановление старой версии, не успешную выкладку. Если Docker/остановка/возврат недоступны — OUTAGE и ручная проверка; только после проверки безопасна аварийная команда `cd /opt/pilingtrack && docker compose up -d app workers`. Автовозврат не откатывает миграции/env/volumes/topology. Обычным up барьер не обходить.
