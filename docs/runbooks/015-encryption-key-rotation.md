# Runbook 015 — ротация `ENCRYPTION_KEY` без потери расшифровки

**Зачем.** Ключ шифрования полей в базе меняется редко, поэтому процедура нигде
в `docs/runbooks/` не была заведена. При этом у неё есть неочевидная ловушка
развёртывания: строка в `.env` **сама по себе до контейнера не доезжает**, и
ротация, выполненная «как кажется правильным», молча не срабатывает, а оператор
считает её сделанной. Этот ранбук закрывает находку №4 отчёта
`docs/audits/hermes-night/R92-env-passthrough.md` и добавляет слой «контейнер»
поверх канонической инструкции `docs/encryption-key-rotation.md`.

**Что важно понимать перед чтением.**

1. **Значения ключей в документе не приводятся и не ищутся.** Ниже — только
   имена переменных и порядок действий.
2. **Правка `docker-compose.yml` (проброс в `environment:`) — задача надзора, а
   не этого ранбука.** Здесь она описана как обязательный шаг: без неё ротация
   не работает. Сам файл compose и код не менялись.
3. **Перезапуск обязателен.** Ключи читаются один раз при старте процесса и
   кэшируются (`src/core/security/encryption.ts:43,60-61`, `cachedRegistry`;
   сброс кэша доступен только тестовому шву `__resetEncryptionKeyCacheForTests`).
   Пока контейнер не пересоздан, новые переменные в нём не видны.

---

## 1. Что читает `src/core/security/encryption.ts`

Только имена (файл `src/core/security/encryption.ts`, `loadKeyRegistry`):

| Имя | Роль | Где читается |
|---|---|---|
| `ENCRYPTION_KEY` | «легаси»-ключ без версии; даёт шифротекст вида `enc:<base64>` | `encryption.ts:74-76` |
| `ENCRYPTION_KEY_VERSION` | метка **активной** версии для новых записей (`v1`, `v2`, …) | `encryption.ts:79` |
| `ENCRYPTION_KEY_V1` … `ENCRYPTION_KEY_Vn` | ключи прошлых версий; перебираются из окружения по regex `^ENCRYPTION_KEY_V(\d+)$` | `encryption.ts:66-71` |

Как выбирается активная версия (`encryption.ts:79-105`):

- если задан `ENCRYPTION_KEY_VERSION` — берётся он; если такого
  `ENCRYPTION_KEY_<VERSION>` нет, процесс **падает на старте** с ошибкой
  (`encryption.ts:80-84`);
- если не задан — берётся **старшая** из определённых `ENCRYPTION_KEY_Vn`, иначе
  `ENCRYPTION_KEY` (легаси);
- если не задано вообще ничего, в `production` — **throw** (`encryption.ts:93-98`).

Формат шифротекста (автоопределяется при чтении, `encryption.ts:11-14,155-173`):

```
enc:<base64>        — легаси-ключом ENCRYPTION_KEY
enc:v1:<base64>     — ключом ENCRYPTION_KEY_V1
enc:v2:<base64>     — ключом ENCRYPTION_KEY_V2 (и так далее)
```

## 2. Ловушка: у `app` и `workers` НЕТ `env_file`

В `docker-compose.yml` (и в `docker-compose.prod.yml`) **не объявлен `env_file`**
ни у сервиса `app`, ни у сервиса `workers` — только блоки `environment:`
(`docker-compose.yml:71-123` для `app`, `:158-194` для `workers`). `.env` в
образ не попадает: `.dockerignore` исключает `.env*`, поэтому и
`import 'dotenv/config'` внутри воркера — пустышка (`src/workers/unified-worker.ts:17`).
Следствие: **в контейнер доходит только то, что перечислено в `environment:`**.

На 02.10.2026 в блоках `environment:` обоих сервисов есть только
`ENCRYPTION_KEY` (`docker-compose.yml:84` у `app`, `:185` у `workers`).
`ENCRYPTION_KEY_VERSION` и `ENCRYPTION_KEY_V1..Vn` **не проброшены ни в один
сервис** (находка №4 R92). Это значит:

- значение, добавленное только в `.env`, активным **не станет** — им останется
  легаси-ключ `ENCRYPTION_KEY`, а новые секреты продолжат шифроваться старым
  ключом;
- удаление старого ключа из `.env` при этом сломает чтение старых данных
  (`encryption.ts:114-119` бросает), и оператор узнает об этом только по тихо
  пропавшим уведомлениям.

**Проброс делается в репозитории** (файл `docker-compose.yml`), надзором, не
этим ранбуком: иначе следующая выкладка перезапишет файл и проброс исчезнет.

Нужны строки (значения берутся из `.env`):

```yaml
# в блок environment: сервиса app И сервиса workers
- ENCRYPTION_KEY_VERSION=${ENCRYPTION_KEY_VERSION:-}
# версионные ключи — перечислять явно (compose не умеет «все ENCRYPTION_KEY_V*»):
- ENCRYPTION_KEY_V1=${ENCRYPTION_KEY_V1:-}
- ENCRYPTION_KEY_V2=${ENCRYPTION_KEY_V2:-}
```

То же по смыслу описано в `docker-compose.yml:104-107` (комментарий про
`DB_IDENTITY_ROLE`) и в ранбуке 014 (шаг 4): **строка в `.env` без проброса до
контейнера не доезжает**.

## 3. Что именно шифруется (проверено `grep encrypt(` по `src/`)

Сегодня в базе зашифровано **единственное поле** — `TelegramConfig.botToken`:

| Точка | Что делает | Файл |
|---|---|---|
| запись при создании/правке бота | `encrypt(...)` | `src/services/telegram/telegram-config-service.ts:83,122` |
| отправитель уведомлений (читает и расшифровывает сам) | `decrypt(...)` | `src/core/notifications/telegram.ts:69,82-83` |
| страница настроек (берёт только хвост токена) | `decrypt(...)`, ошибку глотает | `src/services/telegram/telegram-config-service.ts:49-55` |
| клиентский разбор токена при отладке | `decrypt(...)` | `scripts/tg-debug.ts:3` |

Заголовок `encryption.ts:4-7` упоминает «API keys / OAuth secrets» как будущие
поля — **их в коде пока нет**, отдельных колонок не заведено. Добавление нового
зашифрованного поля описано в `docs/encryption-key-rotation.md` (раздел
«Adding a new encrypted column») и требует такой же правки sweep-скрипта.

Важно про **воркеры**: обработчик события сдачи наряда, который расшифровывает
токен, выполняется **внутри контейнера `workers`** (outbox), а не только в `app`
(комментарий `docker-compose.yml:179-184`). Поэтому проброс версионных
переменных нужен **в оба сервиса**.

## 4. Порядок ротации (без потери расшифровки)

Ротация — это не «заменить `ENCRYPTION_KEY`», а «ввести новый ключ рядом, затем
перешифровать и только потом убрать старый». Ниже — полный порядок; он совпадает
с `docs/encryption-key-rotation.md`, но с учётом контейнерной ловушки из §2.

**Шаг 0. Снять копию.** Убедиться, что текущее значение `ENCRYPTION_KEY` лежит в
менеджере паролей владельца (иначе зашифрованные поля не восстановить; см.
`docs/runbooks/010-restore-drill.md:189`). Значения вслух/в документ не
переносить.

**Шаг 1. Сгенерировать новый ключ** (32 байта hex):

```bash
openssl rand -hex 32      # НЕ печатать и не переносить в переписку
```

**Шаг 2. Прописать оба ключа и активную версию в `.env`** (значения вписывает
владелец):

```
ENCRYPTION_KEY_V1=<текущее значение ENCRYPTION_KEY>   # старый ключ сохраняем
ENCRYPTION_KEY_V2=<новый ключ из шага 1>
ENCRYPTION_KEY_VERSION=v2                             # новые записи — под V2
```

Строку `ENCRYPTION_KEY=` пока не удалять (совместимость чтения легаси-данных).

**Шаг 3. Пробросить эти имена в `environment:`** обоих сервисов `app` и
`workers` — **правка `docker-compose.yml`, делает надзор** (§2). Без этого шага
шаги 2 и 4 ничего не дадут.

**Шаг 4. Пересоздать контейнеры**, чтобы переменные доехали:

```bash
docker compose up -d --no-build app workers
```

**Шаг 5. Проверить, что имена доехали** (только имена, без значений):

```bash
docker compose exec -T app     sh -c 'env | grep -c "^ENCRYPTION_KEY_VERSION="'
docker compose exec -T workers sh -c 'env | grep -c "^ENCRYPTION_KEY_VERSION="'
# ожидаем 1 у обоих; 0 = проброс не доехал (шаги 3-4 не выполнены)
```

**Шаг 6. Перешифровать существующие записи** на активную версию (V2). Скрипт
идемпотентен, печатает только счётчики, а не значения
(`scripts/rotate-encryption-key.ts`):

```bash
npx tsx scripts/rotate-encryption-key.ts
# ожидаем в начале: "Active encryption key version: v2"
# и "TelegramConfig: rotated <N>, skipped <M>" — N строк переведены в enc:v2:
```

**Шаг 7. Проверка после ротации** — до того, как убирать старый ключ.

**Только после** успешного шага 7 и убедительности, что легаси-шифротекстов не
осталось:

**Шаг 8. Убрать старый ключ** — удалить из `.env` строки `ENCRYPTION_KEY=` и
`ENCRYPTION_KEY_V1=` (оставить только `ENCRYPTION_KEY_V2` и
`ENCRYPTION_KEY_VERSION=v2`), пересоздать `app` и `workers`. С этого момента
расшифровать `enc:` и `enc:v1:` строки будет уже нечем — поэтому шаг 7
обязателен. В репозитории соответствующим образом нужно будет **сузить проброс**
(убрать `ENCRYPTION_KEY_V1`, если он больше не нужен) — тоже правка надзора.

## 5. Проверка после (read-only)

Все команды — только чтение; секреты не печатаем.

```bash
# 1. Активная версия в работающем приложении (скрипт печатает метку, не ключ)
npx tsx scripts/rotate-encryption-key.ts
# ожидаем "Active encryption key version: v2" (не "legacy")

# 2. Что шифротекст новых записей помечен v2 — по префиксу колонки, без значения
#    (выполнять на копии/стенде; на бой база не трогается)
#    Пример: SELECT substring("botToken" from 1 for 8) FROM "TelegramConfig";
#    ожидаем префиксы enc:v2: для записей, переписанных sweep-скриптом

# 3. Живой путь расшифровки — отправитель уведомлений.
#    Страница настроек Telegram показывает хвост токена (••••1234) и «токен
#    задан»; пусто = расшифровка не удалась
#    (src/services/telegram/telegram-config-service.ts:46-56).

# 4. В логах не должно быть ошибки отсутствующего ключа
docker compose logs --tail 50 workers | grep -i 'encryption key'
# ожидаем пусто; строка "No encryption key configured"/"key for version ... not
# configured" = ключ версии не доехал или убран преждевременно
```

Признаки **неудачной** ротации (симптомы, а не причина):

- активной осталась `legacy` — не выполнен шаг 3 (проброс) или шаг 4 (перезапуск);
- страница настроек Telegram показывает «без токена», уведомления не уходят —
  старый ключ убран, а легаси-строки ещё не перешифрованы (`:114-119` бросает,
  а `telegram-config-service.ts:52-54` ошибку глотает);
- в логах воркера `Failed to load Telegram config: ... encryption key ...` —
  та же причина на стороне обработчика outbox.
