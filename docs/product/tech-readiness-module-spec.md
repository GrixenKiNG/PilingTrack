## 1. Назначение

Модуль отвечает на один вопрос перед началом смены: **можно ли пускать эту
установку в работу, и если нет — кто и что должен сделать**.

Раньше ответ жил в голове диспетчера. Теперь он вычисляется из фактов
(осмотр, моточасы, наряд-допуск, регламент ТО, допуск диспетчера), фиксируется
неизменяемым снимком и подписывается в хеш-цепочке аудита. Решение
воспроизводимо: по любому снимку видно, какие правила действовали, какие факты
были на входе и какой балл получился.

**Точка входа:** `/admin/to` → [`src/app/(app)/(readiness-admin)/admin/to/page.tsx`](../../src/app/(app)/(readiness-admin)/admin/to/page.tsx)

**Границы.** Модуль не ведёт склад запчастей, не считает стоимость владения, не
управляет закупками и не заменяет производственный отчёт по сваям — это
соседний модуль «Отчёты».

**Режим «Действую как».** У ОРИОНа нет живых механика, мастера и инженера ОТ —
их работу выполняет администратор. Роль выбирается **явно** в шапке модуля
([`acting-role-switch.tsx`](../../src/components/piling/to/readiness/acting-role-switch.tsx)),
права складываются с собственными, а факт замещения пишется в `AuditLog`
отдельной записью с указанием исполняемой роли. Замещать может только `ADMIN`;
то же правило продублировано на сервере, поэтому обойти его через API нельзя.

Когда у ролей появятся живые люди, переключатель ничего не сломает — права
придут из их собственных учётных записей.

**Видимость вкладок** считается на сервере в `bootstrap` и приходит клиенту
готовым словарём `capabilities.screens`. Недоступные вкладки не отображаются
вовсе — раньше оператор видел все семь, а «Отчёты» отвечали ему «Недостаточно
прав».

## 3. Расчёт готовности

Ядро модуля. Чистые функции без обращений к базе:
[`readiness-score.ts`](../../src/modules/readiness/domain/readiness-score.ts),
[`readiness-rules.ts`](../../src/modules/readiness/domain/readiness-rules.ts).

### 3.1 Факты на входе

| Факт | Откуда берётся |
|---|---|
| `inspectionCompleted` | последний завершённый осмотр приходится на **производственную дату тенанта** |
| `inspectionProgress` | `1` — осмотр сегодня, `0.5` — осмотр есть, но не сегодня, `0` — осмотра нет |
| `healthScore` | балл здоровья из осмотра (0–100) |
| `meterKnown` | у установки заполнены моточасы |
| `permitValid` / `permitExpired` | действующий наряд-допуск на эту установку и смену |
| `maintenanceConfigured` | задан регламент: моточасы или дата следующего ТО |
| `maintenanceOverdueHours` / `Days` | перепробег и просрочка |
| `accepted` | смену **допустил** диспетчер (`startedById` заполнен) |
| `criticalDefect` | открытый критический дефект **или** незакрытый наряд ремонта с приоритетом CRITICAL |
| `findings` | производная от `healthScore` |

`inspectionProgress` — это флаг свежести, **а не доля выполненных пунктов**.
Долю пунктов чек-листа экран берёт отдельно, из `latestInspection`
(`itemsAnswered` / `itemsTotal`).

### 3.2 Критерии и веса

Веса настраиваются тенантом, сумма всегда нормализуется до 100.

| Критерий | Вес по умолчанию | Как считается доля |
|---|--:|---|
| Осмотр | 30 | `progress × health`, и ×0.5 если осмотр не завершён |
| Моточасы | 15 | 1 или 0 |
| Наряд-допуск | 25 | действует 1 · на согласовании 0.4 · просрочен 0 · не требуется 1 |
| Обслуживание | 20 | перепробег: `1 − ч/100`; просрочка: `1 − дн/30` |
| Приёмка диспетчером | 10 | 1 или 0 |

Балл — сумма `вес × доля`, ограниченная 0…100. Порог «зелёного» — **85**.

### 3.3 Блокирующие правила

| Условие | Действие по умолчанию | Включено |
|---|---|:-:|
| `CRITICAL_DEFECT` | Запретить запуск | ✅ |
| `PERMIT_EXPIRED` | Запретить запуск | ✅ |
| `MAINTENANCE_OVERDUE_50H` | Предупредить, не останавливать | ✅ |
| `VALID_WORK_PERMIT_REQUIRED` | Запретить запуск | ❌ |
| `INSPECTION_BELOW_80` | Вернуть оператору | ❌ |

Действия ранжированы: `ALLOWED` → `CONFIRMATION_REQUIRED` →
`RETURN_TO_OPERATOR` → `DENIED`. Итоговый вердикт — худшее из сработавших.
`WARN_ONLY` попадает в замечания и вердикт не ухудшает — это отдельная ветка,
иначе интерфейс считал бы предупреждение блокировкой.

**Если опубликованных правил нет — запуск запрещён**, с блокером
`READINESS_RULES_NOT_PUBLISHED`. Отказ по умолчанию, а не разрешение.

### 3.4 Два расчёта, и почему их два

| | Авторитетный | Клиентский предпросмотр |
|---|---|---|
| Файл | [`application/readiness-score.ts`](../../src/modules/readiness/application/readiness-score.ts) | [`application/readiness-facts.ts`](../../src/modules/readiness/application/readiness-facts.ts) |
| Где | сервер, внутри транзакции с tenant-контекстом | браузер, по загруженному журналу |
| Результат | снимок в БД, юридически значим | подсказка «что будет, если нажать» |
| Часы | захваченные (`capturedClock`) | текущие |

Решения принимает только авторитетный. Клиентский существует, чтобы экран не
ждал сервер ради подсветки. **Оба обязаны сходиться**; расхождение — баг, и
именно на этой границе в августе всплывали неверные счётчики.

## 4. Машины состояний

### Смена (`Shift`)

```
PLANNED ──request──> PENDING_ACCEPTANCE ──start──> STARTED ──handover──> HANDOVER_PENDING ──accept──> CLOSED
   ^                        │                                                    │
   └────────decline─────────┘                                                    └──rework──> STARTED
   
отмена: PLANNED | PENDING_ACCEPTANCE | STARTED ──cancel──> CANCELLED
```

Прямой запуск из `PLANNED` **убран намеренно** — иначе допуск диспетчера
обходится. Оператор просит допуск, пускает диспетчер.

### Передача смены (`ShiftHandover`)

```
DRAFT ──submit──> SUBMITTED ──accept──> ACCEPTED
                      └──rework──> REWORK_REQUIRED ──submit──> SUBMITTED
```

### Наряд-допуск (`WorkPermit`)

```
DRAFT ──submit──> PENDING_APPROVAL ──approve*──> APPROVED ──revoke──> REVOKED
                                                     └──expire──> EXPIRED
правка из любого из трёх состояний возвращает наряд в DRAFT и обнуляет подписи
```

**Правило «второго глаза»** ([`approval-policy.ts`](../../src/modules/readiness/domain/permits/approval-policy.ts)):

- `NORMAL` — достаточно подписи диспетчера; автор подписать может.
- `ELEVATED` — нужны подписи диспетчера **и** администратора, обязательно
  разных людей, и автор наряда подписать не может.

Действующими считаются только подписи с `valid = true` и `permitVersion`,
равным текущей версии наряда. Правка наряда обесценивает все прежние подписи —
поэтому в журнале согласования они показаны отдельно, без галочки.

### Дефект (`EquipmentDefect`)

`OPEN → IN_WORK → CLOSED`, ветка `REJECTED` для неподтвердившихся и дублей.
Критический дефект в статусе `OPEN` или `IN_WORK` блокирует запуск.

### Наряд ТО (`MaintenanceRecord`)

`PLANNED → ASSIGNED → IN_PROGRESS → DONE`, плюс `ON_HOLD` и `CANCELLED`.
Открытыми для расчёта готовности считаются первые четыре.

## 5. Экраны

Семь вкладок, [`module-tab-list.tsx`](../../src/components/piling/to/readiness/module-tab-list.tsx).

### 5.1 Центр готовности

Эталонный экран, по нему выровнены остальные. Три колонки:

- **слева** — выбор установки, статус, балл, метрики парка;
- **центр** — цепочка состояния из пяти шагов (осмотр → моточасы → наряд →
  ТО → приёмка), чек-лист смены, следующее действие с указанием **кто его
  держит**;
- **справа** — доказательства готовности (ссылки на первоисточники), журнал
  передач, входящие у диспетчера.

Правило заливки, действующее на всех экранах: **цветом залито только
выполненное**. Текущий шаг обведён, будущие — серый контур.

Нижний блок показывает по каждой роли реальный прогресс её шагов, а не
фиксированную заглушку.

### 5.2 Техника

Парк установок карточками: статус готовности, балл, блокеры, ближайшее ТО,
перепробег. Переход в карточку установки и в журнал ТО.

### 5.3 Смены

Реестр смен с фильтрами, график занятости с живой отметкой «сейчас»
(пересчитывается каждые 60 с из часового пояса тенанта). Действия по правам:
запросить допуск, допустить, отказать, отменить, передать.

### 5.4 Наряд-допуски

Реестр, панель «ожидают согласования» с согласованием прямо в карточке,
журнал согласования из фактических подписей, полоса условий допуска с
разбивкой по долям.

### 5.5 Обслуживание

Сервисный план по остатку до ТО с полосой пробега, загрузка механиков по
**фактическому** исполнителю, расход запчастей из заявок, доказательства
выполнения по реальным полям записи.

### 5.6 Отчёты

Парето причин блокировки по фактам снимков, KPI запущенных смен и готовых
установок, экспорт CSV.

### 5.7 Настройки — 7 разделов

Правила готовности · Чек-листы · Роли и доступы · Справочники · Уведомления ·
Интеграции · Аудит.

Что стоит знать про эти разделы:

- **Правила готовности** — веса, блокеры, черновик/публикация и предпросмотр
  расчёта на выбранной установке. Сводная матрица доступов считается из
  `resolveReadinessCapabilities`, как и полная в «Ролях».
- **Чек-листы** — шаблоны только для чтения плюс предпросмотр пункта глазами
  оператора теми же контролами, что стоят в окне осмотра. Редактор живёт в
  `/admin/checklists`.
- **Роли и доступы** — матрица полномочий из кода и настоящий контур доступа по
  объектам (`UserSiteAssignment`). Пустой список назначений у роли без
  `sites.read_all` — это ни одной площадки, и раздел это подсвечивает.
- **Уведомления** — переключатели сохраняются, но отправка их **не проверяет**;
  из четырёх правил отправитель есть у двух. Экран говорит об этом прямо.
- **Аудит** — лента с фильтрами, детали события и проверка целостности цепочки.
  Политики хранения нет: записи не удаляются.

## 6. Архитектура

Модуль следует DDD/CQRS-раскладке проекта. Домен не знает ни про Prisma, ни
про HTTP.

```
src/modules/readiness/          62 файла, 4 815 строк + 16 тестовых
├── domain/                     чистые правила: оценка, переходы, политика подписей, аудит-хеши
├── application/                сценарии: команды, запросы, конвейер, проекции
└── infrastructure/             репозитории, транзакции с tenant-контекстом

src/modules/equipment/          18 файлов, 1 286 строк — парк, ТО, моточасы, документы
src/modules/inspections/         9 файлов,   928 строк — чек-листы и осмотры
src/components/piling/to/       33 файла,  8 638 строк — интерфейс
src/app/api/readiness*/         27 маршрутов
```

### 6.1 Командный конвейер

Каждая мутация проходит один и тот же путь
([`command-pipeline/`](../../src/modules/readiness/application/command-pipeline/)):

1. **Контекст запроса** — актор, тенант, `correlationId`, `requestId`.
2. **Идемпотентность** — клиент присылает ключ; `tryClaim` захватывает его
   строкой в `IdempotencyKey`. Повтор с тем же телом отдаёт сохранённый ответ
   с пометкой `replayed`; повтор с **другим** телом → `409
   IDEMPOTENCY_KEY_REUSED`. Блокировка строки (`55P03`/`P2010`) → «команда уже
   выполняется». Срок жизни ключа — 7 суток.
3. **Оптимистичная блокировка** — сильный `ETag` вида `"shift-<id>-v3"`.
   Требуется `If-Match` либо `expectedVersion` в теле; если пришли оба и
   расходятся — отказ. Weak ETag и список значений не принимаются.
   Несовпадение версии → `409` с русским текстом «Запись изменилась».
4. **Переход состояния** — проверка по таблице разрешённых переходов, отказ
   тоже по-русски: «Смена передана диспетчеру — действие «принять» сейчас
   недоступно».
5. **Запись + событие** — изменение и событие `ReadinessSnapshotRequested`
   пишутся **в одной транзакции** (transactional outbox).
6. **Аудит** — звено хеш-цепочки.

### 6.2 Снимки и проекции

```
команда ──tx──> запись + OutboxEvent(ReadinessSnapshotRequested)
                                │
                        воркер проекций
                                │
              evaluateAuthoritativeReadiness (транзакция с tenant-контекстом)
                                │
        ReadinessScoreSnapshot (неизменяемый) ──> CurrentReadiness (последний)
```

- **`ReadinessScoreSnapshot`** — неизменяемая история. Хранит факты, правила,
  версию правил, блокеры, доказательства и `factsHash`. Уникален по
  `(tenant, equipment, triggerType, triggerId)` — повторная доставка события
  не плодит дублей.
- **`CurrentReadiness`** — последнее состояние, продвигается только вперёд по
  `calculatedAt`.
- **Часы захвачены**: расчёт использует время события, а не время обработки.
  Иначе снимок, обработанный воркером через час, врал бы о «сегодняшнем»
  осмотре.
- Событие помечается `projected` внутри той же транзакции — двойная обработка
  безопасна.

Триггеры снимков: осмотр, дефект, наряд-допуск, команды смены и отдельно
решение о запуске (`SHIFT_START_DECISION`, снимок привязывается к смене через
`startSnapshotId`).

### 6.3 Хеш-цепочка аудита

[`domain/audit/`](../../src/modules/readiness/domain/audit/) +
[`infrastructure/audit/`](../../src/modules/readiness/infrastructure/audit/).

Каждое звено:

```
hash = SHA256( "PILINGTRACK-AUDIT-V1" ⏎ tenantId ⏎ sequence ⏎ prevHash ⏎ canonical(event) )
```

Событие канонизируется перед хешированием (стабильный порядок ключей).
Персональные данные маскируются **до** расчёта хеша. Голова цепочки
блокируется на время вставки, `sequence` монотонен в пределах тенанта.
Ключ идемпотентности в журнал попадает только хешем. Проверка целостности —
`verify-chain.ts`, ограничение БД `AuditLog_native_chain_complete` требует
метаданных у каждого звена.

### 6.4 Изоляция тенантов

- Все запросы модуля идут через `withReadinessWorkerTransaction` /
  `tenant-transaction.ts`, который устанавливает tenant-контекст транзакции.
  На таблицах включён FORCE RLS (с 03.07.2026).
- Составные ключи `@@unique([tenantId, id])` и внешние ключи по паре
  `(tenantId, id)` — сослаться на чужую строку нельзя даже при ошибке в коде.
- Запрос без `tenantId` **падает**, а не расширяется до всех тенантов. Паттерн
  `IS NULL OR tenantId` в проекте запрещён: он однажды уже вернул чужие строки.

### 6.5 Часовой пояс

Производственная дата считается в поясе тенанта
(`TenantSettings.timezone`, по умолчанию `Europe/Moscow`), а не в UTC и не в
поясе браузера. Ночная смена, начатая в 23:40, принадлежит своей
производственной дате, а осмотр в 00:10 — уже следующей.

### 6.6 Флаги функциональности

`READINESS_SHIFTS_V1`, `READINESS_PERMITS_V1`, `READINESS_AUDIT_CHAIN_V1` —
все **включены по умолчанию**, выключаются явным `false`. Флаг участвует в
расчёте видимости вкладок.

Отдельно: `NEXT_PUBLIC_TECH_READINESS_PRODUCTION_SHELL` переключает
производственную оболочку модуля.

## 7. API

27 маршрутов под `/api/readiness*`. Мутации обёрнуты
`withReadinessCommand` (поверх `withMutation`: CSRF + rate-limit + разбор
ошибок домена в HTTP-ответ), чтения — `withApi`.

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/readiness/bootstrap` | права, справочники, часовой пояс, флаги |

**Коды ошибок:** `409` — конфликт версии либо повторный ключ; `422` —
недопустимый переход или нарушение доменного правила; `428` — не передано
условие конкурентности; `403` — нехватка прав. Тексты — на русском, потому что
их читает оператор, а не разработчик.

BOM для Excel, разделитель `;`, шапка с часовым поясом, фильтрами и
`data_sha256`, экранирование формул (`=`, `+`, `-`, `@` получают апостроф) —
защита от CSV-инъекции при открытии в Excel.

**Сборка чек-листа.** Шаблон собирается из блоков: `BASE` по марке установки,
`HAMMER` по типу молота (`HYDRAULIC` / `DIESEL` / `NONE`), `ROTARY` для
комбинированных (`isCombined`). Уровни: `EO`, `TO1`, `TO2`, `TO3`, `SEASONAL`.
Типы ответов: `YES_NO`, `STATUS4`, `DONE`, `MEASURE`. В осмотре хранится
`templateSnapshot` — слепок шаблона на момент проведения, поэтому правка
шаблона не переписывает историю.

**Моточасы.** Источник истины — история `MeterReading`;
`Equipment.engineHoursTotal` остаётся денормализованным кэшем последнего
показания. Поле `source` (`MANUAL` / `TELEMETRY`) позволит подключить телеметрию
без изменения модели.

## 9. Тестирование

29 тестовых файлов в трёх модулях. Покрыто в первую очередь то, где ошибка
дорого стоит:

- домен готовности — веса, нормализация, вердикты, отказ без правил;
- переходы смены, передачи и наряда;
- политика подписей, включая «второй глаз» и обесценивание при правке;
- конвейер идемпотентности и ETag;
- целостность хеш-цепочки (append → verify);
- tenant-транзакции;
- контракты API и граничные состояния экранов.

По решению владельца новые тестовые файлы не плодим — только существенные
защиты, прежде всего на разрушающих и авторизационных операциях.

## 10. Расхождения с исходным PRD

| Пункт PRD | Как в коде и почему |
|---|---|
| `MAINTENANCE_OVERDUE_50H` блокирует запуск | Понижено до `WARN_ONLY` — решение владельца 08.08.2026. Тенант может ужесточить в настройках, без правки кода |
| Наряд `NORMAL` согласует не автор | Запрет снят: в ОРИОНе наряды заводит администратор, замещая механика, и подписать было некому — контур вставал. Для `ELEVATED` запрет сохранён |
| «Приёмка» = принятая передача смены | Исправлено на **предсменный допуск** диспетчера: приёмка передачи закрывает смену, и 10 баллов начислялись после окончания работы |
| Роль механика включается автоматически | Заменено явным переключателем «Действую как» с записью исполняемой роли в аудит |

## 11. Открытые вопросы

1. **Уведомления не доведены до отправки.** `TenantSettings.notifications`
   не читает никто, кроме экранов настроек. Включить проверку в один приём
   нельзя: `newReports` по умолчанию `false`, и на проде это остановило бы PDF
   сменных отчётов. Нужно решение владельца — либо поменять умолчание, либо
   проводить признак только для простоя.
2. **«Блокер» у пункта чек-листа** — в макете есть, в модели нет.
   `ChecklistItem` не хранит ни признака блокировки, ни «создавать дефект при
   „Нет“». Это миграция схемы плюс изменение логики осмотра.
3. **Политика хранения аудита** отсутствует: журнал растёт без ограничений.
4. **Телеметрия** — модель готова (`MeterSource.TELEMETRY`, `DeviceKey`,
   `TelematicsDevice`), живых данных нет: контур активируется при подключении
   железа. Это не мёртвый код.
3. **Telegram-уведомления планировщика ТО** — единственный необязательный
   остаток дорожной карты CMMS.
4. **`scripts/backfill-close-inspection-maintenance.sql`** — не выполнен на
   проде, нужен в момент деплоя.
5. **Роли `FOREMAN` и `SAFETY_ENGINEER`** живых пользователей не имеют
   by design — исполняются администратором через замещение.
