## Решение

Ограничение подтверждено реальными PostgreSQL, Redis и HTTP: соединение остаётся в открытой транзакции во время отправки; события с одинаковым ключом занимают дополнительные соединения, ожидая advisory lock. Перенос отправки за пределы транзакции НЕ реализован. Проверки характеризуют текущую схему; сравнения с безопасной реализацией резервирования нет, поэтому условие владельца «не больше дублей» не выполнено для изменения runtime.

Текущая схема тоже не даёт exactly-once: при принятом сообщении и потерянном ответе, а также при аварии процесса до фиксации подтверждения, повторная отправка возможна. Фикстура намеренно моделирует принятие сообщения до ответа HTTP; это не утверждение о внутренней обработке реального Telegram.

## Методика измерения и точность

Каждый sample читает pg_stat_activity и наличие **granted advisory lock** в pg_locks. Транзакции группируются по (pid, xact_start), а не только PID; повторное использование соединения не склеивает разные транзакции.

- maxOpenTransactionAgeMs — clock_timestamp - xact_start: нижняя наблюдаемая граница занятости соединения транзакцией.
- maxTransactionAgeWhileHoldingMs — тот же возраст в момент владения замком; явно включает предшествующее ожидание.
- heldLowerMs — интервал между первым и последним sample с granted advisory lock.
- waitLowerMs — интервал между первым и последним sample wait_event=advisory.
- Верхние оценки добавляют два максимальных наблюдаемых шага sample для lock/wait и один для возраста соединения. Это оценки по наблюдениям, не серверные timestamps выдачи/освобождения замка и не строгие гарантированные границы при произвольной задержке наблюдателя.

Номинальная пауза 40 мс плюс SQL; максимальный фактический шаг 77 / 111 / 78 мс соответственно. SQL наблюдения выполняется отдельным owner connection, не подменяет query приложения. Все исходные sample, PID, xact_start и полученные интервалы сохранены в ignored measurements.json. Для итоговой таблицы взят максимальный нижний интервал и соответствующая оценка погрешности. Это один небольшой конкурентный прогон, не p95 и не нагрузочная граница production.

## Предлагаемая граница транзакции

1. Короткая транзакция под advisory lock (tenant, dedupeKey) проверяет подтверждённую отправку и резервирует доставку с устойчивым owner token/epoch. Для разных outbox-строк с одним ключом нужна общая каноническая запись резерва, а не независимый флаг в каждой строке. Резерв фиксируется до освобождения замка.
2. Сеть выполняется после commit. Каждое подтверждение чата сохраняется отдельной короткой транзакцией; прогресс не должен ждать окончания всей отправки.
3. После ответа новая транзакция проверяет актуальность owner/epoch, записывает receipts, sent marker и published; окончательный dedupe TTL ставится только после подтверждённого результата. Неопределённый HTTP-исход сохраняется отдельным состоянием для выбранной политики повторения.
4. Аварийные резервы восстанавливаются по явным правилам. Обычная истекающая Redis lease без устойчивого состояния не доказывает отсутствие дополнительных дублей: старый отправитель может продолжать сетевой запрос, когда новый уже забрал lease. Fencing защищает запись в БД, но Telegram не проверяет token. TTL нельзя молча приравнять к завершению старого процесса.

До реализации требуются решения о месте устойчивого резерва и восстановлении, затем сравнительная матрица текущей/новой схемы: конкурентные одинаковые и разные ключи, много чатов и partial ACK, потеря Redis, истечение lease во время отправки, аварии до/после ACK и записи receipts, остановка/возобновление старого owner. Нужное изменение схемы обсуждается отдельно с владельцем; в B схема не менялась. Простой перенос fetch из callback без резерва ослабил бы текущую сериализацию, поэтому не выполнен.

Практический следующий шаг — согласовать recovery/ownership протокол и только затем прототип сравнения. До этого стоит измерить насыщение общего пула и выбрать ограничение конкурентных доставок с запасом для чтения TelegramConfig; этот прогон из трёх процессов предел пула не измерял.
