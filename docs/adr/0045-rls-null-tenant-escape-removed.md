# ADR-0045. Убрана оговорка «пустой тенант» из политик RLS; полный fail-closed отложен

- **Статус:** принято
- **Дата:** 2026-08-17
- **Заменяет:** уточняет [ADR-0044](0044-rls-fail-closed-scope.md)

## Контекст

ADR-0044 перевёл в fail-closed шесть таблиц модуля техготовности. Остальные
остались «в режиме аудита»: политика пропускает всё, если
`app.current_tenant` не выставлен. Формулировка «режим аудита» скрывала, что
политики бывают двух разных видов.

**Вид А** (21 таблица) — течёт только при невыставленном GUC:

```sql
GUC IS NULL OR GUC = '' OR "tenantId" = GUC
```

**Вид Б** (17 таблиц) — течёт ещё и при выставленном:

```sql
GUC IS NULL OR GUC = '' OR "tenantId" IS NULL OR "tenantId" = GUC
```

Третье условие означает: строка с пустым `tenantId` видна **каждому** тенанту,
даже когда контекст задан правильно. Это тот самый шаблон `IS NULL OR
tenantId`, который CLAUDE.md запрещает после живого IDOR 31.05.2026 — только
здесь он жил не в коде запроса, а внутри самой политики.

Механизм был не теоретическим. `app.current_tenant` выставляется в
транзакциях модуля техготовности
(`readiness/infrastructure/tenant-transaction.ts`), а внутри них читаются
`Equipment`, `Site`, `User`, `AuditLog`, `MaintenanceRecord` — все вида Б.
Не сработало это лишь потому, что строк с пустым тенантом нет ни одной:
проверено по всем 17 таблицам на локальной БД и на снимке прода — 0 из 0.

## Решение

**1. Оговорка `"tenantId" IS NULL` убрана из всех 17 политик вида Б**
(миграция `20260817230000_rls_drop_null_tenant_escape`). Вид Б приведён к
виду А.

**2. Перевод остальных таблиц в fail-closed отложен** и требует отдельной
работы, а не миграции.

## Почему fail-closed нельзя включить сейчас

Универсальный помощник `withTenantContext` из
`core/security/tenant-enforcement.ts` **не вызывается ниоткуда** — только
ре-экспорт в `core/application/index.ts` и упоминание в комментарии.
Единственное место, где GUC действительно выставляется, — транзакции
техготовности.

Значит, для остальных 38 таблиц политика всегда уходит в первую ветку и RLS
не срабатывает вообще; защищает прикладной фильтр `where tenantId`. Включить
им fail-closed — значит мгновенно получить пустые выборки на всех экранах.

Чтобы это изменить, GUC должен выставляться на каждом запросе. Из-за
транзакционной области `set_config(..., true)` это означает завернуть в
транзакцию каждое чтение — при работе через pgbouncer это архитектурное
решение с ценой по производительности, а не правка политики. Отложено до
отдельного разбора.

## Последствия

- Строка с пустым тенантом больше не видна чужому тенанту на пути, где RLS
  действует (транзакции техготовности).
- Поведение на всех прочих путях не изменилось: GUC там не выставляется,
  политика уходит в ту же первую ветку, что и раньше. Регрессии нет.
- **Запись:** политика `FOR ALL` без явного `WITH CHECK` применяет то же
  условие ко вставкам, поэтому вставка строки с пустым `tenantId` при
  выставленном GUC теперь отклоняется. Все шесть вставок в `AuditLog` из
  модуля техготовности задают `tenantId` явно — проверено.
- 21 таблица вида А не тронута: у них этой оговорки и не было.

## Проверка

Проведена на роли без суперправ (под суперпользователем RLS не действует,
включая `FORCE ROW LEVEL SECURITY` — см. ADR-0044):

| Проба | Ожидание | Факт |
|---|---|---|
| GUC не выставлен, `select count(*) from "Equipment"` | режим аудита сохранён | 9 |
| `GUC='orion'` | только свой тенант | 9 |
| `GUC='stranger'` | ничего | 0 |
| вставка в `AuditLog` с `tenantId`, `GUC='orion'` | проходит | `INSERT 0 1` |
| вставка в `AuditLog` без `tenantId`, `GUC='orion'` | отклоняется | `new row violates row-level security policy` |
