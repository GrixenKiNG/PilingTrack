# ADR-0046. RLS переводится в fail-closed целиком

- **Статус:** принято
- **Дата:** 2026-08-19
- **Заменяет:** ADR-0044 («перевести только шесть таблиц техготовности»)
- **Связано:** ADR-0042 (тенантность техготовности), ADR-0045 (убрана оговорка `tenantId IS NULL`)

## Решение

Каждая таблица с колонкой `tenantId`, кроме двух очередей, закрыта строгой
политикой:

```sql
USING ("tenantId" = current_setting('app.current_tenant', true))
```

Запрос, не назвавший организацию, не видит ни одной строки и не может ни одной
записать. Раньше 37 из 43 политик начинались с `GUC IS NULL OR GUC = '' OR …` —
то есть «не назвал организацию, значит показать всё». Плюс три таблицы вовсе не
имели RLS. Итого стало 46 строгих политик и две таблицы без RLS осознанно
(разбор ниже).

## Почему не сделали этого раньше

Перевод требует, чтобы **каждый** путь запроса называл организацию. В августе
2026 это было верно только для модуля техготовности, у которого есть своя
обёртка `withReadinessTenantTransaction`. Остальное приложение ходило в базу
безымянно, и флип превратил бы защиту в отказ.

Блокеры снимались коммитами `0c336b1…cc9c9c1`. Коротко, что пришлось сделать:

| # | Что мешало | Как решено |
|---|-----------|-----------|
| 1 | Организация не доезжала до базы: её знал только запрос | Организация записана в токен сессии (`v: 2`), кладётся в контекст до чтения строки пользователя |
| 2 | Вход по паролю и ПИН-коду: организацию неоткуда взять — она в искомой строке | Отдельная узкая роль `pilingtrack_identity` с `BYPASSRLS`, переключение на одну транзакцию (`SET LOCAL ROLE`) |
| 3 | То же для ключа устройства | Та же роль |
| 4 | Пересчёт проекций шёл по всем организациям сразу | `forEachTenant` — контекст на каждую отдельно |
| 5 | Удаление в проекциях не было ограничено организацией | Скоуп по `siteId in (…)` и по `tenantId` |
| 6 | Сид работал без контекста, два демо-объекта вообще без организации | Сид целиком внутри `runWithTenantContext`, объектам проставлена организация |

## Что нашлось при проверке на стенде (и было починено)

Стенд: копия боевых данных, все политики строгие, приложение подключается
ролью `pilingtrack_app` без `BYPASSRLS`. Ниже — то, что до стенда выглядело
рабочим.

**Хранилище организации существовало в трёх экземплярах.** Next.js собирает
маршруты, `instrumentation` и фоновые задачи разными сборками, и каждая
получает свой экземпляр каждого модуля. Обёртка маршрута клала организацию в
одно `AsyncLocalStorage`, а расширение Prisma читала из другого и **никогда**
не видела значения. Замерено: три экземпляра, тенант не доезжал до базы ни
разу. Лечится так же, как уже лечился клиент Prisma, — хранилище живёт в
`globalThis`. Пока политики в режиме аудита, дефект незаметен: доставка не
работает, но и не требуется.

**Сырой SQL шёл мимо расширения.** `$extends({ query: { $allModels } })`
охватывает операции над моделями; `$queryRaw` моделью не является. Три экрана
собираются одним большим SQL ради скорости — аналитика по объектам, по технике
и часть отчётов. Все они молча показывали ноль. Добавлена обёртка сырых
вызовов (`wrapRawQuery`).

**Массивная форма `$transaction([...])` тоже шла мимо.** Единственный вызов —
сброс буфера телеметрии. `wrapTransaction` теперь разбирает обе формы.

**Пять точек входа без контекста:**

| Где | Что было бы после флипа |
|-----|------------------------|
| Поток событий (SSE), обёртки нет по устройству | Рукопожатие возвращало 401 всем |
| Рукопожатие WebSocket | То же — сокеты не подключались бы |
| Приём телеметрии по ключу устройства | Вставка отклонялась бы политикой |
| Суточные планировщики ТО и техготовности | Перечень организаций брался из `MaintenancePlan` / `Shift`, то есть из таблиц под RLS: ноль организаций, планировщик молча ничего не делает |
| Загрузка настройки Telegram | Уведомления молча пропадали бы |

Планировщик техготовности стоит отметить отдельно: `Shift` строгая с
13.08.2026, а прод перешёл на роль без `BYPASSRLS` в тот же день. То есть
суточный тик техготовности, скорее всего, **уже** ничего не делает на бою.
Проверить после раскатки.

## Что осталось не покрыто

**Пять таблиц с колонкой `tenantId` не имели RLS вовсе.** Три из них закрыты
следующей миграцией (`20260819140000`), две остаются открытыми сознательно:

| Таблица | Решение |
|---------|---------|
| `ReadinessAccessMatrix` | **Закрыта.** Только маршруты `/api/readiness/*`, каждый вызов принимает `tenantId` параметром и падает без него. |
| `TenantAuditChain` | **Закрыта.** Только внутри `withReadinessTenantTransaction`, которая сама выставляет переменную и падает, если та не установилась. |
| `ReadinessBackfillProgress` | **Закрыта.** Только служба дозаполнения, вызываемая по одной организации за раз. |
| `OutboxEvent` | Остаётся без RLS. Воркер публикации ходит в неё заведомо без организации — он только из строки и узнаёт, чья она. Колонка `tenantId` допускает пустоту, то есть строгое сравнение прятало бы такие строки навсегда. Строки живут минуты и не содержат бизнес-данных сверх того, что уже лежит в защищённых таблицах. |
| `IdempotencyKey` | Остаётся. Код, который её использует, мёртв (пять экспортов, ноль вызывающих), `tenantId` тоже допускает пустоту. Правильный шаг — удалить таблицу вместе с кодом, а не защищать. |

Обоснование августа 2026 («очереди и служебные журналы: воркеры разбирают их
сквозь все тенанты») было верно для очередей и по инерции распространено на
соседей. Проверка путей доступа показала, что ни одного обхода сквозь все
организации у первых трёх нет.

**Одноразовые скрипты в `scripts/`.** Они ходят в базу тем же
`DATABASE_URL`, что и приложение, то есть после перехода на `pilingtrack_app`
видят пустоту. Проверено: скрипт, меняющий ПИН-код, не нашёл пользователя.
Лечится не кодом, а порядком запуска — см. ранбук 012.

**Кэш Redis запоминает пустой ответ.** Если после раскатки какой-то экран всё
же окажется пустым, Redis подержит эту пустоту 5 минут. При откате кэш надо
чистить, иначе будет казаться, что откат не помог.

## Цена

Запрос без открытой транзакции стоит вчетверо больше операторов: `BEGIN`,
`set_config`, сам запрос, `COMMIT`. Замерено ранее: 200 чтений — 139 мс против
405 мс. Это плата за доставку организации, а не за сам флип: она уже уплачена
с момента включения расширения.

## Альтернативы, которые отвергли

**Оставить `User` и `DeviceKey` в режиме аудита.** Проще, но означает, что
любой запрос без организации видит все строки этих двух таблиц — включая
будущий, написанный по невнимательности. Узкая роль размыкает круг в трёх
названных запросах, а не в таблице целиком.

**Полагаться только на прикладной фильтр.** Он и так есть и остаётся первой
линией. Но забыть его можно — дважды забывали (31.05.2026 и 22.06.2026), оба
раза ловили глазами. RLS ловит машинно.
