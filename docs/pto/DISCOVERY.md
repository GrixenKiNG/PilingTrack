## 2. Где свая может пропасть (шаг 1)

Цепочка каскадов: `Report → PileWork → PilePassport → PileDrivingSet`, всё `onDelete: Cascade`.

Я проверил, кто реально удаляет данные. Из всех путей открыт **один**:

| Путь | Защита | Итог |
|---|---|---|
| `DELETE /api/reports/delete` (`src/app/api/reports/delete/route.ts:109`, `tx.report.delete`) | Право `reports.manage_all`, транзакция, снимок итогов в событие и аудит. **Проверки паспортов нет.** | **Дыра.** Удаление отчёта с паспортами уничтожает паспорта, залоги, приёмку мастера. След хранит только суммы дня (штуки, метры, часы), по сваям восстановить нечего. UI вызывает его из `admin-reports.tsx:206`. |
| Правка отчёта (`report.repository.ts:169`, `deleteMany` по `PileWork`) | `reconcile-report-entries.ts:45-56`: 409, если удаляется строка с паспортом или поправкой | Закрыто. |
| `hardDeleteSite` (`site-admin-command.service.ts:253`) | Отказ, если есть бригады или отчёты | Закрыто. |
| Удаление поля, куста, пикета | `assertNoSubtreeProduction` | Закрыто. |
| Удаление пользователя (`user-service.ts:343`) | Отказ, если есть отчёты | Закрыто. |

**Вывод шага 1.** Защита сделана на уровне приложения и держится везде, кроме одного маршрута. На уровне базы ничего не держит: любой будущий код или ручной SQL повторит потерю. Нужны обе линии защиты.

## 3. Расхождения ТЗ с кодом

ТЗ в целом точно, но три вещи в нём устарели или неполны:

1. **Поправки уже есть.** ТЗ предлагает придумать защиту от правок. В `PileWork` уже есть `correctsId`, `correctionNote`, `correctionReason`, а `reconcileReportEntries` не даёт удалить строку с поправкой. Для реестра нужно следовать этому же образцу (исходное не трогаем, правка отдельной записью).
2. **Часть «проектных» данных уже в паспорте.** `PilePassport` хранит `designHeadLevelM`, `designRefusalMm`, `planDeviationMm`, `tiltPercent`. Значит, часть будущей геодезии (отметка головы и отклонение в плане) уже собирается, пусть вручную. Новую геодезию строить поверх, не дублируя.
3. **Запрос на 11 прав избыточен.** Рабочий вариант на шаги 1–2: одно новое право (или расширение `piles.manage`) с ролью инженера. См. вопрос владельцу в `ERD.md`.

## 4. Что не измерено

- **Реальные данные.** Сколько на проде повторных забивок и одинаковых номеров на разных полях, не проверялось. Локальная база устарела (копия от 26.05, см. память проекта), прод не читался по правилам проекта. Эти числа нужны до импорта реальных реестров, чтобы оценить долю неоднозначных сопоставлений. Запрос для владельца дан в `ERD.md`, раздел 6.
- **Индекс GitNexus.** `impact` не запускался: правок кода пока нет. Перед шагом 1 запустить для `PilePassport` и `deleteReport`-маршрута.
- **Количество и формат реальных проектных реестров** (какие колонки в XLSX у заказчика): в ТЗ не описано, нужен пример файла.

## 5. Риски и запрещённые изменения

- Не вводить уникальность `(tenantId, pileNumber)` для паспортов.
- Не менять `src/lib/pile-passport.ts`, `REFUSAL_SET_WINDOW`, `DEFAULT_SET_BLOWS` и приёмку мастера (`PENDING/ACCEPTED/NEEDS_REDRIVE`).
- Не менять экраны оператора и маршрут `/admin/reports?view=piles`.
- Не копировать удары, глубины, время из паспортов в новые таблицы: только ссылка.
- Миграции Prisma: `migrate dev` сбрасывает базу, писать SQL вручную и проверять `_prisma_migrations` (память: «Ловушки миграций Prisma»).
