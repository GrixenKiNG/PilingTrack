Перед каждой группой измерений был один GC, между двадцатью измерениями — естественная сборка. RSS журнала ниже, поскольку V8 вернул память во время этой группы.

Каждый результат проверяется: количество машин/объектов/свай, отсутствие пропавших паспортов, фото у всех машин, правильный расход топлива. Проверки стоят вне таймера. Никаких mocks.

Это общий рабочий компьютер, эксклюзивность CPU/Docker не обеспечивалась. Для каждого размера новая БД с теми же миграциями, ANALYZE после seed и новый процесс измерения. Pool max=20, connection timeout=10s, statement_timeout=15s, lock_timeout=5s. Запросы последовательные, без искусственного параллельного потока клиентов.

Это service microbenchmark, не HTTP-нагрузка и не оценка числа одновременно работающих пользователей. p95 — nearest rank 19-й из 20 отсортированных результатов, доверительный интервал не оценён. Первые вызовы содержат, в частности, создание пула; они не включают предшествующий import всего модуля. Холодный диск/ОС-кэш не сбрасывались. После seed/ANALYZE и прогрева данные преимущественно в памяти PostgreSQL; это **hot-cache** измерения. Разница p95 x1/x5 не обязана быть монотонной на общем компьютере при двадцати точках.

Планы получены отдельно от таймеров, на той же app-роли и с transaction-local tenant GUC, для точного SQL и параметров настоящих функций. Это один EXPLAIN каждого выбранного запроса, его Execution Time нельзя называть SQL p95. Исходные планы и captured queries сохранены без сокращений.

| --- | ---: | --- |
| Главный SELECT site analytics | 165.4 | Несколько чтений Report, последовательное чтение всей релевантной истории |

У журнала spill начинается уже на x5: 717 temp written blocks (~5.6 MiB), Execution Time 170.8 мс; на x1 временных блоков нет, Execution Time 40.1 мс. На x20 сортировка и hash joins сбрасывают промежуточные данные на диск. Большой COUNT/агрегат по всей истории не исправится автоматически индексом на дату, когда фильтра даты нет.

Основной harness выбирает до трёх SELECT каждой функции по discovery query-event duration. У fleet duration Prisma может включать ожидание последовательной выдачи связанных SELECT и не равен серверному Execution Time: маленький справочник оказался дольше большого PileWork. Чтобы не принять эту очередь за SQL bottleneck, дополнительно восстановлена **четвёртая свежая БД x20 по тому же seed** и выполнен EXPLAIN всех 15 настоящих fleet SELECT, включая PileWork и Media. Это дополнительное исследование, исходные измерения не перезаписывались. Полный файл `plans-x20-getFleetSnapshot-all-selects.json`; replay завершился 0 и БД удалена. В replay Report прочитал 4 shared blocks с диска, остальные основные запросы показали shared reads 0; холодной нагрузкой это всё равно не является.

## Предлагаемые бюджеты и следующие действия

До согласования владельцем это диагностические ориентиры для **такого же** локального hot-cache одиночного вызова: fleet p95 ≤500 мс, site ≤250 мс, equipment ≤250 мс, journal ≤500 мс. Для harness-процесса — максимум 512 MiB RSS как повод исследовать рост; это не лимит production Next.js и не SLA.

На x1 и x5 все эти временные ориентиры выдержаны. На x20 превышены fleet, site и journal; equipment остался в бюджете. Следовательно, в данной модели проблемы интерактивного отклика проявились **между 50 и 200 машинами / 30000 и 120000 строками истории**, точная граница неизвестна. При другом количестве дней, строк на отчёт, фото или одновременных читателей она изменится. OOM не было, запас до условных 512 MiB уменьшился. Производственная готовность этим не подтверждается.

Предложение по журналу: отдельно исследовать переписывание общего агрегата и широкого DISTINCT-header так, чтобы меньше широких строк попадало в общий sort/hash, сохранив точные итоги всего периода и все нынешние фильтры. Сравнить на тех же raw fixtures и контрольных результатах. Проверить ограниченный transaction-local work_mem в диагностическом эксперименте; глобально поднимать память нельзя без оценки одновременных запросов. Индексы для селективного tenant/date/site-фильтра обсуждать только по новым EXPLAIN: текущая полная выборка закономерно предпочитает seq scan. Здесь SQL, индексы и настройки приложения не менялись.

Для мониторинга следующий кандидат — серверный выбор одного последнего Media на машину и агрегирование последних отчётов/выработки в БД вместо передачи всех связанных строк. Сейчас 2000 Media превращаются в 200 карточек, а 32000 PileWork загружаются в Node. Разница между быстрым SQL PileWork и сервисным временем сама по себе не доказывает, какая доля приходится на сериализацию, Prisma, сеть или JS: нужен отдельный профиль CPU/allocations. Для site analytics — проверить повторные агрегации истории и раннее сужение по tenant/period по фактическому RLS-плану. Это предложения отдельной задачи; изменений src нет.

Следующие замеры: подтвердить безопасный production aggregate baseline; проверить 75/100/150 машин для уточнения границы; увеличить плотность фото и длительность истории; потом воспроизвести на изолированном host, при конкуренции 5/20 читателей и через HTTP с PgBouncer. Нагрузку больше этой матрицы в данном задании не запускали.

## Исправление воспроизводимости после независимого ревью

В исходном replay найден P2: seed создавал данные относительно текущего дня и текущих PERF_* параметров, а EXPLAIN проигрывал сохранённые SQL/параметры. Для исходного cutoff 16.10 набор 23.10 содержит 1600 Report; повтор 24.10 давал бы 1800. Изменение окружения могло также создать 140 машин вместо исходных 200. Это дефект повторного запуска harness; исходные результаты 23.10 остаются валидны.

Сначала без БД запущен config-only тест настоящего prefix seed.mjs: 2 passed / 2 failed, exit 1 (date-fix-before.log). Инъекция затрагивает только календарь, не SQL/Prisma/сервисы. После исправления режим explain-replay читает **дату и размеры исходного config-x20.json**, игнорирует текущие параметры seed и до подключения к БД проверяет tenant/scale, допустимые размеры, дату и согласованность dateFrom. Обычный benchmark по-прежнему берёт текущую дату и параметры окружения.

`node --test output/perf-1023/seed-config.test.mjs`: exit 0, **6 passed / 0 failed / 0 skipped** (date-fix-after.log). Проверены capture-day и следующий день (23/24 октября на исходных артефактах), прежние 1600 отчётов, внешнее изменение размеров, обычный current-day seed, отказ при повреждённом диапазоне дат/чрезмерном размере capture. Дата и ожидаемое число строк в тесте выводятся из сохранённого capture, поэтому он работает и после нового разрешённого benchmark.

Приложение и исходные raw timings/plans не менялись. Полная нагрузка/новая БД, tsc/lint/build/unit/E2E после этой правки не повторялись: изменён только output harness, целевая проверка — конфигурация и отсутствие сдвига набора. Новых контейнеров не создавалось. GitNexus impact seed.mjs вернул UNKNOWN/target not found (exit 1), это ожидаемый предел индекса output, не low; текстовый поиск подтвердил двух вызывающих — run.sh и replay-fleet.sh.
