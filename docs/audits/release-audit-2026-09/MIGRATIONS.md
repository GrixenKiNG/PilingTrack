## Известные риски (по коду/истории)
- Миграции, потенциально блокирующие крупные таблицы (`ADD COLUMN NOT NULL` без default, `CREATE INDEX` без `CONCURRENTLY`) — гейт их отслеживает, конкретные случаи не перечислены в этом проходе.
- `ReportAnalytics.deleteMany` + `recomputeSiteDailySummary` при удалении отчёта — best-effort вне транзакции; при отказе остаются несоответствия проекций (пересчёт ночью как backstop).
- Историческая проблема: в single-tenant prod `Report.tenantId` записывался как NULL — в коде есть комментарий и явное `requireTenantId` (исправлено на уровне кода).

## Рекомендации
1. Прогнать миграции на пустой БД и на снапшоте предыдущей версии (CI job «Schema + migrations (Postgres)» уже есть — расширить проверкой отката).
2. Проверить наличие rollback-плана для каждой новой миграции крупных таблиц.
3. Прогнать `scripts/explain-analyze.ts` на реалистичных объёмах и зафиксировать индексы.
4. Проверить совместимость схемы «старая версия приложения ↔ новая схема» для безопасного rolling deploy.
