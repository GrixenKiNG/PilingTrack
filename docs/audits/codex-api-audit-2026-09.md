## Как читать таблицу

- Путь указан относительно корня репозитория; `:число` у метода — строка его экспорта, у схемы — строка вызова в этом же route.ts.
- `withApi` сама по себе **не проверяет авторизацию, CSRF или частоту**. Проверки прав перечислены отдельно. `withMutation` включает withApi; `withReadinessCommand` включает withMutation.
- «Тело не читается» означает отсутствие входного JSON-контракта; это нормально для GET и команд, которым достаточно path/query. Проверки query не выдаются за safeParse тела. TypeScript-приведение типа и readJsonBody не являются проверкой структуры.
- «Строгое равенство» означает обязательный tenant в запросе, связанном объекте или явное сравнение tenant перед использованием основной сущности. Это **не** сертификат проверки каждого вложенного foreign key. Для create указано, откуда задаётся tenant; фильтра выборки у create нет.
- «Нет» означает отсутствие общего явного сравнения с tenant текущего пользователя в указанной ветке. RLS учитывается отдельно: requireAuth устанавливает контекст (`src/lib/auth.ts:199`), db применяет tenant GUC (`src/lib/db.ts:121`). Действующая роль БД и установленные политики **не проверены**: подключения к БД в этой задаче нет.
- Если в route tenant только передан дальше, а вся цепочка сервиса не проверена, это прямо указано. Это не утверждение наличия или отсутствия уязвимости.

### Обозначения ответов при ошибке

Таблица перечисляет явные ответы маршрута и общий обработчик. Для всех указанных JSON-форм `error` — текст, кроме формата R. HTTP-код ServiceError определяется конкретной доменной проверкой.

| Обозначение | Что получает клиент |
| --- | --- |
| **A** — withApi | ServiceError → его status и `{error: message}`; Prisma P2025 → 404 `{error: "Not found"}`, P2002 → 409 `{error: "Запись с такими данными уже существует"}`; CircuitOpenError → 503 `{error: "Service temporarily unavailable", retryAfter}` + Retry-After; прочие исключения → 500 `{error: "Internal server error"}`. `src/core/api-wrapper.ts:107`. |
| **H** — requireAuth | 401 `{error: "Unauthorized" / "Session is invalid" / "User not found", requestId}`; внутренний сбой проверки → 500 `{error: "Authentication failed", requestId}`. `src/lib/auth.ts:158`. |
| **M** — withMutation | Всё A; до обработчика CSRF → 403 `{error: "CSRF validation failed: …"}`; rate limit → 429 `{error: "Too many requests"}` + Retry-After. `src/core/api-wrapper.ts:181`. Применяется только к методам withMutation/withReadinessCommand, не к соседнему GET. |
| **R** — readinessErrorResponse | ReadinessCommandError → его status и `{error:{code,message,details,correlationId}}`, X-Correlation-Id/X-Request-Id и доменные headers. `src/app/api/readiness/_shared/response.ts:21`. JSON/схемы обычно 400/422; права 403; доменные состояния/версии — по коду ошибки. Ошибки CSRF/rate/requireAuth и обычные исключения остаются M/H/A, не превращаются автоматически в R. |
| **C** — readiness context | Через resolveReadinessRequestContext: H; отсутствие tenant → 403 `{error:{code:"FORBIDDEN",message:"Tenant context is required"}}` (без остальных полей R). `src/app/api/readiness/_shared/request-context.ts:70`. |
| **F** — без общего catch | В показанном route нет нормализации необработанного исключения. Конкретное тело ответа Next.js/прокси в deployed production **не проверено**; стек/HTML/JSON не предполагаются. |
| **J** — readJsonBody | Синтаксически некорректный JSON → ServiceError 400 `{error:"Тело запроса должно быть корректным JSON"}` через A/M. Структуру проверяет отдельная схема. `src/core/api-wrapper.ts:162`. |
| `details:flatten` / `details:issues` | В первом случае результат Zod `error.flatten()`, во втором исходный массив `error.issues`. `[{field,message}]` — явно спроецированный массив, а не полный объект Zod. |

## withReadinessCommand: CSRF и ограничение частоты

**Да: защиты наследуются непосредственно от withMutation, а не реализованы похожим кодом.** `src/app/api/readiness/_shared/route-adapter.ts:17` возвращает `withMutation(..., options)`; `:29` передаёт options без изменения.

Порядок исполнения:

1. `withApi` открывает контекст запроса и обрабатывает общие исключения.
2. `withMutation` вызывает `withCsrf(request)` **до** обработчика (`src/core/api-wrapper.ts:182`).
3. Затем проверяет `rateLimiter.check(identifier, options.rateLimit ?? MUTATION_RATE_LIMIT)` (`:201`).
4. Только после этого readiness-адаптер вызывает `resolveReadinessRequestContext`, получает пользователя/tenant/матрицу прав и запускает команду.
5. ReadinessCommandError из команды получает формат R. Ошибка при разрешении контекста находится **до** внутреннего try адаптера: обычное исключение оттуда уйдёт через A. Отказ CSRF/лимитера также остаётся плоским JSON M.

CSRF применяется к POST/PUT/PATCH/DELETE; readiness-команд нет в списке исключений `src/lib/csrf-protection.ts:28`. Проверяются Sec-Fetch-Site, Origin/Referer относительно Host и наличие хотя бы одного из этих признаков (`:43`). Это та же защита, что у всех withMutation, включая её зависимость от правильной передачи Host прокси; настройки работающего прокси не проверены.

По умолчанию: **100 попыток / 60 секунд, блокировка 60 секунд** (`src/core/api-wrapper.ts:170`). Ключ включает фактический pathname, хеш токена сессии и идентификатор IP (`:195`); это лимит на маршрут/сессию/IP, не единая квота всей организации и не общий лимит всех ID ресурса. Конкретный backend лимитера, распределённость между экземплярами и поведение production при отказе Redis в этой задаче не проверялись.

Отдельные POST с withApi не следует ошибочно считать незащищёнными лишь по имени обёртки:

## Находки

Ниже — подтверждённые свойства кода и вытекающие из них сценарии. **Критичных находок с достаточным подтверждением не установлено.** Это не означает отсутствия критических проблем за пределами проверки. Сценарии не запускались против БД, Redis, хранилища или production. Наличие необходимых данных/известного ID указано как условие, а не предполагается угаданным.

### F-01 — важно: четыре GET готовности не проверяют право чтения

**Код:** `src/app/api/readiness/shifts/route.ts:17`, `src/app/api/readiness/shifts/[id]/route.ts:14`, `src/app/api/readiness/handovers/[id]/route.ts:9`, `src/app/api/readiness/work-permits/[id]/route.ts:14`. Во всех обработчиках после resolveReadinessRequestContext выполняется запрос данных без проверки readiness.read. Контекст только вычисляет capabilities (`src/app/api/readiness/_shared/request-context.ts:79`); queryShift/queryHandover/queryWorkPermit также не проверяют права (`src/modules/readiness/application/shifts/queries.ts:7`, `src/modules/readiness/application/permits/queries.ts:56`). По умолчанию ASSISTANT имеет только readiness.defect.report (`src/modules/readiness/domain/capability-defaults.ts:106`).

**Сценарий:** действующая сессия ASSISTANT → `GET /api/readiness/shifts` → получает смены своей организации, хотя readiness.read не выдано. Зная ID в той же организации, аналогично читает смену, передачу или наряд по ID. RLS не исправляет отсутствие проверки права внутри своей организации.

**Исправление:** одинаково проверять readiness.read перед каждым из четырёх query. Соседние current/history/work-permits-list уже проверяют capability.

### F-02 — важно: события и API аудита не изолированы по организации

**Код:** `src/services/feedback/feedback-event-service.ts:83` возвращает для привилегированной роли пустой where; для остальных — actorId или audience ALL. `:113` читает события с этим условием; `:177` применяет его к read/ack. `src/services/audit/audit-history-service.ts:81` выбирает FeedbackEvent только по scope/targetId; tenantScope ограничивает справочники имён, а не сами события. Модель `prisma/schema.prisma:2515` не содержит tenantId.

**Сценарий:** в общей базе есть события организаций A и B → ADMIN/DISPATCHER A вызывает `GET /api/feedback/events` → код выбирает также события B, включая message/metadata. Обычный пользователь A видит события B с audience ALL. Пользователь с system.read может запросить `GET /api/audit?scope=…&targetId=<известный ID B>` → события не ограничиваются tenant A.

**Исправление:** хранить tenant в FeedbackEvent и проверять его при create/list/read/ack/audit, а глобальные инфраструктурные события выделить в отдельный явно авторизованный канал. Индивидуальные нестандартные политики живой БД не проверены; прикладной защиты в показанном коде нет.

### F-03 — важно: PDF-задания доступны по ID без tenant-проверки

**Код:** period-PDF проверяет только reports.read_all перед status/download (`src/app/api/reports/pdf/route.ts:155`); single-PDF проверяет ownerId либо reports.read_cross_user (`src/app/api/reports/single-pdf/route.ts:151`). Очередь одна — `pdf-generation` (`src/lib/pdf-queue.ts:28`), PdfJobData не содержит tenantId (`:108`), получение задания — Job.fromId без tenant (`:197`). reports.read_all/read_cross_user доступны нескольким прикладным ролям (`src/services/auth/authorization-service.ts:63`).

**Сценарий:** FOREMAN/ADMIN организации A знает UUID ещё существующего PDF-задания B → `GET /api/reports/pdf?jobId=<UUID B>&action=download` либо статус → получает результат/состояние задания B. Через single-pdf чужой владелец также проходит при reports.read_cross_user. UUID снижает возможность перебора, но не является проверкой принадлежности. Условие: async-режим работает и ID стал известен; произвольное получение ID не доказано.

**Исправление:** сохранять tenantId в задании, проверять его до status/download и только затем проверять права владельца/чтения. Новая генерация и чтение уже созданного задания — разные ветки; tenant-проверка при генерации не защищает последующую выдачу.

### F-04 — важно: администратор организации управляет глобальной DLQ

**Код:** `src/app/api/admin/dlq/route.ts:21` / `:71` проверяют dlq.manage; эта способность разрешена ADMIN (`src/services/auth/authorization-service.ts:126`) без отдельного platform-admin. GET возвращает payload/errorMessage по общему where (`src/app/api/admin/dlq/route.ts:36`). retry/discard ищут только id (`src/core/outbox/dead-letter-queue.ts:85`, `:119`). `prisma/schema.prisma:2813` — DLQ без tenantId.

**Сценарий:** ADMIN A → `GET /api/admin/dlq?status=all` → видит payload и ошибки записей B; затем `POST /api/admin/dlq` с `{"id":"<entry B>","action":"discard"}` и допустимыми CSRF-заголовками → помечает чужую запись discarded. Tenant-проверки в этой цепочке нет.

**Исправление:** ограничить операции tenant записей либо ввести отдельные явно платформенные полномочия для общей очереди. Сам по себе ADMIN в текущей прикладной матрице не различает эти два уровня.

### F-05 — важно: API перестроения проекций обходит все организации

**Код:** `src/app/api/admin/projections/rebuild/route.ts:40` проверяет projections.rebuild и затем вызывает функции без tenant (`:50`). `src/modules/reports/application/projections/rebuild.ts:32`, `:92`, `:178` запускают forEachTenant. `src/lib/tenant-iteration.ts:23` читает все активные tenant, а `:33` явно переключает контекст на каждый.

**Сценарий:** ADMIN A → `POST /api/admin/projections/rebuild?name=all` с корректным CSRF → пересчитываются проекции A и B, включая операции удаления/перезаписи (`src/modules/reports/application/projections/rebuild.ts:80`, `:164`). Это подтверждённый выход за границу организации запроса, а не предположение о выключенном RLS: helper сознательно меняет контекст.

**Исправление:** пользовательский endpoint должен передавать tenant актёра; глобальный rebuild — отдельная платформенная операция. Повреждение данных этим пересчётом не утверждается; подтверждены чужие записи и общий объём работы.

### F-06 — важно: привязка чужого mediaId к своему документу обходит запрет скачивания

**Код:** `src/app/api/users/[id]/documents/route.ts:19` и `src/app/api/users/[id]/documents/[docId]/route.ts:19` допускают произвольный mediaId. Пользователь может менять свои документы (`src/services/users/user-documents.ts:68`); mediaId сохраняется без проверки права на Media (`:346`, `:433`). После отказа assertCanAccessMedia download пробует ownsUserDocumentMedia (`src/app/api/media/[id]/download/route.ts:35`), а та проверяет только существование связи с собственным документом (`src/core/media/media-auth.ts:170`).

**Сценарий:** пользователь знает ID завершённого, неудалённого файла другого пользователя **той же организации**, к которому его обычная media-ACL не допускает → `PUT /api/users/<свой userId>/documents/<свой docId>` с `{"mediaId":"<чужой mediaId>"}` → `GET /api/media/<чужой mediaId>/download` → fallback принимает созданную самим пользователем связь и выдаёт подписанную ссылку. RLS по tenant не закрывает этот сценарий внутри организации.

**Исправление:** при create/update документа проверять tenant, статус и право использовать именно этот mediaId; нельзя принимать самосозданную связь как независимое доказательство доступа.

### F-07 — важно: публичный readiness раскрывает исходную ошибку БД

**Код:** `src/app/api/ready/route.ts:24` выдаёт readiness.checks без фильтра; старый alias отдаёт тот же readiness (`src/app/api/readiness/route.ts:14`). `src/core/observability/health-checks.ts:53` помещает Error.message базы в details.error; `:128` добавляет имена отсутствующих env; buildReadiness сохраняет оба объекта (`:192`).

**Сценарий:** во время сбоя БД анонимный клиент делает `GET /api/ready` или `GET /api/readiness` → получает 503 с исходным текстом ошибки драйвера в checks.database.details.error. Состав конкретной ошибки зависит от драйвера; наличие пароля/секрета в ней **не доказано**. Сам факт выдачи внутренней ошибки и диагностических деталей подтверждён.

**Исправление:** публичным probes отдавать только ready/status и минимальные состояния компонентов, подробную диагностику оставить авторизованному system/status.

### F-08 — важно: несколько прикладных веток полагаются только на RLS вместо tenant-проверки

**Код:** `src/modules/reports/application/queries/report-query.service.ts:58`, `:94`, `:232` исключают ADMIN/DISPATCHER из where.tenantId (edit/all/my). `src/services/reports/report-history-service.ts:33` получает tenant из самого отчёта, а не сравнивает с актёром. `src/core/media/media-auth.ts:193` разрешает привилегированные роли до сравнения tenant, а confirm/delete выбирают media по одному id. POST crews передаёт в createCrew только userId актёра (`src/app/api/crews/route.ts:54`); `src/modules/crews/application/commands/crew-command.service.ts:141` читает зависимости по id, assertSameTenant (`:65`) сравнивает их между собой, но не с tenant актёра.

**Сценарий и граница доказательства:** ADMIN A → запрос чужого report/media ID или POST crews со всеми ID организации B → **прикладной код не отвергает чужую организацию**. При рабочем RLS запросы к базе могут быть надёжно заблокированы. Если соединение обходит RLS или нужной политики нет, дополнительного прикладного барьера в этих ветках не остаётся. Факт обхода RLS/утечки на развёрнутом сервере **не проверен**, поэтому данная находка относится к подтверждённому отсутствию требуемой независимой проверки, а не к доказанному production-эксплойту.

**Исправление:** строгое равенство tenant для всех ролей до чтения/изменения ресурса; при создании crew сверять каждую зависимость с tenant актёра. RLS оставить вторым барьером.

### F-09 — мелочь: request-acceptance не валидирует форму тела и проглатывает ошибку JSON

**Код:** `src/app/api/readiness/shifts/[id]/request-acceptance/route.ts:10` превращает ошибку разбора в `{}`; `:13` обращается к body.expectedVersion после TypeScript cast без safeParse.

**Сценарий:** авторизованный пользователь с readiness.shift.manage, корректными CSRF и tenant, существующая смена → POST этого маршрута с JSON `null` → при выполнении callback обращение к свойству null даёт TypeError и общий 500 вместо 400/422. Синтаксически битый JSON, напротив, не отклоняется как битый: команда получает undefined expectedVersion; дальнейший исход зависит от If-Match и состояния смены. Успешное изменение по такой посылке не воспроизводилось.

**Исправление:** readJsonBody + versionedShiftSchema.safeParse и согласованный 400/422.

### F-10 — мелочь: API PDF возвращает внутренний текст ошибок очереди/скачивания

**Код:** `src/app/api/reports/pdf/route.ts:238`, `:265`; `src/app/api/reports/single-pdf/route.ts:249`, `:276`. Обработчики возвращают err.message, обходя нормализацию withApi. Дополнительно `src/lib/pdf-queue.ts:209` возвращает job.failedReason как часть ответа статуса.

**Сценарий:** пользователь, прошедший проверку доступа к PDF, вызывает status/download существующего UUID во время ошибки backend → получает 500 с внутренним message/error; для завершившегося ошибкой задания — failedReason. Конкретные секреты в этих строках не доказаны.

**Исправление:** наружу стабильный код/сообщение и requestId, исходную ошибку — только в серверный журнал.

### F-11 — мелочь: webhook принимает валидный JSON без проверки структуры

**Код:** `src/app/api/alerts/webhook/route.ts:61` проверяет только JSON-синтаксис; `:68` читает payload.alerts, `:76` — alert.labels.severity, `:77` — alert.annotations. Типы interface удаляются при исполнении; safeParse отсутствует.

**Сценарий:** клиент с действительным webhook-секретом отправляет `POST /api/alerts/webhook` с `null` либо `{"alerts":[{"status":"firing"}]}` → необработанный TypeError вместо контролируемого 400. Ошибка возможна и у штатного интеграционного клиента с нарушенным payload. Без знания секрета этот путь недоступен. Формат ответа фреймворка не проверен.

**Исправление:** runtime-схема payload/элементов и ограничение числа alerts; общий безопасный catch. Отсутствие limiter подтверждено кодом маршрута, но наличие внешнего rate limit на прокси не проверено, DoS не заявляется доказанным.

### F-12 — мелочь: отсутствующие координаты погоды превращаются в нули

**Код:** `src/app/api/weather/route.ts:45` — Number(searchParams.get(...)); при отсутствии параметра Number(null) равен 0. Проверка конечности и диапазона пропускает 0 (`:47`).

**Сценарий:** авторизованный `GET /api/weather` без lat/lon → вызывается прогноз для 0,0 вместо ошибки обязательных параметров. Если отсутствует только одна координата, только она подменяется нулём. Успешный сетевой ответ провайдера не проверен; неверные аргументы вызова следуют из кода.

**Исправление:** отдельно проверять наличие и непустое строковое значение обеих координат до Number.
