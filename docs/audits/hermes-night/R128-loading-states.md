# R128-loading-states — Состояния загрузки в разделах админки

Аудит только чтения: как админские разделы (`/admin/**`) показывают момент
загрузки — скелетон/спиннер, или мигание текста и прыжки макета; блокируются
ли кнопки на время запроса. Замороженные области (варианты операторского
экрана, ORION) не проверялись.

Опорные правила продукта: «отсутствие данных должно отображаться явно»
(PRODUCT.md:67) и лежащий рядом с этим принцип «пользователь должен видеть,
что запрос идёт» — в проекте уже есть инструменты для этого
(`src/components/piling/async-ui.tsx:21` `useMinSkeletonDuration`,
`src/components/ui/skeleton.tsx`), но применены не везде.

## Итог

- Всего находок: **19** — критично **0**, важно **6**, мелочь **13**.
- Общая картина: каркас загрузки в проекте есть и на части экранов сделан
  хорошо — `admin-equipment`, `admin-crews`, `admin-sites` (первый вход),
  `admin-dictionaries`, `admin-users`, `admin-reports` (первый вход),
  `admin-telegram`, `admin-dlq` при монтировании показывают полноэкранный
  `Skeleton`. Проблема в двух местах: (1) **повторная** загрузка (смена
  фильтра, сохранение, удаление) на `admin-reports` и `admin-users` подменяет
  **весь экран** скелетоном — фильтры «слетают», страница мигает; (2) целый
  ряд блоков и экранов грузится **текстом** «Загрузка…» или просто пустотой
  без резерва высоты — при появлении данных макет прыгает
  (`admin-incidents`, блоки ТО/осмотров/истории, KPI-полоса аналитики).
- Топ-5 по важности:
  1. `admin-reports/use-reports-data.ts:202` + `admin-reports.tsx:249` — смена
     фильтра/периода и удаление отчёта гасят весь экран скелетоном.
  2. `admin-users/use-users-list.ts:59` + `admin-users.tsx:243` — сохранение и
     блокировка пользователя гасят весь список скелетоном.
  3. `admin-users/user-detail.tsx:133-146` — кнопки «Блокировать/Удалить» в
     карточке пользователя не блокируются на время запроса (двойной клик =
     два запроса).
  4. `admin-telegram.tsx:460` — подтверждение удаления канала Telegram без
     `busy`: кнопка не блокируется (повтор R124 №14 / R113 по классу).
  5. `admin-analytics.tsx:237` — KPI-полоса появляется только после
     `/api/monitoring/fleet` и сдвигает вниз вкладки (прыжок макета).

## Методика

Команды воспроизводимы из корня worktree (`D:\PillingR\wt-night`).

1. Границы области: `rg --files src/app | rg "admin"` — маршруты `/admin/**`,
   включая `/admin/to` (контур техготовности); соответствие экранов
   компонентам — чтение `src/app/(app)/admin/**/page.tsx`.
2. Поиск состояний загрузки: `rg -n "loading" src/components/piling` (файлы с
   `Skeleton`), `rg -n "useMinSkeletonDuration|QueryErrorBanner" src -l`.
3. Поиск текстовых заглушек загрузки:
   `rg -n "Загрузка|Загружаем|Loading|Loader2" src/components/piling/admin-* src/components/piling/maintenance src/components/piling/inspections src/components/piling/ops-shell`.
4. Поиск незаблокированных кнопок: `rg -n "disabled"` рядом с
   обработчиками мутаций; сверка с образцом `admin-crews.tsx:286`
   (R124 №14).
5. Каждый экран читался сплошным `read_file` (ветки первой загрузки,
   повторной загрузки, кнопок-мутаций), а не только grep. Все строки таблицы
   открыты в этой сессии.
6. Асинхронные источники раскладки: `layout-editor/use-page-layout-template.ts`
   (порядок/размер плиток приходит с сервера) — влияние на `/admin` и
   `/admin/analytics`.

Хорошие образцы (не находки): `admin-crews.tsx:192-200` (скелетон),
`admin-crews.tsx:286` (кнопка блокируется, R124 №14),
`admin-equipment/admin-equipment.tsx:64` (скелетон),
`admin-sites/user-assignment.tsx:110` (спиннер),
`admin-reports/report-evidence-row.tsx:78,87` (кнопки выгрузки
`disabled={exporting !== null}`),
`admin-sites/site-editor/delete-site-dialog.tsx:53` (busy),
`admin-users/user-dialogs.tsx:193,333,390` (spinner в диалогах),
`admin-dlq.tsx:179` (кнопка «Обновить» заблокирована).

## Не проверено

- **Runtime-поведение.** Не запускались dev-сервер, БД и Playwright: аудит
  только чтение кода. Фактические тайминги мигания и прыжков макета не
  измерялись (нет замеров CLS/Lighthouse), все выводы — из прочитанного кода
  (все строки таблицы открыты).
- **Точный момент ответа серверов.** Гипотеза «запрос длится заметно долго»
  выведена из структуры кода (сколько запросов, есть ли `Promise.all`), а не
  из замеров латентности `/api/monitoring/fleet`, `/api/reports/all`,
  `/api/users`.
- **CSS-высоты скелетонов.** Совпадение высоты скелетона и итогового блока
  (то, от чего зависит величина прыжка) по классам не измерялось; в находках
  отмечено только наличие/отсутствие резерва высоты.
- **`/admin/to` (контур техготовности).** Просмотрен на уровне `to-module.tsx`
  (`QueryState` `loading` → `TechReadinessModule`, `to-module-bits.tsx:198`
  `LoadingBlock`), панели `to/readiness/**` сплошным чтением не разбирались —
  там возможны дополнительные вхождения того же класса.
- **Вне области (не проверялось по условию задачи):** замороженные
  `src/app/operator/**`, `src/components/piling/operator*/**`,
  `src/modules/operator-mobile/**`, ORION. Операторские и мастерские экраны
  внутри `src/modules/**` не сканировались.
- **Проверки перед коммитом:** код не менялся (аудит только чтения).
  `npx tsc --noEmit` — exit 0. Тесты не запускались: ни один исходный файл не
  затронут, регрессии нечего ловить (изменён только этот документ).
