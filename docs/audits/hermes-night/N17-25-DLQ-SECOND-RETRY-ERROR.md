## Итог

Повторное нажатие «Повтор» по уже обработанной записи DLQ возвращает HTTP 400 с текстом
«Не удалось переотправить» — при том, что первое нажатие завершилось успехом. Это не сбой данных:
запись захватывается атомарно (`updateMany where status='pending'`), дубля доставки нет — второе
нажатие просто «выигрывается» защитой от повторной обработки, но сервер сообщает об этом как об ошибке.
Причина: `retryDlqEntry` возвращает `boolean`, и маршрут сводит к одному 400 и «запись уже обработана»,
и «транзакция упала». Администратор не различает «уже поставлено в очередь» и «настоящий отказ».

Найдено **14** находок: **2 важно**, **12 мелочь**, критичных нет. Топ-5:
1. `src/core/outbox/dead-letter-queue.ts:123-127` + `src/app/api/admin/dlq/route.ts:125-128` — второй
   повтор по resolved-записи даёт 400 «Не удалось переотправить» (важно).
2. `src/core/outbox/dead-letter-queue.ts:151-154` — `catch` превращает любую ошибку транзакции в `false`;
   сервер отвечает тем же 400, реальная причина только в логе (важно).
3. `src/components/piling/admin-dlq.tsx:212-219` — клиент показывает сырой текст сервера; «Не удалось
   переотправить» не говорит, что делать (мелочь).
4. `src/components/piling/admin-dlq.tsx:198,390` — защита от двойного нажатия срабатывает только после
   перерисовки: два клика в одном кадре дают два POST (гипотеза-триггер наблюдения) (мелочь).
5. `src/core/outbox/dead-letter-queue.ts:157-162` — «Отбросить» без захвата: повторный отброс даёт 200,
   несуществующий id — 404; коды асимметричны «Повтору» (мелочь).

Итоговый вердикт по наблюдению 16.10: **ПРОЙДЕНО** — код объясняет и 400, и отсутствие дубля доставки.

Проверяемые вопросы и ответы:
1. **Что меняет первый повтор.** В одной транзакции: `deadLetterQueue.updateMany where {id,status:'pending'} → status:'resolved'`
   (`dead-letter-queue.ts:123-126`), затем `findUnique` и `outboxEvent.create` с `attempts:0`,
   `published: consumer==='projected'`, `projected: consumer==='published'` (`:134-148`). `dedupeKey` не переносится,
   id события новый. Счётчик `attempts` самой записи DLQ **не меняется** — на карточке остаётся прежнее «попыток: N».
   Исходная строка outbox остаётся `published=true` (её проставил потребитель при переводе в DLQ, `outbox-publisher.ts:198-206`).
2. **Второй повтор.** `updateMany` даёт `count:0` → `return false` (`dead-letter-queue.ts:127`) → 400
   («запись уже resolved»). Именно это и наблюдалось.
3. **Устаревшие данные кнопки.** POST отправляет только `{id, action}` — без статуса/версии. Видимость кнопки
   целиком зависит от последнего удачного GET (`admin-dlq.tsx:379`); перед действием повторной проверки нет.
   Если GET после успешного POST не прошёл, в списке остаётся прежняя resolved-запись с кнопкой «Повтор»
   (`admin-dlq.tsx:168-188,217`).
4. **Защита от двойного нажатия.** Есть: `if (actingId) return` и `disabled={actingId === entry.id}`
   (`admin-dlq.tsx:198,390`). Но `disabled`/состояние применяются только после перерисовки; два клика до неё
   оба проходят проверку `actingId === null`. Тест (`admin-dlq.test.tsx:195-215`) между кликами ждёт
   `await waitFor(toBeDisabled)` — то есть проверяет не «два клика подряд», а «клик после перерисовки».
5. **Гонка двух администраторов.** Захват атомарный: победивший ставит `resolved` и создаёт событие; второй
   получает `count:0` → 400 «Не удалось переотправить» и не узнаёт, что запись уже кем-то обработана.
6. **Коды.** Совпадают механически (клиент смотрит только `res.ok`), но семантика расходится: 400 стоит и на
   «неверное тело», и на «уже обработано», и на «транзакция упала»; «отброс» несуществующей записи даёт 404.

- на «уже обработано» (`claim.count===0`): ответ `409 {error:'Запись уже обработана: повтор поставлен ранее. Обновите список.'}`;
- тост клиента при 409: «Эта запись уже обработана (повтор поставлен ранее). Список обновлён.» + `load()`;
- при 400-валидации оставить «Некорректные данные»; при внутреннем сбое — 500, а не 400;
- разделить в `retryDlqEntry` исходы: `'ok' | 'already' | 'error'` (или исключение на реальный сбой), чтобы маршрут
