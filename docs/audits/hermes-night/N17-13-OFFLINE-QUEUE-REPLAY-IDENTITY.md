## Итог

- Найдено 18 пунктов: **критично — 0, важно — 3, мелочь — 15**. Ниже таблицей разложено поведение клиента по каждому ответу сервера и сценарии подмены/потери авторства.
- Главное (важно, #1): **авторство команды обеспечивается ТОЛЬКО фильтром очереди по `ownerId` на клиенте.** Сервер атрибутирует запись тому, чья сессия принесла запрос (`actor.operatorId = user.id`, `command/route.ts:209`), а «своя ли смена» проверяется позже. Записи без `ownerId` (оставшиеся от прежней версии приложения — `offline-queue.ts:228-230`) считаются «своими» для ЛЮБОГО вошедшего: на общем планшете такая команда уйдёт под сессией следующего человека.
- #2 (важно): у `log-production` проверка дубликата по ключу идемпотентности стоит **ДО** проверки принадлежности смены (`production.ts:120-123` перед `125`), а сам ключ идемпотентности привязан к тенанту, а не к машинисту (`shared.ts:324`, `production.ts:604`). Требует совпадения UUID-ключа — на практике почти недостижимо, помечено ГИПОТЕЗА.
- #3 (важно): **у очереди нет ни предела размера, ни срока жизни** (`offline-queue.ts` — ни одной проверки длины/даты; сверено `Select-String` по length/MAX/limit). Отвергнутые (`FAILED`) записи лежат вечно и убираются только вручную; чужую `FAILED`-запись сменщик убрать не может.
- ПРОЙДЕНО: повтор под тем же пользователем, смена пользователя, 401/403/409/422/429/5xx/обрыв, ключ идемпотентности после перезагрузки, 5xx/429 не краснеют. Поведение по каждому статусу — в таблице ниже.
- ПРОЙДЕНО (по коду и тестам): очередь и черновики **не очищаются при выходе** из системы — очередь намеренно (владельческая), черновики живут до 24 ч (`use-local-form-draft.ts:22`).

### Сценарии потери или подмены авторства

1. **Повтор после истечения сессии (тот же человек).** ПРОЙДЕНО. 401 → `auth` → запись ждёт (`offline-queue.ts:467-469`); после входа владельца `useOfflineQueue` шлёт очередь (`use-offline-queue.ts:49-51`). Автор — тот же `operatorId` из сессии.
2. **Повторный вход другого человека на том же телефоне.** ПРОЙДЕНО (для новых записей). `readQueue()` фильтрует по `ownerId` (`offline-queue.ts:290-292`), чужое не уходит (тест `offline-queue.test.ts:289-305`); сменщику показывают счётчик чужих (`:306-310`). Остаётся намеренный случай: записи **без** `ownerId` — см. находку #1.
3. **Смена роли / «Действую как».** ПРОЙДЕНО. Маршрут сверяет РЕАЛЬНУЮ роль (`command/route.ts:193`), заголовок `x-acting-as` атрибуцию не меняет (`lib/auth.ts:189-201`); `ownerId` берётся из `currentUser.id` (`offline-queue.ts:224-226`), а не из `actingAs`.
4. **Смена смены/техники у того же человека.** ПРОЙДЕНО. Устаревшая очередь отдаётся серверу с прежним `shiftId`; `requireOpenShift`/`requireCrew` (`shared.ts:60-87`, `:38-48`) отвергают чужую смену/машину (403), запись краснеет — подмены авторства нет, но требуется ручной разбор.
5. **Совместная работа/пересменка в момент слива.** ГИПОТЕЗА. Окно между взятием снимка очереди (`offline-queue.ts:446`) и HTTP-запросом: если cookie сессии сменилась (другая вкладка/вход), команда может уйти под новой сессией; на сервере её отвергнет проверка авторства (403), но пометку получит запись прежнего владельца (#4, #5, #16).
6. **Потеря при переполнении хранилища.** ГИПОТЕЗА/мелочь. При заполнении `localStorage` `enqueue` бросает `QueueStorageError` (`offline-queue.ts:239-246`); дальше идёт прямая отправка в обход очереди (`api.ts:569-577`). Если и она не прошла временно — запись не сохранена, машинист видит предупреждение о возможной потере.
