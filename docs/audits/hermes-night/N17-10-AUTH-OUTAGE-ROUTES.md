# N17-10-AUTH-OUTAGE-ROUTES — сбои БД/Redis/сети, превращающиеся в 401, 403 или пустой успех

Аудит после фикса `1d24e24f` (`src/lib/auth-failure.ts`). Задача: найти все оставшиеся места, где отказ базы, Redis или сети во время проверки сессии или чтения данных превращается в 401, 403 или внешне успешный пустой ответ.

## Итог

- Находок: **8** — критично **0**, важно **2**, мелочь **6**. Отдельно 4 пункта в «Не проверено».
- **Буквальный класс «сбой инфраструктуры при проверке сессии → 401/403» на маршрутном слое больше не обнаружен.** `requireAuth` отдаёт 401 только на реально отсутствующую/недействительную сессию, а на любое исключение (БД недоступна) — 500 (`src/lib/auth.ts:202-210`); все проверенные маршруты пропускают этот ответ через `if (error) return error` до собственных 401/403.
- Пять маршрутов, где отказ показывают человеку, уже переведены на `authFailureResponse` → 503 + `Retry-After` (`src/lib/auth-failure.ts:17-24`): `assistant/state:21`, `assistant/command:38`, `operator/mobile/state:21`, `operator/mobile/command:191`, `admin/incidents:29,106`.
- Класс «сбой инфраструктуры при чтении данных → успешный, но неверный/пустой ответ» остался **на клиенте**: форма создания смены молча берёт пояс `Europe/Moscow` вместо пояса организации (важно), карточка погоды показывает «данных нет» (замороженная зона), экспорт отчёта оставляет пояс браузера.
- Одно смежное место (вне буквального скоупа 401/403/пусто, тот же класс «отказ инфры → ложная ошибка клиента»): `monitoring/template` отдаёт 400 «Некорректные данные» на сбой БД.
- Слои Redis полный fail-safe и в 401/403/пусто не переходят: рейт-лимитер деградирует в память (не 429), кэш `get` при недоступности возвращает `null` → чтение из БД, отзыв сессии в Redis недоступен → запрос пропускается (не logout).

### Проверено и признано чистым (ПРОЙДЕНО, находок нет)

- Проверка сессии в маршрутах: `requireAuth` (`src/lib/auth.ts:158-212`) — 401 только на отсутствующий/невалидный токен; исключение → 500.
- `withApi`/`withMutation` (`src/core/api-wrapper.ts:107-134`) — `ServiceError`/`CircuitOpenError`/известные Prisma-коды дают свои статусы, любое иное исключение → 500.
- `telemetry/ingest` + `device-key-service.authenticateDeviceByKey` (`src/services/telemetry/device-key-service.ts:109-152`) — сбой БД в `findUnique` пробрасывается → 500; 403 отдаётся только на реально неизвестный/отозванный ключ.
- Readiness-маршруты — не-`ReadinessCommandError` пробрасывается → 500 (`readiness/place-presets:83`, `readiness/export:169`, `readiness/bootstrap:56` и т.п.).
- 403 «чужая организация» (`telemetry/route.ts:151,188`, `telemetry/batch:134`) — это IDOR-проверка; сбой запроса пробрасывается в 500, а не в 403.
- Redis: рейт-лимитер при недоступности переходит в память; `cacheAside`/`redis-cache.get` при недоступности → `null` → чтение из БД; отзыв сессии (`session-service.ts:135-171`) при недоступности Redis пропускает запрос (fail-open, не logout/401).
- Клиентские экраны: `admin-reports/use-reports-data.ts`, `assistant-app.tsx:80-89`, `operator-mobile-app.tsx:252`, `offline-queue.ts:139-144` — 401/403/5xx различаются, «пустого успеха» на сбой нет.
