# N1021-G11 — ключи кэша без организации (cross-tenant leak audit)

## Итог

Проверено 3 файла инфраструктуры кэша + 7 реальных точек использования. Найдено **5 критических** и **2 важных** проблем с отсутствием `tenantId` в ключах кэша.

| Категория | Количество |
|-----------|------------|
| 🔴 Критично (прямая утечка между организациями) | 5 |
| 🟠 Важно (риск при расширении/ADMIN) | 2 |
| 🟢 Мелочь / не проблема | 3 |

Топ-5 самых опасных:
1. **ResponseCache (withApi)** — все GET-маршруты с `cache: true` кэшируются по `endpoint+params+userHash`, **без tenantId** (api-wrapper.ts:94-102)
2. **crews:all** — кэш бригад всех организаций под одним ключом (cached-queries.ts:39)
3. **cache-strategies.ts** — примитивы не требуют tenantId, بالكامل на совести вызывающего (cache-strategies.ts:101,178,237)
4. **redis-cache.ts** — buildKey не добавляет tenantId, пример в доке `'sites:all'` (redis-cache.ts:15,203-205)
5. **weather:conditions:point:...** — кэш погоды по координатам без tenantId (weather-client.ts:160,163)

---

## Методика

1. Прочитал три файла инфраструктуры: `src/lib/cache-strategies.ts`, `src/lib/redis-cache.ts`, `src/core/cache/response-cache.ts`.
2. Нашёл все места вызова их публичных API через `search_files` (cacheAside, writeThrough, staleWhileRevalidate, getOrSet, getOrFetch, withApi).
3. Для каждого вызова открыл файл и проверил: входит ли `tenantId` (или `user.tenantId`) в строящийся ключ.
4. Учёт: `CacheKey.tenantId` в response-cache.ts поддерживается, но `withApi` его не передаёт (передаёт только `userId` — хеш сессии).
5. Исключил frozen-зоны (operator/**, orion/**) из рекомендаций по правке, но включил в отчёт как «не проверено/затрагивает frozen».

## Не проверено

1. **Frozen зоны (operator/**, orion/**) — не аудировались намеренно по AGENTS.md §1. Если там есть свои кэши — они вне области этого отчёта.
2. **Другие вызовы `cache.getOrSet` / `cacheAside`** — проверены только найденные через grep (3 + 2 места). Если есть динамические вызовы или в нестандартных путях — могли пропуститься.
3. **Прямые вызовы Redis** (если где-то `client.set/get` без оберток) — не искали.
4. **Тесты** — моки могут скрывать реальные ключи; проверяли только продакшн-код.
5. **Миграция на модули** — `src/services/**` фасады могут иметь свои кэши; не проверяли глубоко.

## Рекомендации по приоритетам

1. **Срочно**: Исправить `withApi` (api-wrapper.ts) — передавать `tenantId` в `CacheKey`. Это закроет утечки во всех GET-маршрутах с `cache: true` сразу.
2. **Срочно**: Исправить `getCachedCrewsAll` — добавить `tenantId` в ключ и сигнатуру.
3. **Планировано**: Обновить `cache-strategies.ts` и `redis-cache.ts` — добавить опциональный `tenantId` в сигнатуры или хелпер `withTenant(key, tenantId)`.
4. **Косметично**: Унифицировать погоду — убрать `point:` ключ или задокументировать как публичный.
5. **После п.1**: Обновить `invalidateCrewsCache` и аналоги — передавать `tenantId` в `invalidate`.
