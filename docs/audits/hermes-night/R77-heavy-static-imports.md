# R77 — тяжёлые библиотеки, статически подключённые в маршрутах и серверных модулях

Дата: 30.09.2026. Ветка: `hermes/q4-0926`, worktree `D:\PillingR\wt-night`. Только чтение: ни один файл репозитория не изменён (`git status` пуст), создан единственный файл — этот отчёт. Для замеров запускались `node`/`vitest` из `node_modules` — изменялся только кэш `.vite`.

## Итог

- Проверено: 141 `route.ts` в `src/app/api/**`, 1213 файлов `src/**`, 274 тест-файла; граф строился обходом статических `import`/`export from` (динамические `import()` — стоп-ребро).
- **136 из 141** маршрутов в статическом графе достают хотя бы одну «тяжёлую» библиотеку. По списку задачи: `pdfkit` — 2 маршрута, `bullmq` — 2, `@aws-sdk/client-s3` — 5, `@aws-sdk/s3-request-presigner` — 5. `sharp`, `recharts`, `playwright`, `exceljs` — **ни одного** статического подключения на сервере.
- Сверх списка задачи, тот же класс: `ioredis` — 136 маршрутов, `@sentry/nextjs` — 133 (оба через `api-wrapper`), `bcryptjs` — 31.
- Клиентский бандл: из 33 файлов с `'use client'`, достающих тяжёлое, **все** — это `framer-motion` (13 прямых импортов), `recharts` (1 файл) и `@sentry/nextjs` (границы ошибок). Серверных библиотек (`ioredis`, `bcryptjs`, `@aws-sdk`, `pdfkit`, `bullmq`, `sharp`) в клиентских графах **нет ни одной** (ложные срабатывания в первой версии скрипта давали строки `import type`, см. Методику).
- Замеры загрузки (node 26.7.0, тёплый кэш ФС, отдельный процесс): `bullmq` 215 мс, `pdfkit` 118 мс, `@sentry/nextjs` 689–709 мс, `@aws-sdk/client-s3` 90–92 мс, `sharp` 85 мс, `next/server` 86–90 мс, `zod` 123 мс, `ioredis` ~1 мс. На холодном кэше те же модули: `bullmq` 3110 мс, `sharp` 1102 мс, `recharts` 11 502 мс.
- **Главное для решения:** в тестах pdf-маршрутов `pdfkit` и `bullmq` фактически **не загружаются** — тест мокает `@/lib/pdf-queue` и `@/lib/pdf-generator` (`vi.mock`), и замер `DEBUG=vite:resolve` показывает 0 обращений к `pdfkit`/`bullmq`. То есть ленивый импорт в этих маршрутах **не ускорит тесты** (это поправка к R70, находка 14); выигрыш — только холодный старт процесса и первая компиляция серверного чанка в проде. Реальный вес в тестовом сборе держит `@sentry/nextjs` через `api-wrapper` (708 мс на процесс, 54 тест-файла).
- Итого: критично — 0, важно — 7, мелочь — 7. Ни один пункт не меняет поведение сам по себе: это работа по холодному старту и по времени тестов, дефектов (ошибок/утечек прав) в этих местах не найдено.
- Топ-5 правок по выигрышу: (1) `src/workers/unified-worker.ts:26` — `startPdf` тянет `bullmq`+`pdfkit` даже когда pdf-воркер выключен флагом; (2) `src/core/api-wrapper.ts:2` — `@sentry/nextjs` (≈0,7 с на процесс) нужен только в `catch`; (3) `src/app/api/reports/pdf/route.ts:6,8` и `single-pdf/route.ts:7,9` — `pdfkit`+`bullmq` в один чанк со всеми ветками; (4) `src/core/media/media-service.ts:36-37` — `@aws-sdk` статически, хотя рядом в том же файле `sharp` уже лениво; (5) `src/app/api/media/[id]/download/route.ts:3,78` — мёртвый `import { getMediaService }` + `void getMediaService`, тянущий 8 файлов и дублирующий `@aws-sdk`.
- Отдельный ответ на вопрос задачи: `exceljs` в проекте **не установлен** (`package.json` — ABSENT; выгрузка сделана своим `src/lib/xlsx-writer.ts:1-13`), `playwright` в `src/**` **не импортируется** (только devDependency и `playwright*.config.ts`) — обе библиотеки в серверные чанки не попадают.
- Замороженные области (операторские экраны, ORION) не смотрел, кроме попутного графа; из клиентских тяжёлых там только `framer-motion`.

## Методика

Повторяется с нуля, скрипты лежали вне репозитория (скретч-каталог), в репо ничего не писалось.

1. `node r77-graph.cjs` — обход импорт-графа: регулярка по `import ... from '…'`, `export … from`, `require(…)` (статика) и `(await) import('…')` (динамика), с нормализацией `@/` и относительных путей и с **отбрасыванием `import type`** (без этого шага скрипт давал ложные «серверные библиотеки в клиенте»: `src/components/piling/operator-v2/operator-shift-v2.tsx:49` — `import type { OperatorShiftFacts }`). Обход — только по статическим рёбрам (динамический `import()` считается стоп-ребром), точки входа: все `src/app/api/**/route.ts` (141) и отдельно все тест-файлы (274), и отдельно все файлы с `'use client'` (для вопроса о клиентском бандле).
2. `node r77-closure.cjs <файл>` — размер замыкания конкретного модуля в файлах (`s3-service` — 1, `media-service` — 8, `pdf-queue` — 15, `api-wrapper` — 16, `pdf/route.ts` — 36, `unified-worker.ts` — 145).
3. `node r77-deplist.cjs` — все прямые зависимости проекта со размером `node_modules` и числом статических импортов в `src/**`: так найдено, что `exceljs` не установлен, а `sharp` не имеет ни одного статического импорта.
4. Замеры стоимости загрузки — `node -e "require(m)"` в отдельном процессе на каждый модуль, 2–3 прогона (тёплый кэш ФС отделён от холодного; первый прогон по каждому модулю был холодным и давал в 10–25 раз больше). Это нижняя оценка: в Next/webpack те же модули грузятся из серверного чанка.
5. Замер времени тестов — `node node_modules/vitest/vitest.mjs run <файл>` по одному файлу, разбор строки `Duration` (доли import/environment/tests). Отдельно — `DEBUG=vite:resolve`, чтобы увидеть, какие модули реально резолвятся в тестовом процессе (этим доказано, что `pdfkit`/`bullmq` в pdf-тестах не грузятся).
6. Правила ленивой загрузки сверены с документацией (context7): динамический `import()` в обработчике — штатный приём Next.js (`docs/01-app/02-guides/lazy-loading.mdx`); `vi.mock` хойстится и перехватывает в том числе динамические импорты (vitest, `vi.md` + `@vitest/mocker` `wrapDynamicImport`).
7. Прочитаны целиком/по местам: `src/lib/pdf-queue.ts`, `src/lib/pdf-generator/{index,render,storage,types}.ts`, `src/core/media/media-service.ts`, `src/core/storage/s3-service.ts`, `src/core/observability/s3-health-check.ts`, `src/core/api-wrapper.ts`, `src/app/api/reports/{pdf,single-pdf}/route.ts`, `src/app/api/media/**` (кроме замороженных), `src/workers/unified-worker{,.js}.ts`, `src/workers/unified-worker/{config,pdf}.ts`, `src/workers/embedded-workers.ts`, `src/lib/{rate-limiter,redis-cache,db}.ts`, `src/services/auth/session-service.ts`, `next.config.ts`.

### Риски ленивого импорта (отдельно, как просила задача)

1. **Импорт внутри транзакции.** Ни одна из найденных точек сейчас не находится внутри транзакции: `$transaction` встречается в `src/app/api/reports/delete/route.ts:73`, `src/core/outbox/dead-letter-queue.ts:115`, `src/core/security/identity-role.ts:61`, `src/core/security/tenant-enforcement.ts:283` — под pdfkit/bullmq/S3/sharp там ничего нет (в delete-транзакции — снимок, удаление и outbox-событие). Но правило на будущее: лимит транзакции — 10 с (`src/lib/db.ts:54-58`, `timeout: 10000`), и **первый** `await import()` тяжёлого модуля внутри колбэка съест часть этого бюджета (на холодном кэше ФС `bullmq` — до 3,1 с). Выносить импорт до `$transaction`.
2. **Побочные эффекты на импорте модуля.** Безопасны: `pdf-queue.ts` (клиент Redis — в `createRedisConnection()` `:58-74`, очередь — в `getQueue()` `:87`), `pdf-generator/render.ts` (работа только в `renderPdf`), `s3-service.ts:22`, `s3-health-check.ts:13`, `media-service.ts:89` (`new S3Client` — в конструкторе, то есть при первом `getMediaService()` `:499`). Требуют осторожности: `rate-limiter.ts:462` (+`setInterval` `:114`) и `session-service.ts:169` — там объекты создаются на импорте модуля, ленивый импорт сместит момент создания клиента/таймера.
3. **Моки и `vi.resetModules()` в тестах.** `vi.mock` в vitest хойстится и применяется к динамическим импортам (`@vitest/mocker` оборачивает `import()` в `wrapDynamicImport`), поэтому существующие моки `@/lib/pdf-queue`, `@/lib/pdf-generator`, `@aws-sdk/client-s3`, `sharp` продолжат работать. Опасны файлы с `vi.resetModules()`: `src/workers/__tests__/unified-worker.test.ts:174` и `src/workers/__tests__/pdf-worker.test.ts:79,119` — после сброса реестра каждый импорт даёт новый экземпляр модуля; если `workerStates` (`src/workers/unified-worker/state.ts:15`) начнёт попадать в код двумя разными путями (статическим в тесте и динамическим в коде), возможны два разных объекта состояния. Проверять именно там.
4. **Что ленивый импорт не даёт.** Ноль выигрыша на горячем пути, где ветка берётся всегда (например S3 в `media/[id]/download`): код остаётся в серверном чанке, меняется лишь момент его загрузки. И в проде без `serverExternalPackages` в `next.config.ts` (ключа там нет) все эти пакеты **бандлятся webpack'ом**, а не берутся `require`-ом из `node_modules` — поэтому выигрыш измерен в мс загрузки модуля, но реальный cold start зависит ещё и от компиляции чанка (не замерял, см. «Не проверено»).
