# R63 — какие таблицы растут без предела и чистит ли их кто-нибудь

Ветка `hermes/q4-0926`, worktree `D:\PillingR\wt-night`. Задача read-only: ни один существующий файл не изменён, создан только этот отчёт. Замороженные зоны (варианты экрана оператора, ORION) не правились; там, где таблица пишется только из замороженного модуля, это указано явно.

Профиль для оценки роста (из задачи): 1 организация, 10–20 машинистов, ~10 отчётов/сутки.

## Итог

Счёт по важности: **критично — 3, важно — 9, мелочь — 6** (всего 18).

1. В проекте **нет ни одной задачи очистки таблиц**. Единственный периодический «уборщик» в репозитории — ротация файлов бэкапа (`scripts/backup-postgres.sh:59`, 30 суток) и TTL-ключи Redis; всё, что пишется в Postgres, живёт вечно. Поиск `deleteMany` по `src/` даёт 15 совпадений, и ни одно не относится к журналам/служебным таблицам (полный список — в «Методике»).
2. `OutboxEvent` — таблица transactional outbox: строки **только помечаются** `published`/`projected` (`outbox-publisher.ts:198,213`, `event-handlers.ts:623`), но никогда не удаляются. Событие пишется на каждую сваю/бурение/простой каждого отчёта (`report.aggregate.ts:185,207,241`) — при 10 отчётах и ~30 сваях это порядка **100–350 строк в сутки и 40–130 тыс. строк в год**, и по этой таблице каждые 2–10 секунд ходят оба воркера.
3. `FeedbackEvent` (лента аудита, её читает `/admin`) — растёт и в числе строк, и в размере: на каждое сохранение отчёта в `metadata` кладётся **полное состояние отчёта до и после плюс diff** (`report-command.service.ts:334` → `audit-service.ts:81-96`), то есть десятки килобайт JSON на строку. Ни одна строка отсюда никогда не удаляется.
4. `IdempotencyKey` — TTL задуман (7 суток, `idempotency.ts:5,73`), но единственная функция очистки `cleanupExpiredKeys` (`idempotency.ts:187`) **не вызывается ниоткуда** (единственная ссылка — реэкспорт `core/security/index.ts:35`). Таблица растёт вечно, хотя 7-дневный срок давно прошёл.
5. Топ-5 по риску: (1) `OutboxEvent` без удаления, (2) `FeedbackEvent` с полным состоянием отчёта в metadata, (3) `IdempotencyKey` с мёртвой очисткой, (4) `ReportVersion`/`ReportAudit` — по полному JSON-снимку на каждое сохранение и **без FK на `Report`**, поэтому строки остаются сиротами после удаления отчёта, (5) `Media`: строки `pending`/`failed` и осиротевшие объекты S3 не убирает никто (`runRetention` не вызывается — это уже отмечалось в `39-destructive-ops.md` #13).

## Методика

Что смотрел и как это повторить:

- Полный список моделей схемы: `search_files pattern='^model '` по `prisma/schema.prisma` → 83 модели; отдельно перечитаны разделы «журналов» (2569 `AuditLog`, 2520 `FeedbackEvent`, 2548 `FeedbackEventRead`, 2058 `OutboxEvent`, 2819 `DeadLetterQueue`, 2628 `IdempotencyKey`, 2716 `Media`, 2034 `TelemetryRecord`, 1993 `ReportVersion`, 2010 `ReportAudit`, 2749 `ConflictAudit`, 2777 `ReportPhoto`, 2658 `DeviceSyncState`, 2690/2699 offline-таблицы, 2856 `OrionLead`, 973 `ReadinessScoreSnapshot`).
- Кто пишет: `grep -rn "<model>\.create|\.update|\.upsert"` по `src/` с исключением `src/generated`, `__tests__`, `*.test.*`; для каждой находки открыт сам файл и прочитан контекст вызова (частота: на действие, на событие, по расписанию).
- Есть ли удаление: `grep -rn "deleteMany"` по `src/`, `e2e/`, `scripts/` (исключая `src/generated`) — 15 совпадений: `readiness/place-presets/route.ts:77`, `reports/delete/route.ts:165` (ReportAnalytics), `core/security/idempotency.ts:188`, `crews/…/crew-command.service.ts:307`, `inspections/…/inspection-commands.ts:294`, `layout/…/layout-service.ts:106`, `reports/…/rebuild.ts:80,164`, `reports/…/report.repository.ts:165`, `safety/…/equipment-permits.ts:179`, `sites/…/site-admin-command.service.ts:192,193,336`, `services/reports/event-handlers.ts:194` (SiteDailySummary), `scripts/smoke-auth-access.js:180`. **Ни одного по `OutboxEvent`, `FeedbackEvent`, `AuditLog`, `DeadLetterQueue`, `IdempotencyKey`, `Media`, `TelemetryRecord`, `ReportVersion`, `ReportAudit`, `ReadinessScoreSnapshot`.**
- Есть ли TTL/архивация/расписание: `grep -rni "prune|cleanup|retention|purge|ttl|archive"` по `src/` (совпадения — только кэши Redis и `media-service.runRetention`, см. находку 9) и `grep "setInterval"` по `src/workers/**` (задачи-уборщика нет). Сверено с аудитом R59 (`docs/audits/hermes-night/R59-scheduled-jobs.md`): в проекте нет ни `node-cron`, ни crontab; systemd-таймеры (`deploy/systemd/`) — только бэкапы и disk-guard, ни один не чистит таблицы.
- Индексы под очистку проверены по `@@index` каждой модели (указаны в таблице ниже).
- Размер строк оценён по структуре пишущего кода (какие поля кладутся); фактических замеров `pg_total_relation_size` не делал — прод недоступен, поэтому где размер не вычисляется по коду, стоит «не оценено».
- Массовое подтверждение «никто не удаляет»: `grep -rn "cleanupExpiredKeys|runRetention|deletePdfResult|hardDelete"` по `src/`, `scripts/`, `e2e/`.

## Топ-5

1. **`OutboxEvent` не удаляется вообще** (#1). Строки только получают флаги `published`/`projected`; событие на каждую сваю/бурение/простой каждого отчёта — 100–350 строк/сутки, 40–130 тыс./год. Оба воркера сканируют эту таблицу каждые 2–10 секунд.
2. **`FeedbackEvent` — самый крупный журнал** (#2): на каждое сохранение отчёта в `metadata` кладутся `oldData`+`newData`+`diff` (полное состояние отчёта), строка — десятки килобайт, и это то, что читает лента `/admin`.
3. **`IdempotencyKey` с мёртвой очисткой** (#3): TTL 7 суток записывается, но `cleanupExpiredKeys` не вызывается ниоткуда — ключи копятся вечно.
4. **`ReportVersion` и `ReportAudit` без связи с `Report`** (#5, #6): полный JSON-снимок на каждое сохранение отчёта, а после удаления отчёта строки остаются сиротами навсегда.
5. **`Media`: `pending`/`failed` и осиротевшие файлы** (#9, #10): брошенные загрузки и PDF-файлы не убирает никто — `runRetention` и `deletePdfResult` существуют, но не вызываются.

## Не проверено

- **Фактические размеры и число строк.** `pg_total_relation_size`, `count(*)` по таблицам и реальное число событий на одно сохранение отчёта не измерялись: прод недоступен (AGENTS.md запрещает продакшн), локальная БД с боевыми данными не поднималась. Все числа роста — оценка по коду (профиль из задачи), а не замер; размер строк `FeedbackEvent`/`ReportVersion`/`ReadinessScoreSnapshot` оценён по структуре записываемых полей.
- **Выполнено ли партиционирование на боевой БД.** Скрипт в репозитории есть, но запускался ли он на сервере, из этого окружения не видно; в `prisma/migrations` упоминаний `PARTITION`/`pg_cron` нет (проверено поиском).
- **Работают ли реально задачи, которые могли бы чистить.** Прогонов `cleanupExpiredKeys`/`runRetention` не наблюдал; вывод «не вызывается» сделан текстовым поиском по репозиторию, а не по работающему процессу. Косвенно это уже подтверждено аудитом `39-destructive-ops.md` #13 про `runRetention`.
- **S3 lifecycle и ретеншн бакета.** Правила жизни объектов в бакете (если они есть) не проверял: утверждения про PDF-файлы и медиа сформулированы как «в репозитории очистки нет».
- **Сколько фото приходит на один отчёт** (объём `Media` и объектов в бакете) — не измерено, поэтому для `Media` стоит «не оценено».
- **Ретеншн по юридическим требованиям.** Требуемые сроки хранения аудита/медиа/персональных данных (для пунктов 4, 8, 16) в репозитории не найдены; политику хранения определяет владелец, поэтому все предложенные фиксы сформулированы как кандидаты с условием, а не как «сделать сразу».
