# 52 — План-факт и период на дашборде диспетчера: % считается от периода, план — от всего объекта

Файл отчёта: `docs/audits/hermes-night/52-plan-progress-period.md`
Ветка: `hermes/q4-0926`. Задача — только исследование, код не менялся.

## Итог

- Ответ на главный вопрос: **да**. При периоде «7 дней» (и тем более «Сегодня» / «Период»)
  процент на плитках и полосах считается как **(факт за выбранные N дней) / (план на весь объект)**.
  План никогда не режется по периоду — это заложено в `site-analytics-service.ts`.
- Это **не то, что ожидает руководитель**: «40%» в режиме «7 дней» читается как
  «объект выполнен на 40%», а на деле это «за неделю сделан объём, равный 40% всего плана объекта».
- Хуже того, эффект **асимметричен**: за короткий период фактический объём всегда меньше всего плана,
  поэтому переключение в «7 дней»/«Сегодня» **понижает** прогресс почти любого объекта и **плодит ложные
  тревоги «отставание плана»** — даже для уже завершённых объектов.
- Затронуты: KPI-плитка «Сваи» (полоса), KPI-плитка «Бурение» (полоса), обе полосы в `PlanTile`,
  риск «отставание плана» и сортировка списка «План-факт по объектам» (сверху всплывают не отстающие, а
  короткопериодные нули).
- Правильное поведение: **% всегда накопительный (с начала объекта)**, а период влияет ТОЛЬКО на
  числа «за период» (шт/м.п./м/простой). План — это цель объекта целиком, дробить её по календарю нечем
  (в данных нет графика производства по дням).
- Всего находок: **критично — 0, важно — 4, мелочь — 4** (итого 8).

Топ-5:
1. (важно) `pileProgress`/`drillingProgress` = факт периода / весь план — `site-analytics-service.ts:165-170`.
2. (важно) KPI-плитки «Сваи»/«Бурение» пересчитывают тот же смешанный % — `admin-dashboard.tsx:270-271`.
3. (важно) Риск «отставание плана» срабатывает по смешанному `pileProgress` — `admin-dashboard.tsx:226-228`.
4. (важно) Сортировка и топ-4 «План-факт по объектам» опираются на смешанный `pileProgress` — `admin-dashboard.tsx:196,268`.
5. (мелочь) Факт за период и план за весь объект стоят в одной строке плитки без пометки «за период» — `admin-dashboard.tsx:310-311`.

### Конкретные числа (дефолт vs «7 дней»)

Допущения для примера (иллюстрация, не данные прода — см. «Не проверено»): один объект «Объект А»,
план `plannedPiles = 1000` шт, `plannedPileMeters = 5000` м.п. Всё время сделано `950` шт / `4750` м.п.,
за последние 7 дней — `20` шт / `100` м.п.

Дефолт «Весь период» (`dateFrom=''`, `dateTo=''` → сервер: `0000-01-01 … 9999-12-31`):
- KPI «Сваи»: value `950 шт / 4 750 м.п.`, sub `план 1 000 шт / 5 000 м.п.`,
  полоса `= 4750/5000 = 95%`.
- `PlanTile` «Сваи»: value `950 шт / 4 750 м.п.`, полоса `= pileProgress = 950/1000 = 95%`.
- Риск «отставание плана»: `95 < 50` ложно → тревоги нет. Всё согласовано.

Переключаем на «7 дней» (`dateFrom = сегодня−6`, `dateTo = сегодня`):
- KPI «Сваи»: value `20 шт / 100 м.п.`, sub по-прежнему `план 1 000 шт / 5 000 м.п.` (весь объект!),
  полоса `= 100/5000 = 2%` (было 95%).
- `PlanTile` «Сваи»: value `20 шт / 100 м.п.`, заголовок «Сваи · план 1 000 шт», полоса `= 20/1000 = 2%`.
- Риск: `2 < 50` → появляется «Объект А — отставание плана», hint «2% свай» —
  `admin-dashboard.tsx:226-228`. Объект фактически готов на 95%, но во вкладке «7 дней» он — «отстающий».
- Дополнительно: объект с `pileProgress = 2` встаёт в начало списка «План-факт по объектам» (сортировка по
  возрастанию `pileProgress`, `admin-dashboard.tsx:196`) и попадает в топ-4 `planRows`
  (`admin-dashboard.tsx:268`) — то есть в режиме «7 дней» панель сверху показывает самые «нулевые» объекты.
- Крайний случай: объект с планом, выполненный полностью (100%), но без отчётов за последние 7 дней
  (пауза/межсезонье) → `pileProgress = 0/1000 = 0%` → «отставание плана» с «0% свай» и первое место в списке.

То же для «Бурения» (полоса `drillingProgress`) и для режима «Сегодня» (там факт за один день против всего
плана — процент ещё ближе к нулю, ложных «отставаний» ещё больше).

Проверка, что план не режется: `site-analytics-service.ts:75-78` (план из `Site`) и `:86-104`
(подзапросы `pp`/`dp` без `WHERE … r.date`). В режущихся блоках `:105-138` во всех четырёх подзапросах стоит
`WHERE r.date >= ${dateFrom} AND r.date <= ${dateTo}`.

## Предлагаемое поведение и точная правка (код НЕ менялся)

Наименее удивляющее поведение: **процент выполнения всегда накопительный (с начала объекта)**;
переключатель периода влияет ТОЛЬКО на числа «за период» — факт свай/бурения (шт, м.п., м), простой, число
отчётов, состав объектов. План — это цель объекта целиком, и «% плана» по определению накопительный.

Почему не «дробить план по периоду»: у планов нет разбивки по календарю — `SitePilePlan`/`SiteDrillingPlan`
хранят только `count` на объект (`site-analytics-service.ts:86-104`), графика производства по дням в схеме нет.
Распределять план равномерно по дням — это уже выдумывание нормы, которого в данных нет.

Точная правка (предложение, не применять):

1. `src/services/analytics/site-analytics-service.ts`
   - Оставить периодные подзапросы `p`/`d` (`:111-131`) как есть — они дают факт «за период».
   - Добавить парные «безусловные» подзапросы (тот же SQL без `WHERE r.date …`) — например
     `p_all`/`d_all` — и новые столбцы `actualPilesAllTime`, `actualPileMetersAllTime`,
     `actualDrillingAllTime` (сумма по всем `submitted`-отчётам объекта).
   - Считать прогресс от накопительных полей:
     `pileProgress = row.plannedPiles > 0 ? Math.min(100, (row.actualPilesAllTime / row.plannedPiles) * 100) : 0;`
     `drillingProgress = row.plannedDrilling > 0 ? Math.min(100, (row.actualDrillingAllTime / row.plannedDrilling) * 100) : 0;`
     (заменяет `:165-170`).
2. `src/lib/types.ts:352` — расширить `SiteAnalyticsDTO` полями `actualPilesAllTime` /
   `actualPileMetersAllTime` / `actualDrillingAllTime` (их нет в DTO сейчас — прогресс считался на сервере).
3. `src/components/piling/dashboard-kpis.ts:89-134` — суммировать новые `*AllTime` поля в отдельные KPI
   (`actualPileMetersAllTime`, `actualDrillingAllTime`).
4. `src/components/piling/admin-dashboard.tsx`
   - `:270-271` — считать `pileProgress`/`drillingProgress` от накопительных сумм:
     `kpis.actualPileMetersAllTime / kpis.plannedPileMeters`, `kpis.actualDrillingAllTime / kpis.plannedDrilling`.
   - `:226-228` и `:196` — риск «отставание плана» и сортировку «План-факт» вести по накопительному
     `a.pileProgress` (он уже накопительный после п.1 — менять нечего, если сервис отдаёт правильный процент).
   - Плитки `:310-311` — по желанию пометить периодные числа «за период» (находка №5).
5. `src/components/piling/admin-sites/*` — не трогается: страница вызывает сервис без периода
   (`use-sites-overview.ts:64`), там `pileProgress` и так накопительный.
