## Итог

- Находок 14: **критично — 3**, **важно — 7**, **мелочь — 4**. Трасса по шагам для трёх случаев — в разделе «Трасса по случаям».
- Поправка к постановке задачи (проверено): отдельного «онлайнового пути мимо очереди» в коде **нет**. `sendCommand` кладёт команду в очередь **всегда** (`api.ts:157`), и только потом шлёт. Разница между «онлайн» и «офлайн» — не в пути, а в том, кто разбирает отказ: inline-отправка при `permanent` **удаляет** запись (`api.ts:173-176`), а слив очереди при том же самом отказе **оставляет** её как `FAILED` (`offline-queue.ts:350-357`). Один и тот же ответ сервера даёт противоположный итог для данных — это и есть корень находки.
- **Вердикт по (1) онлайн-отправке: теряются.** Запись снимается с устройства, карточки «что введено» не остаётся, а строка состояния в тот же момент пишет «Синхронизировано · Сервер доступен · на устройстве нет очереди» (`operator-status-strip.tsx:36-37`) — то есть прямое утверждение, что всё ушло, при том что сервер запись отклонил.
- **Вердикт по (2) отправке из очереди: не теряются.** `FAILED` остаётся в очереди с `lastError`, видна плашкой с составом записи («Введено: сваи: 12 шт», `offline-queue-banner.tsx:88`), убрать её можно только подтверждением человека (`offline-queue.ts:308-311`, `offline-queue-banner.tsx:92-103`).
- **Вердикт по (4): да, может — и в двух формах.** Полностью молчаливая потеря возможна (сценарий A ниже: смену закрыли в другой вкладке → 409 → запись снята → `reload` переводит фазу в `CLOSED` → `ClosedScreen` не принимает `error`, `operator-mobile-app.tsx:562-563`, `closing-screen.tsx:164`). Частая потеря числа — не молчаливая, но текст отказа не про потерю: он висит ниже списка записей, а само число живёт только в состоянии формы и стирается одним переходом (`work-screen.tsx:86-94,168,219`).
- Класс подтверждён кодом, но не воспроизведён на устройстве (браузер/сервер не поднимались) — см. «Не проверено».

## Трасса по случаям

### (1) Онлайн-отправка сразу

Постановка «не через очередь» неверна: очередь задействуется всегда.

1. `work-screen.tsx:144-155` — `submit()` собирает `entry` из полей формы и зовёт `onLog(entry)`; `:155-156` — форма чистится **только** если `onLog` вернул `true`.
2. `operator-mobile-app.tsx:525-530` — `onLog` = `run(() => sendCommand({command:'log-production', clientCommandId: productionCommandId, shiftId, entry}))`.
3. `api.ts:143-146` — `log-production` входит в `QUEUEABLE` (`offline-queue.ts:67-69`), значит `isQueueable` = true, идём дальше `:156`.
4. `api.ts:157` — `enqueue(command)`: запись уже лежит в `localStorage` и уже видна баннеру. **Это и есть «онлайн-путь» — он начинается с очереди.**
5. `api.ts:168` — `postCommand` → сервер отвечает 400/403/404/409 → `parse` бросает `ApiError(status, payload.error)` (`api.ts:33-35`).
6. `api.ts:172` — `classifyFailure(409)` (`offline-queue.ts:139-144`): 409 не 401, 400≤409<500, не 408/425/429 → **`permanent`**.
7. `api.ts:173-176` — `resolve(clientCommandId)` **удаляет запись из очереди**, затем `throw error`. Текста пользователю здесь не формируется — наружу уходит исходный `ApiError`.
8. `operator-mobile-app.tsx:210` — `setActionError(error.message)`; `:220` — если это 409, запускается `void reload()`; `:221` — `run` возвращает `false`.
9. `work-screen.tsx:155-156` — `recorded === false` → `return` **до** очистки полей. Введённые цифры остаются в состоянии `WorkScreen` (шаг 2 формы жив).
10. `work-screen.tsx:405,407` — `EntriesList`, ниже него `ErrorNote` (это единственное место, где на рабочем экране виден текст отказа). Текст есть в DOM (`role="alert"`, `ui.tsx:303-310`), но ниже списка записей.
11. `operator-status-strip.tsx:9-10,27-39` — очередь пуста (шаг 7), `online` = `navigator.onLine` = true → рисуется ветка «хорошо»: **«Синхронизировано · Сервер доступен · на устройстве нет очереди»**. Причина ровно та же, что в R76 №19: слово «Синхронизировано» выводится из «очередь пуста», а очередь пуста потому, что запись только что удалили.

Что именно делает 4xx по `log-production`: 400 — `production.ts:254,286,297,311,385-386,406,413,416,432,459`, `shared.ts:111`; 403 — `shared.ts:38,71`, `route.ts:187-190`, CSRF (`api-wrapper`/`csrf-protection`); 404 — `shared.ts:61`; 409 — `shared.ts:63,289-295`, `production.ts:148-154,190-195,216-220`. Все они дают один и тот же итог шагов 6-7.

### (2) Отправка из офлайн-очереди

1. Путь записи в очередь: машинист ввёл 12 свай → `api.ts:157` `enqueue` → `api.ts:168` запрос падает по сети → `api.ts:172` `classifyFailure(null)` = `temporary` → `:177-179` `markAttempt(id, msg, false)` (состояние `PENDING`) → `throw QueuedOffline` → `operator-mobile-app.tsx:201-208` трактует это как успех и возвращает `true` → `work-screen.tsx:158-162` **чистит форму**. Здесь очистка безопасна: запись лежит на устройстве и показана плашкой (`offline-queue-banner.tsx:56-61`).
2. Позже `use-offline-queue.ts:30-38,46-63` (запуск, `online`, `visibilitychange`, таймер 30 с) вызывает `flushQueue(sendQueuedCommand)` → `offline-queue.ts:340-359`.
3. `offline-queue.ts:344-346` — `FAILED` пропускаются; берётся `PENDING`.
4. `:347-349` — `await send(item.command)`: `sendQueuedCommand` = `postCommand` без повторной постановки (`api.ts:129-131`). Сервер отвечает 4xx → `ApiError`.
5. `:350-357` — `catch`: `classifyFailure(status)` = `permanent` → `markAttempt(id, msg, true)` → состояние **`FAILED`**, `lastError` = текст сервера. **`resolve` не вызывается — запись остаётся.**
6. `offline-queue.ts:281-283` — удалить её автоматически нечем; удаление только через `discard` (`:308-311`) и только для `FAILED`, по кнопке с подтверждением (`offline-queue-banner.tsx:92-117`).
7. **Вердикт: запись становится `FAILED`, а не удаляется.** То же подтверждает тест `offline-queue.test.ts:67-80` и `:109-117`.
