## Итог

Найдено **16 точек**, из них **2 критично**, **8 важно**, **6 мелочь**.

Контур удаления в проекте в основном сделан правильно: у бригад (`deleteCrew`) и шаблонов чек-листов (`deleteTemplate`) «удаление» на деле — мягкая деактивация с записью в журнал (`crew-command.service.ts:340-370`, `template-commands.ts:70-75`); удаление пользователя, объекта, вида документа, канала Telegram и строки допуска к технике снабжены проверкой зависимостей и следом в аудите. Все находки — там, где этого образца **нет**: иерархия объекта (пикет/куст/поле) и установка.

1. **критично** — удаление пикета/куста/поля объекта (`site-admin-command.service.ts:390-419`) не проверяет зависимые строки: пикет удаляется каскадом дочерних узлов, а у выработки (`PileWork.picketId`, `LeaderDrilling.picketId` — `ON DELETE SET NULL`, `prisma/migrations/20260419190903_init/migration.sql:1156,1165`) молча обнуляется привязка к месту забивки. Удаление — в один клик с иконки-корзины **без подтверждения** (`hierarchy-tree.tsx:46-53,74-81,97-104` через `use-site-mutations.ts:252-269`) и **без записи в аудит**. Рабочие строки задним числом теряют место работ.
2. **критично** — удаление установки (`equipment-command.service.ts:35-46`) каскадом сносит её осмотры ЕО/ТО со всеми ответами, историю наработки, наряды ТО, топливный журнал, регламенты и документы (`ON DELETE CASCADE`), а у отчётов **обнуляет `equipmentId`** (`ON DELETE SET NULL`). Единственная проверка — «нет активных бригад» (`:41-43`), след в журнал не пишется. Опасность снижена лишь тем, что кнопка удаления в интерфейсе не подключена (диалог `DeleteEquipmentDialog` не импортируется нигде), но сам маршрут `DELETE /api/equipment/[id]` живой и защищён только правом `equipment.manage`.
3. **важно** — удаления записи топлива (`fuel-log.ts:147`), регламента ТО (`maintenance-plan.ts:113`), документа установки (`equipment-document.ts:92`) и показания моточасов (`meter-reading.ts:238`) не оставляют следа в журнале аудита, в отличие от всех «хороших» примеров выше.
4. **важно** — удаление канала Telegram (`admin-telegram.tsx:316` → `telegram/configs/route.ts:131-176`) и строки допуска к технике (`equipment-permit-matrix.tsx:270` → `safety/equipment-permits/[id]/route.ts:13-43`) не спрашивает подтверждения: одно нажатие «Удалить» необратимо убирает строку.
5. **важно** — удаление установки ломается о `RESTRICT`-связи (бригада, дефект, смена, наряд-допуск) сырой ошибкой внешнего ключа: `deleteEquipment` их не проверяет и не перехватывает, наружу уходит 500 вместо понятного отказа.

2. **Действия внешних ключей.** Каждое «каскад/запрет/обнуление» проверял не по догадке, а по SQL миграций: `grep -rn "_fkey" prisma/migrations/*/migration.sql`. 3. **Кто может вызвать.** Для каждого маршрута смотрел `assertCan(...)`/`can(...)` и обёртку (`withMutation`), для каждого сервиса — проверки владельца/арендатора перед удалением.
4. **Аудит и подтверждение.** `rg -n "recordAuditEvent" ` рядом с каждой точкой удаления; `rg -n "confirm\(|ConfirmActionDialog|window.confirm"` по `src/components/**` для поиска кнопки и её подтверждения.
5. **Мягкая альтернатива.** Проверял наличие `isActive`/`deactivate`/`softDelete` у той же сущности (`Equipment.isActive` + `retireEquipment`, `Media.isDeleted` + `softDelete`, `ChecklistTemplate.isActive`, `Crew.isActive`).
