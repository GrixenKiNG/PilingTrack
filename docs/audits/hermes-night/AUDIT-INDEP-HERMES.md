## Резюме для владельца

Проверены права доступа и изоляция организаций на всех 141 маршруте `src/app/api/**`. Картина существенно лучше, чем можно ожидать от продукта в разработке: **все бизнес-маршруты проверяют вход**, тенантная фильтрация в выборках почти всюду строгая (равенство, отказ при пустой организации), запись отчёта идёт одной транзакцией под advisory-замком, у каждой правки есть след. Найденные проблемы — это, в основном, **расхождения между задокументированным правилом и кодом**, а не открытые дыры в одном-тенантном режиме (сейчас прод работает в одном тенанте `orion`).

Критичных дефектов, эксплуатируемых прямо сейчас, в проверенном объёме не подтверждено. Основное, на что стоит смотреть перед SaaS:

1. **Обход правила «организации нет — отказ».** `listReportsForUserScope` не падает при пустом `tenantId`, а просто **не ставит фильтр** — прямое расхождение с жёстким правилом проекта (`src/modules/reports/application/queries/report-query.service.ts:279-283`). Эксплуатация ограничена (выборка по своему `userId`), но правило нарушено.
2. **Режим «Действую как» не доходит до части проверок.** Ряд решений о правах и о тенантной фильтрации принимается по **собственной** роли (`user.role`), а не по исполняемой (`resolveEffectiveRole(role, actingAs)`), вопреки инварианту в `authorization-service.ts:141-200`. Это ~9 мест (см. реестр).
3. **Скачивание PDF по `jobId`** теряет проверку владельца, если запись задачи уже вычищена очередью — тогда файл доступен любому с правом `reports.read_cross_user` (`reports/single-pdf/route.ts:190-197`).
4. **ADMIN/DISPATCHER видят медиа и часть данных любых организаций** (`media-auth.ts:193` и др.). Для одного клиента это задумано; для SaaS — утечка между клиентами, которую нужно закрывать до второго тенанта.
5. **Слабый статус доступа у части маршрутов** относительно их назначения (тест Telegram под `reports.read_all`, диагностика системы под `users.manage`).

Осторожный вывод: **как пилот внутри одной компании — допустимо с условиями**; **как основная система одной компании — готовность не подтверждена** (не проверялись основной производственный процесс, сохранность данных, восстановление, нагрузка); **как SaaS для нескольких клиентов — не готово** (изоляция клиентов при привилегированных ролях не выдерживает проверки). Подробнее — в разделе «Вердикты».
