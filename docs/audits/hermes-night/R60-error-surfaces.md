# R60 — Что видит пользователь, когда страница или маршрут падает

Ветка `hermes/q4-0926`, worktree `D:\PillingR\wt-night`, базовый коммит `e1c0bb8a`. Задача read-only: ни один существующий файл не изменён, создан только этот отчёт. Замороженные зоны (варианты экрана оператора, ORION) открывались только на чтение — замечания по ним помечены отдельно.

Повод: ответить на четыре вопроса про каждую поверхность отказа — что человек увидит, утекают ли наружу детали (стек, текст исключения, имена таблиц), уходит ли ошибка в Sentry, и что с этим делать.

## Итог

Границы ошибок в проекте есть ровно один комплект на всё приложение: `src/app/error.tsx`, `src/app/global-error.tsx`, `src/app/not-found.tsx`, `src/app/loading.tsx`. Ни одна группа маршрутов (`admin`, `(auth)/login`, `operator` и его варианты, `orion`, `print`) своих `error.tsx`/`not-found.tsx` не имеет — все наследуют корневые. Текст везде русский, кнопки повтора есть, утечки стека или текста исключения нет ни в одном из них.

Главная брешь не в этих файлах, а рядом: всю аутентифицированную оболочку (`(app)` — и админскую, и операторскую) оборачивает клиентская граница `AppErrorBoundary`, у которой **нет** `onError`. React считает такую ошибку пойманной, Next.js в проде для явных границ только пишет `console.error`, а комментарий в самом файле обещает, что текст «остаётся в консоли/Sentry». В Sentry он не попадает — то есть самый частый сценарий падения экрана для машиниста и админа сейчас не наблюдаем.

Маршруты API: из 141 файла `route.ts` контракт обёртки соблюдён везде — 8 методов (в 7 файлах) идут без `withApi`, и все 8 перечислены с причинами в тесте `api-routes.test.ts`. Необёрнутый маршрут при исключении отдаёт HTTP 500 с **пустым** телом (не русский текст, не «Internal Server Error»): в Sentry он всё равно попадает через `onRequestError`, но пользователю и внешнему вызывающему (Alertmanager, healthcheck) достаётся ответ без объяснения.

Счёт по важности: **критично — 0, важно — 3, мелочь — 11** (всего 14). Утечек, требующих немедленного вмешательства (стек, схема БД, секрет), не найдено.

Топ-5:
1. Падение любого экрана в `(app)` (админ или оператор) показывает `AppErrorBoundary`, а он не отправляет ошибку в Sentry — комментарий `app-error-boundary.tsx:14-15` утверждает обратное (#1).
2. Раздел технической готовности (крупнейшая площадь в приложении) при падении вкладки показывает «Раздел временно недоступен» и пишет только `console.error` — в Sentry ничего (#2).
3. `/api/health` не имеет `try/catch`, а он же — цель `HEALTHCHECK` в Dockerfile: неожиданное исключение даёт 500 и через 3 попытки контейнер помечается `unhealthy` (#3).
4. `print/briefing-journal` и публичный сайт ORION при падении показывают красный экран приложения «Экран не открылся» — печатному документу и внешнему посетителю это не подходит (замороженная зона, только замечание) (#11).
5. Ошибки API с русским `error` иногда уносят пользователю английский внутренний текст: `Site not found`, `Tenant context missing`, `<field> required` (#7).

## Не проверено

- Как поверхности отказа выглядят **в проде под строгой CSP** (`script-src 'nonce-…' 'strict-dynamic'`, `src/proxy.ts:167-169`). Комментарий в прокси (`:161-166`) прямо говорит, что ослабление CSP делалось только для `next dev`, потому что «app/loading.tsx + not-found boundary» грузили чанки без nonce. Проверить это можно только сборкой прод-образа и загрузкой 404/ошибки — сборка требует env и БД, которых в этой задаче нет. Риск: экран 404 или ошибки может остаться без гидратации. Проверка: `npm run build && npx next start`, затем `curl -s http://localhost:3000/нет-такой-страницы | grep -o '<script src="[^"]*"[^>]*>' | grep -vc nonce` (ожидается 0) — см. `next.config.ts:44`.
- Ловится ли **серверная** ошибка вложенной раскладки (например, `(app)/admin/layout.tsx` бросает при недоступной БД) клиентской границей `AppErrorBoundary` или уходит в корневой `error.tsx`. Это зависит от того, как RSC-поток доставляет ошибку в ближайшую границу; без запущенного приложения (нужны env и БД) не проверял. Практический вопрос — попадёт ли такая ошибка в Sentry (корневой `error.tsx` репортит, `AppErrorBoundary` — нет).
- Точное поведение `wget --spider` против `/api/health`, отвечающего 500 (какой код возврата и приводит ли он к `unhealthy` в реальном compose) — выведено из документации wget и логики `HEALTHCHECK`, но на живом контейнере не воспроизводилось.
