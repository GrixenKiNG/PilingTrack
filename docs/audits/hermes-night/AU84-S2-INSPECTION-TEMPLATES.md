## Итог

В PilingTrack два независимых контура осмотров. (1) Журнал ЕО/ТО — шаблоны живут в БД (`ChecklistTemplate`/`ChecklistSection`/`ChecklistItem`), собираются из блоков БАЗА+МОЛОТ+ВРАЩАТЕЛЬ, результат — `Inspection`+`InspectionAnswer` со снимком шаблона. (2) Чек-листы места машиниста — состав лежит в КОДЕ (`checklist-catalog.ts`), результат — `OperatorChecklistExecution`+`OperatorChecklistAnswerRecord`. Версионирования шаблонов в БД нет: «правка» = деактивация старой строки и создание новой, история редакций нигде не хранится.

Найдено 22 позиции: критично — 1, важно — 5, мелочь — 16.

Топ-5:
1. (критично) Ответы 4-статусного контроля `REMARK`/`FAULT` НЕ считаются отрицательными (`defect-rules.ts:45`), поэтому осмотр с неисправностью не заводит дефект и не требует фото неисправности. Задевает штатный пункт сида (`seed.ts:76`, тип `STATUS4`, `photoRequired`).
2. (важно) `startInspection` (legacy) принимает деактивированный шаблон: проверки `isActive` нет, хотя текст ошибки утверждает обратное (`inspection-commands.ts:195`).
3. (важно) Сравнение состояния «до/после смены» не знает значений `REMARK`/`FAULT` (`state-diff.ts:36-41`) — ухудшение вида «OK → FAULT» не попадает в передачу смены.
4. (важно) Два контура осмотров используют разные `sourceKey` дефекта (`defect-rules.ts:88` vs `checklist-run.ts:125`) — одну и ту же неисправность машины можно завести дважды.
5. (важно) Legacy-старт `startInspection` не создаёт наряд ТО (нет `maintenanceRecordId`), в отличие от блочного старта (`inspection-commands.ts:208-215`).

## Резюме для владельца (5 строк)

1. Осмотры ведут две разные подсистемы: механик/офис — по шаблонам из базы, машинист на телефоне — по спискам, зашитым в код; это два независимых мира, и они друг о друге не знают.
2. Шаблоны в базе не версионируются: правка стирает старую версию и создаёт новую, посмотреть историю редакций нельзя; уже начатый осмотр при этом не ломается — он держит собственную копию списка.
3. Главная ошибка: тип «4 статуса» (Исправно/Замечание/Неисправно/Не проверено) реально работает только для первых двух кнопок — «Замечание» и «Неисправно» система не распознаёт ни как неисправность, ни как повод потребовать фото.
4. Из-за этого пункты вида «Наголовник без трещин» (тип «4 статуса», фото обязательно) в действующем шаблоне не заводят дефект и не блокируют осмотр без фото.
5. Остальное — эксплуатационные мелочи (нет лимита истории, нет уникального ключа у ответов, счётчик фото считается вне транзакции); ничего из этого данные не теряет.
