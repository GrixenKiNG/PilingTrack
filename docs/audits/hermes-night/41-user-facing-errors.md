# 41. Тексты ошибок, которые доходят до пользователя: английские, технические, без следующего шага

## Итог

- Всего находок: 36 (критично — 5, важно — 21, мелочь — 10). Это read-only аудит: код не менялся, сервер не поднимался, выводы — по чтению кода и по факту выполнения zod-проб (см. «Методика»).
- Общая картина: серверная часть в основном переведена (модули `equipment`, `crews`, `media`, `safety`, `readiness` уже отвечают по-русски — правки после аудита 27 в части английских `ServiceError` сделаны). Основные дыры теперь на стыке «API → экран» и в общих заглушках обёртки.
- Критично: пользователь застревает без объяснения. Экран входа отдаёт английское «Failed to fetch» / «Validation failed»; оператор при отправке сменного отчёта видит английское «Failed to fetch» или «Report was saved but could not be retrieved» — при том, что отчёт УЖЕ сохранён (человек повторяет отправку); любой 500 превращается в «Internal server error» на десятках экранов.
- Важно: обёртка `withApi` отдаёт четыре английские заглушки (`Internal server error`, `Not found`, `Too many requests`, `Service temporarily unavailable`), а почти все экраны показывают `body.error` дословно (`err instanceof Error ? err.message : …`, ~30 обработчиков). Отдельно: переводчик zod-сообщений `api-error-message.ts` написан под zod v3, а в проекте zod v4 — фактические тексты не совпадают ни с одной парой в таблице (подтверждено пробой node).
- Важно: 38 маршрутов отвечают «Некорректные данные», и `details` с полем до формы не доходят — UI читает только `error`. Человек видит «Некорректные данные» и правит поля наугад (эталон решения уже есть: `api-error-message.ts` и `src/components/piling/to/readiness/api/client.ts`).
- Важно: 44 места отвечают внутренней фразой про организацию («Организация пользователя не определена», «Не задан контекст организации», «Организация не определена») — пользователь не может ни понять, ни исправить.
- Важно: английские тексты остались в модулях `inspections` и `sites`, в `dictionary-service` и `telegram-config-service`, в `lib/auth.ts` и в CSRF-отказе (он показывается тостом на любой мутации).
- Важно: `app-error-boundary.tsx` печатает пользователю сырое `(error as Error).message` в блоке `<details>`, а глобальный сбой отдаёт английскую страницу Next (`global-error.tsx`, файла `src/app/error.tsx` нет).
- Топ-5 по цене: (1) «Failed to fetch» на входе и на отправке отчёта, (2) «Report was saved but could not be retrieved» при успешно сохранённом отчёте, (3) «Internal server error» как заглушка на всех 500, (4) «Некорректные данные» без указания поля, (5) английские тексты zod v4 в форме отчёта оператора.
- Хорошая новость: в проекте есть готовые образцы правильного поведения — `src/lib/api.ts:111-133` (`loadJson`/`loadErrorMessage`), `src/lib/api-error-message.ts`, `src/components/piling/to/readiness/api/client.ts:57-71`. Лечится это не переписыванием текстов, а подключением этих же helpers на мутационных экранах.

## Методика

Всё воспроизводимо; Python в окружении нет, использован node + grep + read_file. Замороженные области (`src/app/orion/**`, `src/app/api/orion/**`, `src/components/orion/**`, `src/app/operator/**`, `src/app/(app)/operator/**`, `src/components/piling/operator*/**`, `src/modules/operator-mobile/**`) исключены, кроме общих компонентов (`report-form/**`, `login-page.tsx`), которые используют и не-операторские экраны.

1. Точка входа — прочитаны целиком: `src/core/api-wrapper.ts`, `src/lib/service-error.ts`, `src/lib/api.ts`, `src/lib/api-error-message.ts`, `src/lib/tenant.ts`, `src/lib/client-feedback.ts`, `src/lib/csrf-protection.ts` (фрагмент), `src/app/api/reports/upsert/route.ts`, `src/app/global-error.tsx`, `src/components/piling/app-error-boundary.tsx`.
2. Инвентаризация «кто бросает какой текст»: скрипт `errscan.cjs` (node) обходил `src/app/api`, `src/modules`, `src/services`, `src/lib`, `src/core`, `src/components/piling` (без `__tests__`, без заморозки), собирал `new ServiceError|Error|ReadinessCommandError|OperatorCommandError('литерал')` и `error: 'литерал'` в ответах, отделяя ASCII-only (304 шт.) от кириллицы; полный вывод — 529 строк. Команда: `node errscan.cjs > errscan.txt`.
3. Проверка фактических текстов валидатора (ключевая находка): `node -e "const {z}=require('zod'); …"` — реальные сообщения установленного zod (package.json:117 `zod ^4.3.6`): `Too small: expected number to be >=0`, `Invalid input: expected string, received undefined`, `Invalid input: expected "A"`. Сверено с таблицей переводов `api-error-message.ts:50-56`.
4. Как UI показывает ошибку: `grep -rn "instanceof Error ? …\.message" src/components/piling` (без `operator`) → ~60 мест; отдельно собраны тосты (`sonner`) и inline-показы (`role="alert"`, `setError(...)`, `setFailed(...)`). Для каждого спорного места читались строки вверх до места, где ошибка возникает (например `use-crews-data.ts:191-212` — `authFetch` без обёртки, значит в `catch` приходит TypeError браузера).
5. Кто рендерит текст сервера дословно: найдены и прочитаны локальные хелперы `extractApiError` (`admin-sites/use-site-mutations.ts:20-28`), `responseError` (`admin-dictionaries.tsx:76-83`), `messageFromBody`/`responseError` (`to/readiness/api/client.ts:51-71`), `commandFailure` (`to/readiness/screens/shared.tsx:262-274`).
6. Группировка дублей: одинаковый текст в разных местах сведён в одну находку со списком `path:line` (например «Не задан контекст организации» — 44 места, «Некорректные данные» — 47 вхождений в 38 файлах).
7. Что НЕ подтверждено динамически, помечено в разделе «Не проверено»: сервер не поднимался, запросы не отправлялись, `tsc/lint/build` не запускались (правок нет, задача read-only).
