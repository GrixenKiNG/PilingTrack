# W4-AUDITLOG-STOPPED — «AuditLog не пополняется с 28.09» (D-20260930-002)

Только чтение. Worktree `D:\PillingR\wt-night`, ветка `hermes/q4-0926`, `HEAD = 6f123dd2`.
Ни один существующий файл не изменён; создан только этот отчёт. Код и воркеры не запускались.
Локальная БД (`pilingtrack-postgres`, БД `pilingtrack_test`) читалась **только SELECT**.
Боевой сервер/боевая БД не трогались (AGENTS.md §1).

## Итог

- **Поломки писателя нет.** В `AuditLog` физически пишет ровно один путь — цепочка техготовности
  (`audit-repository.ts:45`, единственный `.auditLog.create` во всём `src/`). Он не менялся и не
  отключался ни одним коммитом; коммита, «остановившего» запись, не существует.
- **«Тишина с 28.09» объясняется замыслом + отсутствием писателя.** Все прикладные события (вход,
  выход, сдача/правка отчёта, справочники, техника, ТО) пишутся в **другую** таблицу `FeedbackEvent`
  (`audit-service.ts:959`), поэтому в `AuditLog` от входа и сдачи отчёта **не появляется ничего — так и
  должно быть**. Единственный **автоматический** писатель цепочки — планировщик readiness в процессе
  `unified-worker` (`readiness-scheduler.ts` ← `unified-worker.ts:188`); в процессе Next.js его нет
  (`embedded-workers.ts:26` — только `outbox`/`projection`). Пока воркер не запущен, цепочка не растёт.
- **Оценка «не пополняется с 28.09» на момент проверки уже неверна:** после 28.09 в цепочку легли
  звенья `315` (01.10 06:24 UTC) и `316` (01.10 09:22 UTC, `shift.auto-closed`). Тишину 29–30.09
  объясняет не отработавший планировщик: на локальной БД висит смена `STARTED` с 04.10, которую
  планировщик обязан был автозакрыть, но не закрыл (SELECT ниже).
- **«546 строк без occurredAt» — не свежий дефект, а легаси.** Ровно 546 строк не имеют ни `hash`, ни
  `occurredAt`, и **все** они датированы 02.08–20.09 (действия `acting_as_mechanic` 506, `draft_saved`
  31, `published` 9). Это строки, записанные до включения цепочечного писателя на этих путях; новых
  среди них нет. Трактовка «в AuditLog перестали писаться новые строки и 546 без occurredAt» — ошибка
  чтения данных детектором.
- Итог по severity: **критично — 0, важно — 4, мелочь — 2** (всего 6). Отдельно — архитектурный долг
  (ADR-0043 п.1).

Топ-5:

1. **важно** — `AuditLog` пишет **только** цепочка техготовности (`audit-repository.ts:44-45`);
   `recordAuditEvent` пишет в `FeedbackEvent` (`audit-service.ts:954-976`). Детектор QA мерит не тот
   журнал: вход и сдача отчёта в `AuditLog` не попадут никогда (проверка `tasks.md:95` ложна).
2. **важно** — единственный автоматический писатель цепочки — планировщик в `unified-worker`
   (`unified-worker.ts:188`), в процессе Next.js его нет (`embedded-workers.ts:26`). Без
   `npm run worker:all` цепочка не пополняется автоматически ничем.
3. **важно** — 546 строк без `occurredAt` = легаси 02.08–20.09 по трём действиям (506+31+9),
   подтверждено SELECT'ом; не признак сегодняшней поломки.
4. **важно** — ADR-0043 п.1 (`docs/adr/0043-audit-hash-chain.md:13`) объявляет `AuditLog` единственным
   источником аудит-API, а фактически аудит-историю рисует `FeedbackEvent`
   (`audit-history-service.ts:101`). Это расхождение замысла с кодом, а не поломка записи.
5. **мелочь** — комментарий `record-audit.ts:17-18` ссылается на «общий `recordAuditLog` в core», файла
   которого нет с `be261f79` (18.08).

- **Цепочка `orion` цела:** 316 звеньев, голова `TenantAuditChain.orion.lastSequence = 316` = максимум
  `sequence` (SELECT). Звенья после 28.09 есть: `315` (01.10 06:24 UTC) и `316` (01.10 09:22 UTC).
- **Ни один коммит не «останавливал» запись:** `git log -S 'auditLog.create' --all -- src` в сентябре
  даёт только `2af0de08` (26.09) — добавление записи, не удаление; инфраструктура цепи не менялась с
  `be261f79` (18.08). Все коммиты взяты как предки `HEAD` (`git merge-base --is-ancestor` → OK).
- **`FeedbackEvent` живёт и пополняется:** дневные счётчики 27.09…06.10 есть каждый день (например
  30.09 = 124, 05.10 = 90, 06.10 = 135; SELECT) — то есть «пишется только FeedbackEvent» верно, но это
  и есть штатный операционный поток.
- **Находка R87 №2 (requestId/correlationId) закрыта в коде:** `append-audit.ts:46,61` подставляют
  идентификаторы до вычисления хэша (`:73`); коммиты `f5a90d46`/`8c0512a0` — предки `HEAD`. Рантаймом
  (INSERT против CHECK) не перепроверялось — вне рамок этой задачи.

## Вердикт

**«так задумано»** — в части «AuditLog не пополняется».

Поломки писателя нет: в `AuditLog` пишет только цепочка техготовности
(`audit-repository.ts:44-45`), прикладные события идут в `FeedbackEvent` (`audit-service.ts:959`) —
это осознанный (задокументированный в коде и ADR) выбор, а не сломанный путь. Коммита, после которого
запись «прекратилась», **не существует**: единственное сентябрьское изменение писателя —
`2af0de08` (26.09), которое записей **добавило**. Наблюдаемая «тишина» объясняется двумя причинами:
(а) детектор мерит не тот журнал — вход и сдача отчёта в `AuditLog` не пишут и никогда не писали;
(б) единственный автоматический писатель цепи (планировщик readiness) работает только в процессе
`unified-worker`, которого на стенде не было (локально это доказывает неавтозакрытая смена `STARTED`
с 04.10 против последнего звена 01.10).

**«ошибка теста»** — в части «546 строк без occurredAt». Это не свежие строки, а легаси-слой
02.08–20.09 (506+31+9, действия без хэша); они и не должны иметь `occurredAt`. Ожидание «вход + сдача →
`max(sequence)` вырастет» (tasks.md:95) по коду неисполнимо.

**«дефект» — только как архитектурный долг, не как поломка:** ADR-0043 п.1 (`docs/adr/0043-audit-hash-chain.md:13`)
объявляет `AuditLog` единственным источником аудит-API, но код и читатель аудит-истории живут на
`FeedbackEvent` (`audit-history-service.ts:101`). Это расхождение замысла с реализацией — решать
владельцу (довести п.1 до кода или понизить его и поправить детектор QA).
