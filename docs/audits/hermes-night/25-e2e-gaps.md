# E2E-пробелы: какие ключевые сценарии не покрыты ни одним Playwright-тестом

READ-ONLY исследование. Существующие файлы не менялись; создан только этот отчёт.
Все пути в таблицах — реально открытые файлы (чтение или grep с выводом строки).

## Итог

В наборе 12 файлов Playwright: 38 уникальных тестов, `npx playwright test --list` → **114 тестов в 12 файлах** (38 × 3 проекта: chromium, Mobile Safari, Mobile Chrome; проект `unauthenticated` собирает 0).
Из 10 затребованных сценариев **ни одного нет в полноценном виде**: «нет покрытия» — 6 (вход по PIN, операторский цикл смены, корректировка отчёта диспетчером, xlsx-выгрузки, PDF-экспорт, наряд ТО, DLQ-retry, создание пользователя, объект/бригада — см. карту ниже), «есть, но не проверяет главное» — 3 (создание отчёта, осмотр, вход по паролю).
Самое опасное: **весь набор e2e за одну ночь упражняет ровно два пишущих эндпоинта** — `POST /api/auth/login` (6 вызовов) и `POST /api/reports/upsert` (1 вызов, при этом тест принимает ответы `[200,400,403,404,500]`, т.е. зелёный и при 500).
Операторского контура нет вообще — это подтверждено историей: коммит `6f9cc6fd` («Честное состояние — покрытия у оператора сейчас нет») удалил 4 спека `e2e/operator-v3/*.spec.ts` как нерабочие и не заменил их.
Локальный прогон не воспроизводим одной командой: в `playwright.config.ts` нет блока `webServer`, сервер надо поднимать вручную, а `e2e/inspection-to-flow.spec.ts` требует шаблоны, которых `npm run db:seed` не создаёт.
Всего находок: **26** — критично 4, важно 12, мелочь 10. Топ-5 пробелов по риску (деньги/правильность отчёта) — в конце раздела «Находки».

## Методика

1. `npx playwright test --list` (exit 0) → 114 тестов / 12 файлов / по 38 на проект (chromium, Mobile Safari, Mobile Chrome).
2. Прочитаны целиком все спеки `e2e/*.spec.ts` (11 файлов), `e2e/role-audit.spec.js`, а также `playwright.config.ts`, `e2e/README.md`, `e2e/global-setup.ts`, `e2e/page-objects/login.page.ts`, `e2e/fixtures/auth.fixture.ts`, `e2e/fixtures/role-audit.mjs`.
3. Инвентарь переходов: `grep -rhoE "goto\('[^']+'\)" e2e` — какие страницы вообще открываются. Отдельно проверено, что `e2e/comprehensive-test.ts` (единственное место с `goto('/admin/sites'|'/admin/reports'|'/history')`) **не собирается Playwright** (`--list | grep -c comprehensive` = 0).
4. Инвентарь пишущих вызовов: `grep -rnoE "(request|page\.request)\.(post|put|patch|delete)\('[^']+'" e2e/*.spec.ts e2e/*.spec.js` → только `/api/auth/login` (6×) и `/api/reports/upsert` (1×, `report-creation-flow.spec.ts:45`).
5. По каждому сценарию найден его код: UI-страница, обработчик и эндпоинт (`grep` по `authFetch(`/api/...`)`, чтение `src/app/api/**/route.ts`, `src/modules/**`), затем сверка с картой e2e-покрытия.
6. Проверены предпосылки локального запуска: `prisma/seed.ts` (какие пользователи и оборудование), `scripts/seed-checklist-blocks.ts`, `src/lib/pdf-queue.ts` (нужен ли Redis), `src/core/outbox/dead-letter-queue.ts` (откуда берутся записи DLQ).
7. История удалённых тестов: `git log --diff-filter=D --name-only -- e2e/`, `git show 683c0214^:e2e/tests/shift.spec.ts`, `git show 6f9cc6fd --stat`.
8. Часть строк цитируется по выводу `grep -n` (содержимое строки видно), без полного чтения файла — см. «Не проверено».

### Топ-5 пробелов по риску (деньги и правильность отчёта — вперёд)

1. **Операторский цикл смены целиком** (находки 2, 3, 1). Оператор забивает сваи, отмечает простой и отправляет отчёт с телефона; это и есть данные, из которых собирается выручка стройки. Ни один UI-шаг этого цикла не проверяется: `/operator` (`src/app/(app)/operator/page.tsx:22`) не открывает ни единый собранный тест, записи идут в `POST /api/operator/mobile/command` (`src/app/api/operator/mobile/command/route.ts:206-243`), а единственный «отчётный» тест — API-хак с accept-множеством статусов. Пока это не покрыто, любая регрессия операторского экрана или команды `log-production`/`submit-report` уходит в прод незамеченной.
2. **Создание и корректировка суточного отчёта** (находки 4, 3, 1). Диспетчер правит отчёты, и именно правка попадает в историю/аудит; в e2e нет ни одной записи через `/api/reports/admin-upsert` (`src/components/piling/admin-reports/report-form-dialog.tsx:171`) и ни одной правки через форму `/report` (`src/components/piling/report-form/use-report-form.ts:432`). Ошибка в сохранении правки означает тихую порчу отчётности.
3. **Выгрузки xlsx (журнал забивки и сводка отчётов)** (находка 5). Это документ, который подписывают и отдают заказчику (`src/modules/reports/application/queries/pile-passport.service.ts:400`), а в e2e не проверено ни одно скачивание — ни фильтр периода, ни имя файла, ни непустое содержимое. Достаточно одной строки в e2e на `waitForEvent('download')` для журнала (`src/app/api/pile-passports/export/route.ts:25`) и для `?format=xlsx` (`src/app/api/reports/export/route.ts:61`), с проверкой, что размер ответа > 0 и заголовок `Content-Disposition` содержит ожидаемое имя.
4. **PDF-экспорт периода и одиночного отчёта** (находка 6). Печатная форма — то, что уходит в подпись/архив; в e2e нет ни синхронного (`GET /api/reports/pdf?dateFrom&dateTo`), ни одиночного (`src/app/api/reports/single-pdf/route.ts:132`) пути. Минимальный тест: авторизоваться админом, запросить синхронный PDF за короткий период, убедиться в `content-type: application/pdf` и непустом теле (асинхронный BullMQ-путь — вторым шагом, с ожиданием статуса задачи).
5. **Осмотр с дефектом и завершение осмотра** (находка 7, 8). Незакрытый осмотр и незаведённый дефект — это эксплуатационный риск (блокировка пуска и допуска, внеплановый простой), а e2e подтверждает только черновик: завершение осмотра (`src/components/piling/inspections/run-inspection.tsx:200-216`) и правило «ответ "нет" на помеченный пункт заводит дефект» (`src/modules/inspections/application/commands/inspection-commands.ts:323`) не вызываются. Минимальное дополнение к существующему спеку: выбрать пункт, помеченный как дефектный, ответить «нет», завершить осмотр с подписью и проверить, что осмотр `COMPLETED` и дефект появился в списке дефектов.
