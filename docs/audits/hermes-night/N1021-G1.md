# N1021-G1 — валидация тел PUT в пяти маршрутах

Дата: 21.10.2026. Только чтение; единственный изменённый файл — этот отчёт.
Рабочая ветка: `night/glm-1021`.

## Итог

- Проверено 5 маршрутов PUT: `settings`, `layout/[surfaceId]`, `monitoring/template`, `readiness-rules`, `readiness/access-matrix`. По каждому доведено до места, где тело реально проверяется.
- Родовое наблюдение: **ни один из пяти маршрутов не проверяет тело на уровне маршрута** — нет `schema.safeParse`, есть только «JSON разобрался или нет». Вся содержательная валидация живёт в сервисном/доменном слое, и здесь маршруты резко неодинаковы.
- Числа: **критично — 0, важно — 3, мелочь — 7** (10 находок).
- `settings`, `readiness-rules`, `access-matrix` — валидация образцовая: неизвестные ключи отбрасываются, вложенные поля типизируются, массивы фиксированного размера, строки ограничены. «Сломать чтение у других» через них нельзя.
- Топ-5:
  1. (**важно**) Валидатор раскладки возвращает клон входа целиком — неизвестные ключи на любом уровне шаблона сохраняются в JSONB дословно.
  2. (**важно**) `card.background`/`card.borderColor` в том же валидаторе не имеют ограничения длины — неограниченная строка в JSONB, который читает каждый пользователь организации.
  3. (**важно**) `assetId` у блока `image` не проверяется ни на тип, ни на длину — ещё одна неограниченная строка.
  4. (**мелочь**) `entityId` в `/api/layout/[surfaceId]` берётся из query без проверки формата — произвольное число записей `ModuleLayoutTemplate`.
  5. (**мелочь**) Ни один маршрут (и обёртка) не ограничивает размер тела запроса перед `request.json()`.

## Методика

Как проверялось (можно повторить):

1. Прочитан каждый из пяти маршрутов: `src/app/api/settings/route.ts`, `src/app/api/layout/[surfaceId]/route.ts`, `src/app/api/monitoring/template/route.ts`, `src/app/api/readiness-rules/route.ts`, `src/app/api/readiness/access-matrix/route.ts` — фиксация места разбора тела и того, куда оно передаётся далее.
2. Для каждого маршрута открыта цепочка до функции валидации:
   - `settings` → `saveSettings` (`src/modules/settings/application/settings-service.ts`) → `sanitizeSettings` (`src/modules/settings/domain/settings.ts`);
   - `layout` → `saveLayout` (`src/modules/layout/application/layout-service.ts`) → `surface.validate` (`src/modules/layout/domain/surfaces.ts`) → `createTemplateValidator` (`src/modules/layout/domain/layout-template.ts`) и `createPageLayoutValidator` (`src/modules/layout/domain/page-layout-template.ts`);
   - `monitoring/template` → `saveTemplate` (`src/modules/monitoring/application/template-service.ts`) → тот же `saveLayout` (тонкий алиас);
   - `readiness-rules` → `saveReadinessDraft` (`src/modules/readiness/application/readiness-rules-service.ts`) → `sanitizeRuleSet` (`src/modules/readiness/domain/readiness-rules.ts`);
   - `access-matrix` → `saveAccessMatrixDraft` (`src/modules/readiness/application/access-matrix-service.ts`) → `sanitizeAccessMatrix` (`src/modules/readiness/domain/access-matrix.ts`).
3. Проверены общие обёртки: `withApi`/`withMutation` (`src/core/api-wrapper.ts`), `withReadinessCommand` (`src/app/api/readiness/_shared/route-adapter.ts`), `assertRole` (`src/core/security/authorization.ts`) — есть ли в них проверка типа/размера тела.
4. Сверена схема хранения: `prisma/schema.prisma` — столбцы `Json` и `String`, куда попадают проверенные структуры, чтобы оценить, может ли лишнее попасть в базу.
5. По каждому пункту анкеты задания (неизвестные ключи / типы вложенных полей / максимум массивов и строк / попадание лишнего в базу) вывод сделан только по реально прочитанным строкам; остальное отнесено в «Не проверено».

Замороженные зоны (operator screen, ORION) не затрагивались; они здесь и не участвуют — все пять маршрутов обслуживают кабинет администратора.

### Приложение — замечания ниже порога таблицы

- `src/modules/layout/domain/layout-template.ts:148` — лимит 200 блоков есть (это хорошо), но он не компенсирует #1–#3: лимит ограничивает количество блоков, а не суммарный размер шаблона.
- `src/modules/layout/domain/page-layout-template.ts:58–60` — `widget.settings` ограничен 4000 символами через `JSON.stringify(...).length` — по объёму достаточно, но внутренние ключи settings не проверяются по смыслу («validated by the widget itself at render time», строка 23) — рендер-потребители не исследовались (см. «Не проверено»).
- `src/modules/readiness/domain/access-matrix.ts:78–80` — `version` от ввода принимается строкой любой длины, но в `saveAccessMatrixDraft` версия перезаписывается `bumpVersion(state.published.version)` (`access-matrix-service.ts:179`), поэтому неограниченная строка ввода в базу не попадает. Не дефект.
- `src/modules/readiness/domain/readiness-rules.ts:286–292` — то же: версия/отметки времени от ввода отфильтрованы по типу, а в базу из сохранения идут только `criteria`/`blockers` (`readiness-rules-service.ts:115–120`). Не дефект.
- О прочности чтения: `getLayout` на чтении прогоняет сохранённое через `surface.validate` и при провале откатывается к дефолту (`layout-service.ts:45–46, 53`) — испорченная хранением строка не уронит GET; но extra-ключи (см. #1) валидацию проходят и всё же отдаются читателям.

## Не проверено

- Как часто JSONB раскладок читается в UI (сколько GET на экран/на пользователя) — частота чтений экрана мониторинга не измерялась; сценарий «влияет на чтение у других» построен по механике хранения (`prisma/schema.prisma:1557`), а не по замерам.
- Наличие платформенного ограничения размера тела для route handlers Next.js App Router в конфигурации этого приложения (self-host/прокси) — не проверено; вывод #5 сделан по коду обёртки и маршрутов, где лимита нет.
- Потребители `page-layout widget.settings` на рендере (правило «validated by the widget itself» из `page-layout-template.ts:23`) — какие виджеты и как валидируют settings, за рамками задания.
- Поведение `sanitizeSettings` со суррогатными парами/невалидным unicode в строках — не проверено.
- Фактический максимум JSONB-значения в PostgreSQL на стенде (формальный предел — 1 ГБ на значение) — не проверено.
- Клиентский редактор раскладки: не проверено, может ли он сам случайно отправить кучу посторонних ключей из своего состояния; проверялся только серверный приём.
