# AU30-S2 — Справочники и сданные отчёты: что при изменении марки сваи, причины простоя, типа бурения, установки, объекта и пользователя

Ветка: `hermes/q4-0926`

## Итог

- **Критично: 0. Важно: 8. Мелочь: 10.** Всего 18 находок.
- Главное: **отчёт не хранит ни одного снимка имени.** `Report`, `PileWork`, `LeaderDrilling`, `ReportDowntime` держат только внешний ключ (`siteId`, `userId`, `equipmentId`, `pileGradeId`, `typeId`, `reasonId`), а имя и длина подставляются **живьём** из справочника при каждом чтении. Значит любое переименование в справочнике **задним числом** переписывает то, что показывают уже сданные отчёты, журнал забивки, печатные формы и «История отчёта».
- Для марок/причин/типов бурения этот перепис задним числом закрыт запретом (`renameDictionaryItem` отдаёт 409, если элемент используется). Для **объекта, пользователя и установки запрета нет**: переименование объекта/оператора/установки молча меняет исторические отчёты (№1–№3).
- **Длина марки сваи (`PileGrade.lengthMm`) — единственное поле, которое разрешено менять у используемой марки**, и оно пересчитывает погонные метры всех прошлых отчётов, аналитики и печатных форм (№4, по решению владельца — «разрешено с подтверждением»).
- «Вывод установки из эксплуатации» (рекомендованная замена удалению) **убирает её историческую выработку из «Аналитики техники»**, потому что запрос фильтрует `isActive = true` (№5). Объект так себя не ведёт — неактивный объект с отчётами в периоде остаётся (№13).
- Архивация и удаление справочных элементов сделаны безопасно: архивные записи отдаются на чтение (старый отчёт резолвит имя), использование проверяется до удаления, а на уровне БД стоит `Restrict` (№6–№8).

## Не проверено

- **Исполнение в БД не запускалось.** Проверка только по коду и схеме (`prisma/schema.prisma`); рабочая БД и `.env` не читались (запрет AGENTS.md). Реальные `409`/`Cascade`/`Restrict` в живой базе не воспроизводились — выводы основаны на коде-обработчике и объявлениях FK.
