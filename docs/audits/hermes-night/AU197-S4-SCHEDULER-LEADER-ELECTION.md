# AU197-S4-SCHEDULER-LEADER-ELECTION — планировщики: лидер и повторный запуск

Версия (git rev-parse HEAD): `ff18f3e4ec5b3b72da7ae2f65fd759783571ab5a` (ветка `hermes/q4-0926`).

## Итог

Резюме для владельца (5 строк):

1. Два воркера (outbox и projection) защищены выборами лидера на Redis — это сделано аккуратно и покрыто 15 юнит-тестами (121 тест в `src/workers` + leader-election — ПРОЙДЕНО). `ff18f3e4`.
2. Пять суточных/часовых планировщиков лидера НЕ имеют вообще: их единственная защита — «идемпотентность». Реально замок есть только у планировщика ТО (advisory lock), у остальных — нет.
3. Хуже всех: тик техготовности (`src/modules/readiness/application/scheduler.ts`) при двух экземплярах пишет ДУБЛИ записей в журнал и ДУБЛИ событий в outbox (события `ReportSubmitted` → повторные уведомления). Это не гипотеза в коде, а прочитанный факт; достижимость требует второго процесса — ГИПОТЕЗА.
4. Остановка (или падение) контейнера `workers` тихо убивает всю суточную рутину, и `/api/health/deep` замечает это только через TTL пульса — до 3 суток для суточных задач.
5. Находок: важно — 5, мелочь — 7, критично — 0. Ничего из найденного не теряет и не портит данные; самое дорогое — дублирующие уведомления и слепая зона наблюдаемости.

Счёт по важности: критично 0, важно 5, мелочь 7 (всего 12).

Топ-5:
1. readiness-scheduler: аудит и outbox-события пишутся для всех выбранных строк, даже если `updateMany` обновил 0 (защиты от второго экземпляра нет).
2. Планировщики `pm` / `projection-rebuild` / `readiness` / `idempotency-cleanup` / `pdf-cleanup` не имеют ни лидера, ни кросс-процессного замка (единственное исключение — advisory lock в планировщике ТО).
3. Пульс планировщиков: TTL = 3 интервала (у суточных — 3 дня), поэтому остановка планировщиков почти невидима.
4. Нет джиттера у задержек старта (60/90/90/120 с) — два экземпляра стартуют синхронно.
5. Потеря лидерства не обрывает текущий батч outbox, а отправка отчёта в Telegram не идемпотентна — возможен повторный отчёт.
