# T-IDEMP-RLS-CHECK — RLS на пяти таблицах-кандидатах на очистку и таблице `Media`

Проверка только чтением, к коммиту F-IDEMP-CLEANUP (`src/workers/unified-worker/idempotency-cleanup-scheduler.ts`).
Вопрос владельца: что произойдёт, если будущая фоновая уборка пойдёт в `IdempotencyKey`,
`OutboxEvent`, `FeedbackEvent`, `ReportVersion`, `ReportAudit`, `Media` **без контекста организации**.

## Итог

- **критично — 2, важно — 4, мелочь — 3** (всего 9). Ни одна находка не требует правки кода — это карта состояний для будущей уборки.
- **Главное:** три из шести таблиц (`Media`, `ReportVersion`, `ReportAudit`) закрыты строгой политикой fail-closed. Фоновая задача без контекста организации прочитает **ноль строк**: очистка не упадёт, а молча «удалит 0». Это ровно тот сценарий, ради которого писался отчёт.
- Вторая половина: `IdempotencyKey`, `OutboxEvent` и `FeedbackEvent` вне RLS — задача без контекста удалит **все** строки, в том числе всех организаций. На проде сегодня (одна организация `orion`) это правильно; до второй организации — межтенантное удаление.
- Существующий `Media.runRetention()` + `hardDelete()`, если его подключить к воркеру как есть, **сегодня удалит 0** — он ходит в базу без контекста, а политика строгая (`src/core/media/media-service.ts:443`).
- Роль воркеров в репозитории **нефиксированная**: `docker-compose.yml:162` берёт `${APP_DB_USER:-${POSTGRES_USER:-postgres}}`, а шаблоны `.env.*.example` `APP_DB_*` не содержат. По шаблону воркер получит роль-владельца (суперпользователя) и **обойдёт RLS** — тогда строгие таблицы тоже будут удалены целиком.
- `DEFAULT_TENANT_ID`, который есть в окружении воркеров (`docker-compose.yml:186`), в GUC `app.current_tenant` **не попадает** — надеяться на него как на «контекст» нельзя.

### Сводная таблица (ответ на вопрос задачи)

| таблица | RLS | политика (миграция:строка) | роль воркера | фоновое удаление без контекста даст |
|---|---|---|---|---|
| `IdempotencyKey` | **не включён вовсе** (`relrowsecurity=f`) | политики нет; решение оставить вне RLS — `20260819140000_rls_remaining_tenant_tables/migration.sql:20-25`, подтверждено `20260903000000_rls_remaining_tables/migration.sql:200-206` | `pilingtrack_app` (BYPASSRLS=f) — ранбук 011; при пустом `APP_DB_USER` — владелец/суперпользователь | **удалит все строки** (всех организаций). Так и работает F-IDEMP-CLEANUP; на однотенантном проде корректно |
| `OutboxEvent` | **явно выключен**: `ALTER TABLE "OutboxEvent" DISABLE ROW LEVEL SECURITY` | политики нет (карта состояний — `20260702000000_drop_stray_rls_tenant_outbox/migration.sql:11-12`) | то же | **удалит все строки**. Это задумано: воркер публикации разбирает очередь сквозь все организации (`docs/adr/0046-rls-fail-closed.md:90`) |
| `FeedbackEvent` | **не включён** (у таблицы нет колонки `tenantId` вовсе) | политики нет; почему — `20260903000000_rls_remaining_tables/migration.sql:215-219` | то же | **удалит все строки** (лента общая на весь стенд) |
| `ReportVersion` | `ENABLE` + `FORCE` | строгая, через родителя: `EXISTS (SELECT 1 FROM "Report" r WHERE r."reportId" = "ReportVersion"."reportId" AND r."tenantId" = current_setting('app.current_tenant', true))` — `20260903000000_rls_remaining_tables/migration.sql:182-187` | то же | **ноль строк, без ошибки** (`NULL = 'orion'` → NULL → строка не проходит) |
| `ReportAudit` | `ENABLE` + `FORCE` | строгая, тот же шаблон по `ReportAudit"."reportId"` — `20260903000000_rls_remaining_tables/migration.sql:189-194` | то же | **ноль строк, без ошибки** |
| `Media` | `ENABLE` + `FORCE` | строгая: `"tenantId" = current_setting('app.current_tenant', true)` — `20260819120000_rls_fail_closed_all/migration.sql:55,82` (включение — `20260516100000_extend_rls_tenant_scoped/migration.sql:18,29`, FORCE — `20260701020000_force_row_level_security/migration.sql:23`) | то же | **ноль строк, без ошибки**. Существующий `runRetention()` в этой роли сегодня именно так и вернёт 0 |

**Почему «ноль», а не ошибка.** При незаданной переменной `current_setting('app.current_tenant', true)` возвращает `NULL`; сравнение `"tenantId" = NULL` даёт `NULL`, то есть «строка не подходит». Postgres не поднимает ошибку — `DELETE` просто затронет 0 строк. Это записано в теле миграции: `20260819120000_rls_fail_closed_all/migration.sql:13-16`.

**Почему у воркера нет контекста.** GUC доставляется только из `getRequestTenantId()` (`src/core/security/tenant-rls.ts:57-60`), а он читает `AsyncLocalStorage`, который заполняет аутентификация внутри обёртки маршрута; воркеры через обёртки не проходят (`src/core/security/tenant-context.ts:20-21`). `resolveGucTenantId()` вернёт `null` → `set_config` не выполняется вовсе (`src/core/security/tenant-rls.ts:82-100`).

## Не проверено

1. **Фактическое состояние базы не измерялось.** Выводы получены из миграций и кода. `pg_class.relrowsecurity`, `relforcerowsecurity` и список `pg_policies` на живом Postgres не снимались: прод запрещён (AGENTS.md §1), локальная база не поднималась (задача только на чтение). Быстрый способ проверить — `docker exec -i pilingtrack-postgres psql -U postgres -d pilingtrack_test < scripts/rls-state.sql` (`scripts/rls-state.sql:13-16`); отчёт 2 этого скрипта прямо ожидает ровно две таблицы без RLS (`scripts/rls-state.sql:42-46`) — по моим данным их три, потому что `FeedbackEvent` в его список «с tenantId» не попадает (у неё нет колонки).
2. **Реальная роль воркеров на проде не проверена.** `.env` читать запрещено (AGENTS.md §1), поэтому опираюсь на журнал ранбука `docs/runbooks/011-app-db-role.md:305` («13.08.2026 прод переключён», `pilingtrack_app`, `bypassrls=f`) и на то, что в `docker-compose.yml` сама переменная перечислена (`:78`, `:162`) и `DB_IDENTITY_ROLE` тоже (`:107`, `:194`). Если по факту `APP_DB_*` на проде пусты — действует ветка находки №4.
3. **Не читал `docs/runbooks/012-rls-fail-closed.md`** целиком (на него ссылаются миграции и ранбук 011); порядок раскатки роли опознания в отчёте не воспроизводится.
4. **Число строк в таблицах не измерялось** — сколько ключей/событий реально удалит уборка, в репозитории нет; единственные оценки — `docs/proposals/data-retention.md:129-131` (11–18 тыс. строк `IdempotencyKey` в год).
5. **Поведение `runRetention` под ролью-владельцем не проверялось экспериментально** — вывод «ноль строк» следует из того, что `pilingtrack_app` не имеет `BYPASSRLS` (`scripts/app-role-grants.sql:73-74`) и GUC не выставляется. Проверка на копии базы (ранбук 011, этап 1) это закроет.
6. **ERRATUM к списку из задания:** в миграциях пять таблиц описаны как «без RLS» (`IdempotencyKey`, `OutboxEvent`, `ReadinessAccessMatrix`, `ReadinessBackfillProgress`, `TenantAuditChain` — `20260819120000_rls_fail_closed_all/migration.sql:30-35`), но три последние закрыты следующей миграцией `20260819140000_rls_remaining_tenant_tables/migration.sql:35-51`. К шести таблицам задания это отношения не имеет, но при чтении комментария 20260819120000 легко ошибиться.
