# Аудит: надёжность фоновых задач (workers, outbox, pdf-queue, планировщики, durable-алерты)

Дата: 2026-09-25. Ветка `hermes/fixes-0925`, по заданию — только чтение, без правок.

## Итог

Отчёт покрывает 4 подсистемы: outbox-конвейер (src/services/reports/outbox-publisher.ts + core/outbox/dead-letter-queue.ts), PDF-очередь (BullMQ, src/lib/pdf-queue.ts + src/workers/**), суточные/часовые планировщики (PM, readiness, projection-rebuild) и durable-алерты (core/notifications/** + services/notifications/durable-alert-delivery.ts).

Найдено **51** нахождение: **4 критично**, **27 важно**, **20 мелочь**.

Критичное:
1. Telegram-хендлер сданного отчёта (`handleReportSubmittedTelegram`) глотает все ошибки и не пробрасывает их — outbox помечает событие `published=true`, уведомление с PDF теряется навсегда без ретрая и без DLQ.
2. Ретрай из DLQ не восстанавливает `tenantId`: пере-поставленное в outbox event-строке событие остаётся без тенанта, и под fail-closed RLS его доставка уходит в Telegram `DEFAULT_TENANT_ID` (чужая/неверная организация).
3. `retryDlqEntry` и `moveToDlq`+claim не атомарны: краш между записью и подтверждением даёт либо потерю события, либо дубликаты в DLQ.
4. Планировщик PM не имеет защиты от двух воркеров: дедупликация нарядов — check-then-act вне транзакции, при двух репликах `unified-worker` возможны дубликаты PLANNED-нарядов (заявка «идемпотентен, лидер не нужен» не выполняется для конкурирующих процессов).

Топ-5 по значимости для владельца:
1. Потеря Telegram-уведомлений отчёта без следа (не проброс ошибки) — 1), `src/services/reports/event-handlers.ts:371-375`.
2. Ретрай DLQ ломает тенант события — 2), `src/core/outbox/dead-letter-queue.ts:95-105`.
3. Дубликат сообщения при сбое сети Telegram (send внутри транзакции, до commit) — durable-алерт, `src/services/notifications/durable-alert-delivery.ts:14-24` (в коде признано, но не решено).
4. Двойной прогон PM-планировщика при двух воркерах — 4), `src/modules/equipment/application/commands/pm-scheduler.ts:94-133`.
5. Планировщики (PM/readiness/projection-rebuild) не пишут heartbeat и запускаются только в отдельном процессе `unified-worker`: если он не выкачен или лёг, `/api/health` этого не показывает.
