## Итог

- Находок 14: **критично — 0**, **важно — 7**, **мелочь — 7**. Потери данных и дыр в правах нет (действие доступно только `ADMIN`, подтверждение у «Отбросить» есть, защита от двойного клика работает и на клиенте, и на сервере); проблема — в **непрозрачности повтора** и в **молчаливом характере** действий.
- Топ-5:
  1. **Повтор может заново отправить PDF отчёта в Telegram.** Повтор любого события, упавшего у потребителя `published` (в т.ч. самих старых `ReportPdfDeliveryRequested`), заново прогоняет публикацию события, а та снова ставит доставку PDF с **новым** `dedupeKey` (`report-pdf:<новый id>`). Дедуп по исходному событию не срабатывает → компания получает второй PDF. Кнопка «Повтор» при этом **без подтверждения** и без предупреждения (`src/core/outbox/dead-letter-queue.ts:130-144`; `src/services/reports/event-handlers.ts:529-543,611-623`).
  2. **Действия админа нигде не записаны.** Ни `retry`, ни `discard` не пишут аудит (`src/app/api/admin/dlq/route.ts:66-95`), тогда как сопоставимое админское действие — пересборка проекций — пишет `recordAuditEvent('projections.rebuilt', …)` (`src/app/api/admin/projections/rebuild/route.ts:72-80`). Кто и когда «разобрал» очередь — не восстановить.
  3. **«Отправлены повторно» ≠ «доставлено».** Статус `resolved` ставится в момент **постановки в очередь**, а не после успешной обработки (`dead-letter-queue.ts:119-122`; подпись статуса — `src/components/piling/admin-dlq.tsx:47`). Если обработка снова упадёт, создаётся **новая** pending-запись без ссылки на исходную — админ видит «Отправлено повторно», а проблема жива.
  4. **Что сломалось — понять нельзя.** Тип события показан машинным кодом (`ReportSubmitted`, `ReportPdfDeliveryRequested`) без перевода (`admin-dlq.tsx:192`), `aggregateId` — сырой cuid без имени отчёта/объекта (`:198-202`), текст ошибки — сырой технический (часто английский), причём **обрезан в две строки без возможности раскрыть** (`:214`), хотя payload раскрыть можно.
  5. **Повтор события об удалённом объекте ничего не «чинит», но и не зацикливается.** Проекции возвращаются досрочно (нет отчёта → нет `siteId/userId`, `event-handlers.ts:77-82`, `projection-worker.ts:85-89`), PDF-доставка тоже выходит на `null` (`event-handlers.ts:565-569`). Запись помечается `resolved`, но тост «Событие отправлено повторно» обещает больше, чем произошло.
- Защищено (проверено, не находка): право — только `ADMIN` (`authorization-service.ts:133`); чтение/запись идут через `withApi`/`withMutation` (CSRF + rate limit, `api-wrapper.ts:178-222`); захват записи атомарный (`updateMany where status:'pending'`, `dead-letter-queue.ts:119-123`) и кнопки блокируются на время действия (`admin-dlq.tsx:233,243`).

## Ответы на вопросы задания

**1) Что админ видит по каждому событию.** Карточка: тип (`eventType` — машинный код, без русского), статус-бейдж, `попыток: N`, `aggregateId` (cuid), `sourceOutboxId`, даты создания/обновления, текст ошибки (`errorMessage`, обрезан двумя строками) и кнопка «Показать payload» (сырой JSON). Итог: **непонятно**. Нет перевода типа события, нет имени отчёта/объекта/пользователя вместо cid, нет полного текста ошибки (раскрывается payload, но не ошибка), нет подсказки «что именно произойдёт при повторе» (например, «повтор заново отправит PDF отчёта в Telegram»). Evidence: `admin-dlq.tsx:192,196-214,215-225`.

**2) Какие действия и их защита.**
- Действия: «Повтор» (`retry`) и «Отбросить» (`discard`) — только они, `z.enum(['retry','discard'])` (`route.ts:61-64`). Действия показываются лишь для `pending` (`admin-dlq.tsx:227`).
- Права: `dlq.manage` → только `ADMIN` (`authorization-service.ts:133`); в маршруте `assertCan(user!,'dlq.manage')` (`route.ts:21,71`) с учётом режима «действую как» (`authorization-service.ts:159-165`); страница — `requirePageAbility('dlq.manage')` (`layout.tsx:4`).
- Подтверждение: есть только у «Отбросить» (`window.confirm`, `admin-dlq.tsx:88`); у «Повтор» подтверждения нет (`:229-238`).
- Аудит: **отсутствует** для обоих действий (см. находку 2).
- Двойное нажатие: защищено — клиент блокирует кнопку на `actingId` (`:233,243`), сервер атомарно захватывает запись (`updateMany where {id,status:'pending'}` → `count===0` значит «не я», `dead-letter-queue.ts:119-123`).
- tenantId в запросах: ни GET, ни POST не фильтруют по организации (`route.ts:36-41`; `dead-letter-queue.ts:119,154,176`). По модели доверия (ADMIN — платформенная роль) это не дефект сегодня; но при появлении «тенант-админа» станет кросс-тенантным (before tenant #2).

**3) Повтор события об удалённом объекте.** Разбор по типам (из кода, без прогонки):
- Проекция (`ReportCreated`/`ReportSubmitted`/`ReportDeleted`, потребитель `projected`): обработчики восстанавливают `siteId/userId/tenantId` из `Report` по `aggregateId`; отчёта нет → все три пусты → досрочный `return` с warn, **без throw** (`event-handlers.ts:64-82,213-229`; `projection-worker.ts:85-89,117`). Итог: **очистит** — запись станет `resolved`, новый DLQ-ряд не появится, Telegram не тревожится. Минус — наружу уходит «Событие отправлено повторно», хотя ничего не спроецировано.
- Старая Telegram PDF-доставка (`ReportPdfDeliveryRequested`): `deliverReportPdf` грузит контекст по `aggregateId`; отчёта нет → `ctx === null` → warn + `return` (`event-handlers.ts:565-569`); отчёт **есть** → PDF снова уходит в Telegram (`:611-623`).
- Общий случай постоянного отказа (не связано с удалением): автоматического зацикливания нет — запись помечается `resolved` сразу, а после 5 новых попыток (`outbox-publisher.ts:173-207`) создаётся **новая** pending-запись в DLQ без ссылки на предыдущую. То есть каждое «зацикливание» требует нового клика админа, но цепочку «повтор X → снова упало» по экрану не проследить.
- Замечание о «пустом успехе»: досрочный `return` в проекции и в PDF-доставке считается успехом — событие закрывается молча, хотя работа не сделана. Это лучше петли, но админ не узнаёт, что «повтор» был пустышкой.

**4) Telegram о новых записях и шум повтора.** Да, `moveToDlq` шлёт **отдельное** сообщение в Telegram при **каждой** новой записи (`dead-letter-queue.ts:94-106`), гасится переключателем «Недоставленные события» (`deliveryFailures`, `settings.ts:60`; `outbox-publisher.ts:186-189`). Текст — сырой и технический: тип события латиницей, `aggregateId`, фрагмент текста ошибки (может нести имена таблиц/колонок). Повтор, снова упавший, создаёт новую запись → **новый** алерт: шум растёт с каждым кругом. Плюс сам повтор PDF-события шлёт PDF в чат (находка 1). Отдельная оговорка: `moveToDlq` срабатывает из воркера без запроса, а `getConfigs()` берёт тенант развёртывания (`getRequestTenantId() ?? DEFAULT_TENANT_ID`, `telegram.ts:44-45`), поэтому алерт уходит в чаты **тенанта развёртывания**, а не организации события (для мультитенанта — важно, для нынешнего одного — мелочь).
