# 50 — Здоровье хранилища (R2/S3) и потеря фотографии при медленном хранилище

Ветка: `hermes/q4-0926` (worktree `D:\PillingR\wt-night`). Задача read-only, изменений в существующих файлах не делалось.

## Итог

Разобрана цепочка «health-чек хранилища → вердикт системы → лог» и путь загрузки фото (presign → PUT → confirm).

Наблюдаемое «16 раз в сутки storage:"down" + "System health recovered" через секунды» объясняется конструкцией, а не сбоем: health-чек S3 — это один `ListObjectsV2` с жёстким таймаутом **2000 мс, позаимствованным у проверки БД** (`DB_CHECK_TIMEOUT_MS`), без повторов; любой ответ дольше 2 с даёт `storage: down`, а `down` у storage **безусловно** переводит всю систему в `unhealthy` — состояния «медленно» у хранилища нет. Опрос идёт каждые 15 с, но в лог пишется только смена картины, поэтому 16 пар строк = 16 реальных «морганий» R2 за сутки.

Второй контур — загрузка фото. Фотография физически попадает в R2 на шаге PUT, но запись в БД становится `completed` только после успешного confirm (сервер скачивает объект и делает миниатюру). Confirm идёт через общий `s3CircuitBreaker`, **без таймаута и без отмены**; если R2 в этот момент тормозит, запись навсегда остаётся `pending`, объект в R2 сиротеет, а восстановления нет — ни повтора на сервере, ни воркера-сверки. Пользователь при этом видит лишь тост с общей ошибкой, а photoId теряется вместе с состоянием компонента.

Счёт по важности: **критично — 0, важно — 9, мелочь — 13** (всего 22). «Критично» не выставлено сознательно: ни в одном из проверенных путей фото не терялось *без* сообщения об ошибке — клиент всегда показывает тост. Полностью «молчаливую» потерю подтвердить не удалось (см. «Не проверено»).

Топ-5:
1. `checkers/storage.ts:21` + `aggregate.ts:26` — один медленный ответ S3 (>2 с) делает всю систему `unhealthy`; у хранилища нет состояния `slow`.
2. `media-service.ts:187-190` — `confirmUpload` качает объект из R2 без таймаута и без `AbortController`; медленный R2 вешает запрос.
3. `media-service.ts:141` / `:264-274` — запись создаётся `pending` до presign и остаётся `pending`, если confirm упал; объекта-сироты и `pending`-строки некому убрать (воркера сверки нет).
4. `s3-health-check.ts:37-57` + `helpers.ts:6-21` — таймаут health-чека отклоняет промис, но не отменяет HTTP-запрос; каждые 15 с стартует новый, старые продолжают жить.
5. `media-service.ts:153` + `circuit-breakers.ts:193` — `s3CircuitBreaker` накрывает локальную подпись URL (сети нет), а `confirm` по сети делит с ним состояние: 5 неудачных confirm открывают брейкер и блокируют выдачу presign для всех (503).
