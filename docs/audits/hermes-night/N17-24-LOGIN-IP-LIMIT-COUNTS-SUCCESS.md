# N17-24 — лимит входа по IP считает успешные входы

Аудит только чтением. Версия кода: `git rev-parse HEAD` = `30dc3b74651b350c21e5f9dd46a045745637db88` (ветка `hermes/code-1011`), рабочая папка `D:/PillingR/wt-night-code`. Папки `wt-night-code-code` в задании нет — работал в текущей. Приложение не менялось, создан только этот отчёт.

Вопрос задания: лимит входа по IP (`src/lib/rate-limiter.ts`, `login-ip:*`) считает успешные входы и никогда не сбрасывается. Наблюдение стенда 16.10 (после 21 успешного входа 22-й получает 429 с `retryAfter ≈ 1800 с`) проверено по коду.

## Итог

1. **Да, успешный вход считается в общий лимит по IP.** Проверка `login-ip:<ip>` идёт первой и инкрементирует счётчик до сверки пароля (`src/services/auth/auth-service.ts:79`); сброс на успехе касается только `accountKey` и `lockoutKey` (`:136-137`), `login-ip` не сбрасывается никогда. Статус: **ПРОЙДЕНО**.
2. Порог: `LOGIN_IP_RATE_LIMIT` = 20 попыток / 15 мин, затем блок 30 мин (`src/lib/rate-limiter.ts:40-44`). 20-я попытка разрешена, 21-я блокируется — код и юнит-тест дают именно это (`rate-limiter.ts:79-84`, `src/lib/__tests__/rate-limiter.test.ts:32-47`); наблюдение стенда «21 успех → 22-й 429» расходится на одну попытку (см. «Не проверено»).
3. На общем IP (планшет на смену, Wi-Fi, NAT) 20 любых входов за 15 минут закрывают вход на 30 минут **всем, включая верный пароль** — блок проверяется до пароля. Статус: **ПРОЙДЕНО**.
4. Если `TRUST_PROXY` ≠ `true`, ключ вырождается в `login-ip:host-<домен>` — один счётчик на всю компанию (`rate-limiter.ts:500-505`, `docker-compose.yml:117-123`). Значение переменной на бою не читал. Статус: **ГИПОТЕЗА**.
5. Теста «успешные входы не считаются» нет; есть тест, который фиксирует обратное — что `login-ip` при успехе **не** сбрасывается (`src/services/auth/__tests__/auth-service-credentials.test.ts:113-122`). Статус: **ПРОЙДЕНО**.
6. Сбросить `login-ip`-блокировку из приложения нельзя: ни эндпоинта, ни ветки сброса; остаётся ждать до 30 минут или вручную удалять Redis-ключи `rl:login-ip:<id>` / `rl:blocked:login-ip:<id>`. Статус: **ПРОЙДЕНО**.
7. Вывод: правка **нужна**; считать в `login-ip` следует только **неуспешные** попытки (то есть сбрасывать/не инкрементировать IP-бакет при успешном входе). Подбора это не ослабляет — защита остаётся на аккаунтных бакетах `login:<email>:<ip>` и `login-acct:<email>`. **Согласовать с владельцем по безопасности** (тема затрагивает и анти-подбор, и доступность входа).
8. «Операторский вход» сегодня — тот же `POST /api/auth/login`: путь по ПИН-коду удалён коммитом `bb40d7ed` (27.09); `src/app/api/auth/pin/route.ts` отсутствует. Оператор делит тот же IP-бакет.
