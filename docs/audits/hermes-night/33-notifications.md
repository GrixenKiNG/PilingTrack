# 33 — Уведомления: доходят ли до нужных людей, с верным текстом и ровно один раз

## Итог

Аудит только чтением: проверены отправители Telegram (8 точек), durable-доставка, планировщики, флаги настроек, формат текстов, идемпотентность и изоляция организаций. Найдено **34 находки: 2 критично, 17 важно, 15 мелочь**.

Топ-5:
1. **критично** — алерт о простое (главный канал диспетчеру) теряется молча: `handleDowntimeAlert` глотает ошибку отправки и не смотрит на результат `sendAlert`, а outbox помечает событие `published` → повтора и DLQ нет (event-handlers.ts:272-288). Durable-путь (дефекты) так не делает.
2. **критично** — частичная доставка считается успехом: если из трёх чатов ответил один, событие помечается доставленным (durable-alert-delivery.ts:20-23), и чат, которому алерт о запрете работ не дошёл, не получит его уже никогда — тихая потеря, видимая только строкой в логе (telegram.ts:93-105).
3. **важно** — дубли не по сбою, а по устройству: `upsertReport` пересобирает агрегат со **всеми** строками (report-command.service.ts:205-211, 372-374), `addDowntime` эмитит `DowntimeAdded` на каждую (report.aggregate.ts:241-251), а обработчик не дедуплицирует. Каждое сохранение отчёта в 24-часовом окне = новый алерт про тот же простой и новый PDF «Корректировка отчёта».
4. **важно** — числа в текстах сырые: «Простой 2.3333333333333335 ч» (event-handlers.ts:276) и «Простои 8,167 ч» в подписи PDF (event-handlers.ts:398,419) вместо «2 ч 20 мин» — общий форматтер `formatDowntimeHours` (lib/downtime-hours.ts:66), которым пользуется весь UI, в уведомлениях не применён ни разу.
5. **важно** — время в алерте серверное, а не тенантное: `new Date().toLocaleString('ru-RU')` без `timeZone` (telegram.ts:144), TZ в контейнерах не задан → в сообщении UTC, то есть на 3 часа раньше московского, при том что `settings.timezone` в продукте существует и валидируется.

Сверх ожиданий: флаг касается не всех видов сообщений (происшествие, Alertmanager, DLQ — без выключателя), а «ключ» идемпотентности — это cuid внутри текста, который читают люди.

## Не проверено

- **Фактическая отправка в проде** — нет доступа к серверу, боту и базе; всё выше — по коду. Токен бота и реальные `chatId` не читал (секреты, AGENTS.md §1).
- **Задан ли `DEFAULT_TENANT_ID` в проде** — не проверено (в `.env.example:12` значение `"default"`); от этого зависит, теряется ли Alertmanager-уведомление целиком или уходит в организацию по умолчанию.
- **Таймзона рантайма контейнера** — не проверено эмпирически; вывод «UTC» сделан из отсутствия `TZ=` в `Dockerfile*`, `docker-compose*.yml` и примерах env (текстовый поиск по репозиторию вернул ноль совпадений). Если TZ задаётся вне репозитория (оркестратор), время в алерте всё равно серверное, а не тенантное.
- **Поведение Telegram Bot API при 429/битом HTML** — не проверял вживую (нет токена); выводы «сообщение не уйдёт» — из разбора кода `response.ok` и практики API.
- **Причина падения «частичной доставки»** — точная доля случаев (`migrate_to_chat_id`, удаление бота из группы) не измерялась.
- **Содержимое PDF** (`generateSinglePdf`, лист простых) — отдельный отчёт 28-pdf-content.md; здесь проверял только подпись к документу и имя файла.
- **Замороженные зоны**: `src/app/orion/**` (в т.ч. `api/orion/lead/route.ts:128` — публичная форма шлёт `sendMessage` в чат DEFAULT_TENANT_ID) и `src/modules/operator-mobile/**` — читал только для описания отправителя, поведение не оценивал.
- **Экран и лента feedback-center.tsx** — не разбирал, ограничился упоминанием, что отдельного журнала отправок Telegram в продукте нет (notifications-section.tsx:224).
- **Тесты уведомлений** (`src/core/notifications/__tests__/telegram.test.ts`, `durable-alert-delivery.test.ts`) — прочитал для понимания ожидаемого поведения, но не запускал (аудит — только чтение; `npm run test:unit` в этой сессии не выполнялся).
