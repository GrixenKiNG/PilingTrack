# 20. Лимиты выборок и N+1: where запросы читают строки без потолка

Дата: 26.09.2026. Ветка: `hermes/q3-0925` (worktree `wt-night`). Задача read-only: изменён только этот файл.

## Итог

Найдено **31** находка: **1 критично**, **13 важно**, **17 мелочь**. Ни одна не ломает работу сегодня (объёмы малы: ~40 отчётов/мес на тенант), но критичная уже сейчас читает всю таблицу `AuditLog` **дважды на каждое открытие экрана** журнала аудита.

Топ-5:

1. **критично** — `readChain` (`src/modules/readiness/infrastructure/audit/audit-repository.ts:87`): `auditLog.findMany` без `take`, и `GET /api/readiness/audit` вызывает его **дважды** за запрос (`route.ts:33` + `verify-chain.ts:85`), а фильтры и `limit=500` применяются уже в памяти — то есть таблица читается целиком и/или пересчитывается SHA-256 по каждой строке.
2. **важно** — тот же `readChain` в выгрузке: `src/app/api/readiness/export/route.ts:81` и `:114` (datasets `audit` и `reports`), плюс `workPermit` (`:59`) и `readinessScoreSnapshot` (`:102`) без `take`.
3. **важно** — `getSiteWithHierarchy` (`src/modules/sites/application/queries/site-query.service.ts:93`, шаблон include — `:14–49`): карточка объекта тянет `fields → clusters → pickets` целиком, без `take` ни на одном уровне.
4. **важно** — `getFleetSnapshot` (`src/modules/monitoring/application/queries/fleet-monitoring.service.ts:170`): все фото всей техники без `take` на каждой загрузке дашбордов (`/api/monitoring/fleet` дёргают 5+ экранов), хотя используется ровно одно фото на установку.
5. **важно** — `getItemUsage` (`src/services/dictionaries/dictionary-service.ts:138, 151, 161`): переименование/удаление элемента справочника читает **все** строки `PileWork` / `LeaderDrilling` / `ReportDowntime` за все годы, чтобы посчитать DISTINCT в JS.

Отдельно: N+1 ровно того вида, что ищет задание (`for … await db.x.findUnique`), **внутри четырёх заявленных глобов не подтверждён** — все срабатывания автомата оказались ложными (см. «Методика»). Настоящие N+1 живут рядом: `rebuild.ts:198→209` (по одному `upsert` на каждый отчёт тенанта), `report-command.service.ts:156→162`, `inspection-commands.ts:244→257`.

## Методика

Что и как искал (всё воспроизводимо; скрипты лежат во временном каталоге сессии, в репозиторий не добавлялись):

1. Обход scope: `src/app/api/**/route.ts` (93 GET-обработчика), `src/modules/**/application/queries/**` (13 файлов), `src/services/**/*-service.ts` (19 файлов), `src/core/infrastructure/raw-queries.ts`.
2. Автомат №1 (балансировка скобок вокруг `findMany(`): для каждого вызова проверялось наличие `take`/`cursor`/`distinct` в блоке аргументов. Результат: **87** вызовов `findMany`, из них **60 без `take`** и **27 с `take`**. По каждому из 27 отдельно проверено, нет ли внутри вложенных коллекций без собственного `take`; такие есть только у перечисленных в таблице (пользователи, паспорт сваи, карточка установки) — остальные `take`-вызовы вложенных списков не тянут.
3. Автомат №2 (N+1): для каждого `for`/`while`/`.map(async`/`.forEach(async` искался `await …db|tx …findMany|findUnique|count|groupBy|$queryRaw` в пределах 25 строк. **24** срабатывания; каждое открыто руками — **в заявленном scope все 4 оказались ложными** (`fleet-monitoring.ts:183` — цикл кончается на 188, запрос на 193; `feedback-event-service.ts:153` и `report-history-service.ts:15` — там просто сборка `Map`; `dictionary-service.ts:186` — агрегация в памяти). Настоящие N+1 найдены в `application/commands` и `projections` (вне 4 глобов) — вынесены в таблицу с пометкой.
4. Автомат №3: `$queryRaw`/`$executeRaw` без `LIMIT` в scope. Все совпадения — точечные (`set_config`, `INSERT … RETURNING`), либо агрегаты с `GROUP BY`; два чтения сырых строк (`raw-queries.ts:134`, `:195`) в таблице.
5. Широкий повторный проход по `src/modules/**` и `src/app/**` (кроме заморозки `operator*`/`orion*`) — 74 вызова `findMany` без `take`; всё существенное либо попало в таблицу, либо делегировано уже перечисленным сервисам.
6. Индексы проверялись по `prisma/schema.prisma` (2499–2610 и др.) и `prisma/indexes.sql`.
7. Руками открыт каждый `path:line` из таблицы (чтение файлов), ни одна строка не взята из грепа без просмотра контекста.

Ожидаемые объёмы (оценка по посылке задания, **в БД не считалось — локальной базы в worktree нет**): 40 отчётов/мес × 24 мес = **~960 отчётов на тенант, ~1920 на двух**; дочерние строки — оценка 3–8 `PileWork` и 1–3 `LeaderDrilling`/`ReportDowntime` на отчёт, то есть **~3–8 тыс. `PileWork` на тенант за 2 года**. Число строк `AuditLog`/`FeedbackEvent` оценить нельзя (нет данных о частоте команд) — помечено как «не проверено».

Связь с уже сданным `docs/audits/hermes-night/03-performance.md`: часть находок пересекается. Что там закрыто в этом worktree на момент аудита: `raw-queries.ts` уже имеет потолок `PERIOD_REPORTS_LIMIT = 2000` с явной ошибкой (`raw-queries.ts:25,99`), `audit-history-service.ts:84` уже с `take`, `user-service.ts:87` уже `groupBy` вместо `findMany`. Экспорт отчётов теперь ограничен окном 92 дня в маршруте (`reports/export/route.ts:10,54`) — это меняет оценку находки №1 из прошлого отчёта. ## Не проверено

- **Ожидаемые количества строк** — оценка по посылке задания (40 отчётов/мес × 24 мес), а не подсчёт по базе: локальной БД в worktree нет (`prisma/` содержит только `schema.prisma`, `migrations/`, сиды; файлов `.db`/`.sqlite` нет). Число строк `AuditLog`, `FeedbackEvent`, `Inspection`, `Media` оценить нечем — нет данных о частоте соответствующих команд.
- **Стоимость `distinct: ['type']` в Prisma** (находка №10) — обосновано документацией/поведением Prisma (фильтрация `distinct` выполняется движком после выборки), **но на живой БД не измерялось**; если в проекте включён `relationJoins`/иной драйверный режим, вывод стоит перепроверить планом запроса.
- **`src/app/**` как серверные компоненты (`page.tsx`)** — широкий автомат №5 не нашёл там `findMany` без `take`, но страницы, читающие данные через `fetch` к API, покрыты только со стороны API.
- **Замороженные области** (`src/app/operator/**`, `src/app/api/orion/**`, `src/components/orion/**`, `src/modules/operator-mobile/**`) исключены из таблицы по правилу задания — в них остаются неразобранные чтения (например `operator-mobile/application/mobile-shift-query.ts` — 11 вызовов `findMany`, часть, судя по автомату, без `take`).
- **Файлы вне 4 заявленных глобов**, где чтения явно избыточны и затронуты лишь по касательной: `src/modules/reports/application/projections/rebuild.ts:44,110,187,198→209`, `src/services/reports/outbox-publisher.ts:94` (там `take` есть — проверено), `src/core/realtime/publisher/ws-publisher.ts:32`, `src/core/observability/lag-monitor.ts:108,125,147` (только `count`), `src/services/users/user-documents.ts:270` (ранее отчитано в `03-performance.md` #8, вне глобов `*-service.ts`).
