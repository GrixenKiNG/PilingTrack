# Отчёт по тихому проглатыванию ошибок (silent failures) — 02

Аудит читает только `src/**`, минуя тесты (`*.test.*`, `__tests__`), замороженные зоны
(варианты операторского экрана `src/app/operator/**`, `src/components/piling/operator*/**`,
`src/modules/operator-mobile/**`) и публичный сайт ORION (`src/app/orion/**`,
`src/app/api/orion/**`, `src/components/orion/**`). Ни один файл не изменялся.

## Итог

Паттерн «проглатывание ошибки» в кодовой базе массово присутствует в **чтениях и служебной
телеметрии** и в подавляющем большинстве **оправдан** (кэш, метрики, heartbeat, защитный
разбор тела ответа `res.json().catch(...)`). Именно поэтому сырых «пустых» catch мало —
кодовая база уже проходила разбор таких мест (в комментариях зафиксированы инциденты
2026-05-20, N-4, молчаливые потери отчётов из-за tenantId=NULL).

Реальных находок, где проглатывание делает **невидимой ошибку бизнес-записи** (отчёты, сваи,
простой, ТО, готовность, уведомления) — **1 значимая** и **4 мелких**. Критичных
(«запись потеряна без следа, оператор видит успех/пустоту») — **1 кандидат** (домен
«отчёты», `use-report-form.ts:182`), плюс значимая — сбой чтения признаков готовности
подменяется пустым списком. Количество оправданных проглатываний (считаю отдельно): ~55+.

Проверка каждого кандидата выполнялась открытием файла и чтением контекста catch. Сомнительные
места, которые я не смог трассировать до конца, перечислены в «Не проверено».

## Методика (как воспроизводимо)

1. `git status` подтвердил: изменения только `AGENTS.md`; ветка `hermes/night-0925`.
2. Поиск по `src/**`, **исключая** `__tests__/`, `*.test.*`, `*.spec.*`, `node_modules`,
   и удаляя замороженные `*operator*` и `*orion*`:
   - `grep -rnE "\.catch\s*\(\s*\(\s*\)\s*=>\s*\{\s*\}"` — пустые inline-catch;
   - `grep -rn "catch\s*\{\s*$"` + сверка многострочных пустых блоков catch;
   - `grep -rnE "\.catch\s*\(\(\s*\)\s*=>\s*(null|undefined|\[\])"` — подстановка значения;
   - `grep -rnE "Promise\.allSettled"` — игнорирование отказов;
   - `grep -rn "void "` + скрипт-сканер fire-and-forget записей (`.create/.update/.save/...`)
     без `await`/`void`/`return`.

   Ключевая эвристика: паттерн `await <res>.json().catch(...)` на **GET** и `catch{/*ignore*/}`
   при мертвой/служебной записи (последний визит устройства, счётчик соединений) — не находка.
   Находка — когда **бизнес-запись** (отчёт, простой, наряд, правило уведомления) или её
   *чтение-признак* при сбое молча превращается в «пусто/успех».

3. Каждая находка подтверждена `read_file` нужного фрагмента (строки в таблице).

Один-в-один количество дистрибутивов по файлам, где встречен любой `.catch(...)`,
не привожу: их ~157 строк по всей `src/`, и почти все — защитный разбор `res.json()`.
Вместо этого: находки (таблица ниже) + отдельный подсчёт оправданных.

**Оправданные проглатывания (только счёт, без находок):**
- ~50+ мест `await <res>.json().catch(() => null/{})`: защитный разбор тела ответа на **чтении**,
  который всегда предваряется проверкой `res.ok`/`!response.ok` в коде далее — реальная ошибка
  HTTP не скрывается (напр. `src/app/api/**/route.ts`, `admin-*`, `pile-journal`, `maintenance/*`,
  `readiness/screens/*`, `to/fuel-panel.tsx`).
- `core/outbox/dead-letter-queue.ts:77-78` (fire-and-forget Telegram-аларт о DLQ): сам `sendMessage`
  внутри `telegram.ts:162,168` логирует и успех, и отказ (`logger.error`/`logger.warn`), поэтому
  внешний `.catch(() => {})` ничего не скрывает.
- `ws-server.ts:386-387` (счётчик соединений/heartbeat) — телеметрия, best-effort.
- `device-key-service.ts:142-144` (`void ...update({ lastUsedAt })...catch(() => {})`) — служебная
  запись «последний визит» телеметрии, fire-and-forget по назначению (AGENTS: телеметрия спит).
- `health-tracker/aggregate.ts` `catch {} // best effort` — сбор метрик, оправдан.
- `realtime`, `worker`, `outbox` пульсации `void recordLeaderHeartbeat(...).catch(logger.error)` —
  логируют, best-effort.

## Не проверено

- **Полный перебор всех ~157 строк `.catch(...)`** — десятки из них я не открывал по одной.
  Классифицировал по паттерну (чтение `res.json` + проверка `.ok`), а не по месту. Для
  стопроцентной уверенности в каждой требуется открыть каждую строку — сделано для всех
  «подозрительных» (таблица), чтения-разборы не трассировал поштучно.
- Является ли `fetchReadinessShifts/...` в `to-module.tsx:418-424` единственным входом этих
  вкладок (нет ли дублирующего механизма ошибок сверху) — посмотрел `setShifts/permit/defects`
  (стр. 462-464): они просто ставят пустой результат. Глубже не нырял.
- Реальные коды статусов/поведение `readOptionalCollectionWithIssue` и `readAuthoritativeCollection`
  (нужно открыть их реализацию, чтобы дать точный фикс для находки №1) — не открывал.
- Post-/Put-роуты `src/app/api/readiness/{access-matrix, place-presets}/route.ts`, где
  `request.json().catch(() => null/{})` — разбор на запись; безопасность аналогична чтениям,
  но явно не проверил, что `null` везде приводит к 400, а не к валидной записи.
- Дочерние `catch`-цепочки в `operator-mobile/v7/v10` и `operator-v2/*` не смотрел — заморозка.
- Behaviour `telegramNotifier.sendMessage` при падении (бросает ли или возвращает false) — для
  точного фикса находки №6 нужно открыть `src/core/notifications/telegram`.
