# Границы суток по UTC вместо пояса организации: где «день» считается не по МСК

Дата: 2026-09-26. Ветка: `hermes/q4-0926` (в задаче указана `hermes/q3-0925`; worktree `D:\PillingR\wt-night`, `git branch --show-current` → `hermes/q4-0926`). Только чтение кода: файлы не менялись, БД не открывалась, приложение не запускалось.

Проверялся один вопрос: где приложение режет сутки по UTC (или по поясу процесса), а не по поясу организации, из-за чего свая / простой / осмотр, сделанные между 00:00 и 03:00 МСК, попадают не в тот день.

Находка №1 прошлого аудита (`docs/audits/hermes-night/32-exports.md`, границы периода журнала забивки через `new Date(\`${d}T00:00:00.000Z\`)`) **не повторяется**: она исправлена, `pile-passport.service.ts:157-173` теперь считает границы через `zonedDayStartUtc`/`addDays`.

## Итог

Найдено **18 точек**, из них: **1 критично**, **5 важно**, **12 мелочь**. Главный вывод: «день отчёта» в продукте хранится строкой (`Report.date String // YYYY-MM-DD`, `prisma/schema.prisma:1935`) и заполняется через `getTodayInTimezone()` — поэтому цифры свай/простоя по дням считаются от дня тенанта и **не** ломаются ночью. Проблемы сосредоточены там, где день выводится из **момента времени** (`drivenAt`, `recordedAt`, `inspectionDate`, метки телеметрии) или из `new Date()` на сервере: контейнер живёт в UTC (`Dockerfile` не задаёт `TZ`), значит серверные «сутки» начинаются в 03:00 МСК.

1. **критично** — в подшиваемом `.xlsx` журнала забивки строка «Журнал выгружен» печатается UTC-временем (`pile-passport.service.ts:458`): документ, сформированный 26.09 в 01:00 МСК, датирован «2026-09-25 22:00», хотя весь остальной документ — в поясе организации.
2. **важно** — «показания счётчика внесены сегодня» (`operator-shift-query.ts:216`) считается от UTC-полуночи: машинист, снявший показание 26.09 в 01:30 МСК, на экране считается **не** внесшим показания, и шаг закрытия смены блокируется (`components/piling/operator/shift-phase.ts:166`).
3. **важно** — экран «Надёжность ТО» отправляет на сервер наивную строку `from=2026-09-20T00:00:00` (`admin-analytics.tsx:150`), сервер парсит её как UTC (`app/api/maintenance/kpi/route.ts:26`) → окно KPI (MTBF/MTTR/доступность/простой) сдвинуто на 3 часа: работа 20.09 00:00–03:00 МСК в период не входит, а 27.09 00:00–03:00 МСК входит.
4. **важно** — расход топлива в аналитике техники берётся по окну UTC-суток (`equipment-analytics-service.ts:154-155`), тогда как сваи/бурение/простой в том же ответе ограничены днём отчёта: две группы чисел за один период считаются по разным границам.
5. **важно** — титул журнала на экране `/pile-journal` считает «Период забивки» по UTC (`pileJournalHeader` без `timezone`, `app/api/pile-passports/route.ts:57`), а в выгружаемом `.xlsx` — по поясу организации (`pile-passport.service.ts:349-359`): на ночных сваях период в титуле экрана противоречит тем же строкам под собой и файлу.

Сервер: `Dockerfile` (стадии `node:22-alpine`, без `ENV TZ`) — пояс процесса UTC; все примеры ниже считаются по МСК = UTC+3.

3. Каждое попадание читал по файлу и решал: это (а) граница суток/«сегодня», сравниваемая с моментом времени → находка; (б) чистая подстановка дня тенанта (строка `YYYY-MM-DD`) → корректно; (в) отображение в браузере (пояс телефона = МСК) → не дефект.
4. Сценарий-эталон для примеров: свая/событие 26.09 00:30 МСК = `2026-09-25T21:30:00Z`; «сегодня» 26.09 10:00 МСК = `2026-09-26T07:00:00Z`.
