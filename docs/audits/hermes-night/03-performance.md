# Аудит производительности БД: паттерны доступа, которые замедлятся с ростом данных

Отчёт: docs/audits/hermes-night/03-performance.md
Проект: PilingTrack (Next.js 16 + Prisma 7, PostgreSQL). Схема: `prisma/schema.prisma`.
Вопрос: какие паттерны обращения к БД станут медленными, когда накопятся годы ежедневных отчётов, свай, простоев, аудита и медиа.

## Итог

Найдено **18** находок (2 критично, 9 важно, 7 мелочь). Ни одна из них не ломает работу при сегодняшних объёмах — код местами уже оптимизирован (raw-агрегаты, проекции `SiteDailySummary`/`ReportAnalytics`, батчинг медиа, `take` в пагинациях). Но три класса мест будут деградировать линейно с числом лет данных:

1. **Аналитика и выгрузки гоняют по всей таблице отчётов с дочерними include и агрегируют в Node** — `admin/analytics/overview` и `fetchReportsForExport` за каждый запрос материализуют целый период отчётов с сваями/бурением/простоями. У `Report` **нет** составного индекса под этот паттерн (`tenantId,date,status`), поэтому такие запросы — последовательное сканирование растущей таблицы.
2. **`FeedbackEvent` растёт с каждым событием аудита** (входы, сохранения отчётов, действия со справочниками — это одна таблица, см. `audit-service.ts`), а читается по полям без подходящего индекса: `(scope,targetId)` и `action`. Ещё два запроса к ней делаются **без `take`**.
3. **Append-only таблицы не имеют ретеншена/архивации** (`AuditLog`, `FeedbackEvent`, `ReportVersion`, `ReportAudit`, `OutboxEvent`, `TelemetryRecord`) — каждый год они растут без потолка, и индексные сканы по ним дорожают.

Топ-5 по цене:
- выгрузка отчётов без предельного размера (можно вернуть всю историю в один ответ);
- аналитика периода с детскими include без совместимого индекса и без кэша;
- история сущности по `scope+targetId` без составного индекса в растущем `FeedbackEvent`;
- список пользователей тянет ВСЕ логины-события без `take`;
- `listDocumentsNeedingAttention` материализует все документы тенанта, чтобы отфильтровать просрочку в JS.

Дыра №1 по влиянию на повседневную работу — **`FeedbackEvent` без индекса `(scope,targetId)`**: каждая сессия и каждое изменение пишут в эту таблицу, а экраны "история/журнал" читают её по незаиндексированным колонкам; при годах накопления это станет первым заметным тормозом UI.

## Методика

Всё — **read-only** (к БД не подключался и ничего не запускал). Опытным путём обход не запрашивал (правило: "не проверено" — честно помечено).

1. Полностью прочитал `prisma/schema.prisma` (2865 строк) и выписал для растущих таблиц все `@@index`/`@@unique`: `Report` (1972–1985), `ReportVersion` (1992–2002), `ReportAudit` (2009–2024), `PileWork` (2171–2207), `ReportDowntime` (2387–2423), `TelemetryRecord` (2033–2050), `AuditLog` (2563–2607), `FeedbackEvent` (2515–2539), `Media` (2710–2736), `MaintenanceRecord` (580–616), `UserDocument` (192–213), `MeterReading` (731–745).
2. По всему `src/` искал обращения к этим таблицам: `db.<table>.findMany/groupBy/count/aggregate`, `$queryRaw`, N+1 в циклах.
3. Прочитал целиком файлы чтения данных: `report-query.service.ts`, `report.repository.ts`, `raw-queries.ts`, `site-analytics-service.ts`, `equipment-analytics-service.ts`, `fleet-monitoring.service.ts`, `audit-history-service.ts`, `audit-service.ts`, `report-history-service.ts`, `feedback-event-service.ts`, `user-service.ts`, `user-documents.ts`, `dictionary-service.ts`, `telemetry-ingestion-service.ts`, `media-service.ts`, `equipment-query.service.ts`, маршрут `admin/analytics/overview`.
4. Для каждого запроса сопоставил `where`/`orderBy` с реальными индексами схемы и оценил рост соответствующей таблицы.
5. Ничего не запускал и не проверял планы запросов (нет БД) — выводы про индексы и сканирования основаны на чтении схемы, это помечено «не проверено» где применимо.

### Приложение (доп. мелочи, path:line)
- Дата-фильтр и сортировка по `date desc` в `report-query.service.ts:118` / `raw-queries.ts:66` / `equipment-query.service.ts:92` опираются на `(siteId,date)`/`(userId,date)`, но не на `(tenantId,date)` — при фильтрации только по организации происходит сортировка/сканирование среза. Покрывается индексом `(tenantId,date,status)` из #1/#2/#5.
- `fleet-monitoring.service.ts:193` — `report.findMany` по окну 7 дней с include детей; bounded по времени, но не кэшируется и выполняется на каждую загрузку дашборда (вместе с `media.findMany` на :170).
- `markAllFeedbackEventsRead` помечает только последние 100, семантика «всех» не выполняется (feedback-event-service.ts:228–234).

## Не проверено

- **Планы запросов / реальные времена.** БД не было — выводы про seq-scan и стоимость индексов основаны на чтении схемы (`prisma/schema.prisma`), а не на `EXPLAIN`. Для подтверждения худших кандидатов (#1, #2, #3, #4, #5) достаточно `EXPLAIN ANALYZE` на живых объёмах.
- **Точные объёмы строк.** Не считал: сколько отчётов/свай/простей в день, размер тенантов — оценка «линейно с годами» качественная, а не количественная.
- **Ветка телеграм/уведомления (`durable-alert-delivery.ts:15`)** — `FOR UPDATE` по `OutboxEvent`; отметил как мимо цели (поиск, не тормозящий запрос).
- **Проекции `SiteDailySummary`/`ReportAnalytics`** читаются `findUnique` (O(1)) — это уже правильный паттерн, их не менял бы.
- Правда ли `FeedbackEvent`-события входа пишутся на каждый логин (объём писателей в этой таблице) — подтверждено косвенно через `audit-service.ts`/`auth`-обработчики; точную частоту под нагрузкой не замерял.
