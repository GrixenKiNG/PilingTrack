# AU242-S3-LARGE-FILE-UPLOAD-UX — Загрузка больших файлов: интерфейс

Ревью: `git rev-parse HEAD` = `3f9cbf4914bb723371c396e988f79500964c7993` (ветка `hermes/q4-0926`).
Только чтение; код приложения не менялся. Отчёт — единственный созданный файл.

## Итог

- Все загрузки фото в проекте идут по одной схеме: `POST /api/media` (presign) → `PUT` напрямую в S3/R2 → `POST /api/media/{id}/confirm`. Ни одной библиотеки/обёртки для загрузки в `package.json` нет (`grep -iE "upload|dropzone|axios|progress" package.json` → пусто).
- **Индикатора прогресса нет нигде.** Загрузка выполняется через `fetch(...PUT)`, у которого нет события прогресса; во всех компонентах показан только неопределённый спиннер `Loader2` (например `photo-section.tsx:105` + `:183-190`). Файл в 10 МБ на мобильной сети — «крутилка» без процентов и без оценки времени.
- **Отмены загрузки нет нигде.** Ни `AbortController`, ни `signal`, ни кнопки «Отмена» в пути загрузки (проверено `rg "AbortController|signal:"` — в клиентских загрузках совпадений нет). Прервать залипание в 10 МБ можно только закрытием вкладки.
- **Лимит размера продублирован и рассинхронизирован.** Сервер читает `MEDIA_MAX_FILE_SIZE` (по умолчанию 10 МБ, `media-service.ts:508`), а клиент хардкодит `10 * 1024 * 1024` в 4 компонентах, а для фото плитки установки — вообще **12 МБ** (`equipment-tile-asset-storage.ts:1`). При выборе картинки 10–12 МБ клиент пропускает её, сервер отвечает 400, а пользователь видит бессмысленное «Не удалось начать загрузку (400)» (`equipment-photo-upload.ts:23`).
- **Сообщение при отказе сервера — техническое.** Для превышения размера сервер отдаёт «Размер файла 11534336 некорректен: нужно целое положительное число не больше 10485760» (`media-service.ts:126-129`), и в 4 экранах оно попадает в toast через `(await presign.json()).error` без перевода в человеческий текст.
- **Серверная сторона лимита в порядке (ПРОЙДЕНО):** размер проверяется на presign (`media-service.ts:119-130`), фиксируется в подписанном `ContentLength` (`:155-160`) и повторно проверяется по реальному объекту на confirm (`:224-240`, 413).

Счёт по важности: **критично — 0, важно — 7, мелочь — 11** (всего 18).

## Не проверено

- **Замороженные области.** `src/components/piling/operator-v5/operator-v5-app.tsx`, `src/components/piling/operator-mobile/**` (в т.ч. `screens/checklist-screen.tsx`, `screens/incidents-tab.tsx`, `api.ts`) содержат свои файловые вводы, но по AGENTS.md это замороженные варианты экрана оператора — не разбирались. Прогресс/отмена/лимит там могут отличаться.
- **ORION** (`src/components/orion/orion-handoff-site.tsx` — есть `type="file"`) не разбирался: замороженная область.
- **Реальные значения env** (`MEDIA_MAX_FILE_SIZE`, `S3_*`) не читались: `.env*` запрещены правилами. Вывод о рассинхроне лимитов — из кода и дефолтов, не из прод-конфигурации.
- **Поведение браузера.** Не проверял вживую (нет запуска приложения): сработает ли `ContentLength`-подпись как защита от «заявлено 1 КБ, залито 10 МБ», и не срабатывает ли `change` при повторном выборе того же файла — ГИПОТЕЗА по коду, не наблюдение.
- **Строки `Media` в статусе `pending`** — очистку искал только текстовым поиском по `src/workers/**` и `src/core/observability/**`; общий cron/скрипт вне этих каталогов мог не попасть в поиск.
- **Один файл на загрузку.** Все компоненты берут только `e.target.files?.[0]` — множественная загрузка не проверялась как отдельный сценарий.
