# Гонки записи: где двое меняют одну запись и молча теряют или задваивают результат

Дата: 2026-09-27. Worktree `D:\PillingR\wt-night`, ветка `hermes/q4-0926`. Только чтение кода: файлы не менялись, приложение не запускалось, к базе не подключались. Проверялся один вопрос: где два одновременных актора (два человека, повтор с телефона + диспетчер, два воркера) пишут одну и ту же строку так, что один результат теряется либо считается дважды.

## Итог

Найдено **22 точки**, из них **2 критично**, **9 важно**, **11 мелочь**. Контур техготовности (`src/modules/readiness/**` для смен, нарядов-допусков, дефектов, снимков готовности) проверку на одновременность проходит почти образцово: `Serializable` + идемпотентный ключ в той же транзакции + `updateMany` со статусом в `WHERE` + версия в `WHERE` + `SELECT … FOR UPDATE` в цепочке аудита + `ON CONFLICT … DO UPDATE … WHERE calculatedAt > …` в `CurrentReadiness`. Все находки — там, где этот образец **не** применён: отчёты, моточасы, осмотр/дефекты, наряды ТО (планировщик), бригады, правила готовности, настройки и фоновые задания.

1. **критично** — `POST /api/reports/upsert` без `reportId` и без версии у двух одновременных отправок создаёт **два отчёта за одну смену одного машиниста** (`report-command.service.ts:106-112`): выработка задваивается в аналитике и в дневной сводке объекта (у `Report` уникален только `reportId`, `prisma/schema.prisma:1930`).
2. **критично** — `saveAnswers` пишет ответы осмотра **вне транзакции и без статуса в `WHERE`** (`inspection-commands.ts:264-277`): повтор с телефона задваивает ответы, а завершение осмотра, посчитанное по снимку ответов, расходится с тем, что лежит в базе, — решение о допуске принимается по данным, которые можно переписать после решения.
3. **важно** — одновременная подпись наряда-допуска двумя согласующими оставляет его навсегда «на согласовании» со всеми подписями (`permits/commands.ts:258-265`): ни один из двух не видит подпись другого и не выполняет переход в `APPROVED`, а повтор подписи отбивается 409 «решение по этой роли уже принято».
4. **важно** — кэш `Equipment.engineHoursTotal` обновляется чтением-записью внутри транзакции (`meter-reading.ts:157-186`): при двух одновременных показаниях в кэш попадает не последнее, наработка «откатывается», вместе с ней едут пороги ТО.
5. **важно** — дедупликация дефектов осмотра «прочитал-потом-создал» без уникального индекса (`inspection-commands.ts:381-407`, `sourceKey` уникален? нет — `prisma/schema.prisma:676`): два одновременных осмотра одной машины заводят два открытых дефекта по одному пункту.
