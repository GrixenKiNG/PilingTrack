## Итог

1. Режим офлайн — это **очередь в `localStorage`** (`pilingtrack.operator.queue.v1`), а не полноценный офлайн: на устройстве лежат только 3 добавляющие команды — `log-production`, `report-incident`, `correct-production` (`offline-queue.ts:29,67-69`). Всё остальное (переходы смены, осмотры, приёмка, фото) работает только онлайн.
2. Идемпотентность на сервере настоящая: уникальный индекс `@@unique([tenantId, clientCommandId])` на 8 таблицах + чтение-дедуп + осторожная обработка `P2002` (`schema.prisma`, `production.ts:118-121,555-578`). Повтор при потере ответа дубля не создаёт — **ПРОЙДЕНО**.
3. Потеря ответа для очереди безопасна: таймаут 20 с/120 с → ошибка без статуса → `temporary` → запись остаётся `PENDING` и уйдёт повтором (`api.ts:284-285,603-620`). Успех «чужого» 200 (captive-portal) отсекается проверкой поля `data` (`api.ts:242-267`) — **ПРОЙДЕНО**.
4. **Главный пробел контракта:** `close-shift`, `finish-work`, `submit-report` (и `confirm-ppe`, `acknowledge-briefing`, `submit-knowledge`) **не несут `clientCommandId`** — идемпотентности у переходов смены нет; при потере ответа повтор даёт 409 «Смена уже закрыта» (`route.ts:161-176`, `shift-close.ts:41-96`). Данные при этом не теряются (экран перечитывается в `CLOSED`), но перехода ключом не защищены.
5. Сервис-воркера нет: PWA снят, `public/sw*` отсутствует (`next.config.ts:114-116`). Значит нет ни Background Sync, ни офлайн-отдачи страницы: очередь отправляется **только пока открыт экран** и откладывается, если вкладку закрыть (`use-offline-queue.ts:49-70`). Смена пользователя на устройстве не чистит очередь — чужие записи ждут хозяина (`offline-queue.ts:224-230,306-310`). Фото офлайн не поддерживаются вовсе (`api.ts:647-737`).

Найдено: **критично — 0**, **важно — 5**, **мелочь — 5** (всего 10 в таблице ниже; порядок — по значимости).

## Контракт по пунктам (что делает код)

### 1. Что хранится на устройстве — ПРОЙДЕНО
- Ключ хранилища — `localStorage`, ключ `pilingtrack.operator.queue.v1` (`offline-queue.ts:29`). Обоснование выбора localStorage вместо IndexedDB — комментарий `offline-queue.ts:21-24`.
- Элемент очереди: `ownerId`, `ownerName`, `clientCommandId`, `label`, `command`, `queuedAt`, `attempts`, `state` (`PENDING|FAILED`), `lastError` (`offline-queue.ts:34-52`).
- В очередь можно положить **только** `log-production`, `report-incident`, `correct-production` (`offline-queue.ts:67-69`, гейт `isQueueable`, `77-83`).
- Осмотр НАМЕРЕННО не в очереди: двигает фазу смены (`offline-queue.ts:56-66`).
- **Не хранится**: состояние смены (выводится сервером, `operator-mobile-app.tsx:111-115`), фотографии (в очередь не идут, см. п. 8).

### 2. Что и когда отправляется — ПРОЙДЕНО
- Единый хук `useOfflineQueue` шлёт очередь при: монтировании/появлении вошедшего пользователя, событии `online`, возврате на вкладку (`visibilitychange`), таймере каждые 30 с при наличии `PENDING` (`use-offline-queue.ts:8,49-70`), и по кнопкам «Повторить»/«Отправить записи с телефона» (`use-offline-queue.ts:32-41,72-82`).
- Одновременно идёт **одна** отправка: `flushQueue` держит `inFlight` (`offline-queue.ts:422-440`).
- При отправке команды: сначала `enqueue` (запись на диск), затем `postCommand`, при успехе — `resolve` (снятие) (`api.ts:547-621`). Успех снимает запись; отказ по существу (4xx кроме 401/408/425/429) помечает `FAILED` и **не** удаляет (`api.ts:603-609`).

### 3. Идемпотентность на сервере (ключи, уникальные индексы) — ПРОЙДЕНО
- Ключ — `clientCommandId` (uuid, `api.ts:739-742`).
- Уникальные индексы `@@unique([tenantId, clientCommandId])` в `prisma/schema.prisma`:
  `OperatorChecklistExecution:1243`, `OperatorChecklistAnswerRecord:1268`, `OperatorShiftEvidence:1291`, `SafetyIncident:1334`, `PileWork:2206`, `PilePassport:2307`, `LeaderDrilling:2383`, `ReportDowntime:2427`.
- Чтение-дедуп перед записью: `production.ts:118-121` (+ `findByCommand` `production.ts:582-594`), `incidents.ts:61-73`, `checklist.ts:107-111`, `production-corrections.ts:76-77`, `shared.ts:314-333` (`recordEvidence`).
- `P2002` обрабатывается осторожно: команда считается выполненной только если её запись реально найдена повторным чтением (`production.ts:555-578`).

### 4. Потеря ответа — ПРОЙДЕНО
- Таймауты запроса: команда/чтение 20 с, загрузка файла 120 с (`api.ts:284-285`).
- Ошибка без HTTP-статуса (обрыв, таймаут, `status:0`) → `classifyFailure` = `temporary` (`offline-queue.ts:139-144`) → `markAttempt(..., permanent=false)` → `PENDING`, будет повтор (`api.ts:611-620`).
- Чужой ответ 200 (Wi-Fi-портал) не считается успехом: `parse` требует поле `data`, иначе бросает `ApiError(0)` → снова `temporary` (`api.ts:242-267`).
- Для неочередных команд (`close-shift` и др.) спасения нет: 401 → увод на вход (`operator-mobile-app.tsx:451-454`), CSRF-403 → «обновите страницу и повторите» (`api.ts:168-169,523-524`).

### 5. Смена пользователя на устройстве — ПРОЙДЕНО
- Владелец записи — `ownerId` на момент `enqueue` (`offline-queue.ts:224-230,346-357`).
- Чтение очереди фильтрует по владельцу: `readQueue`/`pendingCount` возвращают только «свои» (`offline-queue.ts:228-230,290-296`).
- Чужие записи не отправляются и показываются сменщику счётчиком и именами (`foreignQueueSummary`, `offline-queue.ts:298-310`; баннер `offline-queue-banner.tsx:13-17`).
- Выход чистит `currentUser`, но **не** очередь (`store.ts:105-113`; ключ очереди не трогается). `QueueOwnershipError` защищает от подмены чужого ключа (`offline-queue.ts:203-208,335-337`).

### 6. Закрытие смены с непустой очередью — ПРОЙДЕНО (механизм) / риск в таблице
- Барьер **только на клиенте**: при `pending > 0` кнопка закрытия заменяется на «Отправить записи с телефона», при `failed > 0` — «Повторить отклонённые» (`closing-screen.tsx:69-84,88-114`).
- Сервер `closeShift` про очередь не знает и знать не может (`shift-close.ts:41-96`); проверяет лишь ЕО после работы (`shift-close.ts:58-69`).
- Следствие: закрытие с другого устройства/вкладки/прямым вызовом API при непустой очереди на телефоне — записи потом получат 409 (см. находку №2).

### 7. Обновление сервис-воркера — ПРОЙДЕНО
- Сервис-воркера **нет**: PWA снят 2026-05-24, «no service worker, no manifest» (`next.config.ts:114-116`); в `public/` нет `sw*.js`; в `src/` нет `serviceWorker.register`.
- Значит «обновление SW» неприменимо. Полное обновление страницы (перезагрузка/новая версия бандла) очередь **не роняет**: она в `localStorage` и переживает перезагрузку. Теряется только незафиксированная память вкладки — черновик открытой формы (состояние React), сервер/очередь это не восстанавливают.
- Отправка очереди после перезагрузки возобновляется хуком при монтировании (`use-offline-queue.ts:49-51`).

### 8. Как с фотографиями — ПРОЙДЕНО
- Загрузка фото — **три онлайн-запроса подряд** (получить ссылку → PUT файла → подтвердить), в очередь не кладётся (`api.ts:647-737`).
- Фото привязано к ключу команды: осмотр — `entityId = clientCommandId:itemId`, тип `equipment_defect` (`api.ts:658`); происшествие — `entityId = clientCommandId`, тип `safety_incident` (`api.ts:657-658`, `incidents-tab.tsx:70`).
- Сервер принимает фото только после проверки: `requireConfirmedImages` (осмотр, `shared.ts:343-374`) и `confirmedIncidentImages` (происшествие, `incidents.ts:141-164`) сверяют `mediaId + entityId + userId + uploadStatus='completed' + contentType image/*`.
- Офлайн фото не поддержаны: `uploadPhoto` упадёт, а команды с `mediaIds` (осмотр, происшествие) не в очереди → ни снимок, ни запись не сохранятся, форма останется с ошибкой.
