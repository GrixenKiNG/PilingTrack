# Готовность: почему выключены e2e-тесты tech-readiness и что нужно для их включения

## Итог

Спека `e2e/tech-readiness-production.spec.ts` создана в **единственном** коммите
5ef27bb5 «docs(readiness): define production implementation» (2026-07-30) и
легла в репозиторий **уже со `test.describe.skip`** — никакой последующий коммит
.skip не добавлял. Это проектный e2e-эталон будущей «production» реализации
модуля, написанный по (теперь заменённому) дизайн-контракту, а не по коду.

Запустить спеки «как есть» нельзя ни в одной конфигурации: 0 из 5 тестов
пройдут. Причин три класса, по убыванию жёсткости:

1. **Нет источника аутентификации.** `openIsolatedSession` шлёт заголовки
   `X-Test-Tenant / X-Test-User / X-Test-Role`, но ни одного их потребителя в
   коде нет (нет middleware, нет роута, нет тест-аутентификации) — все прочие
   e2e логинятся через форму `/login`. Сессия не создастся → редирект/401, все
   тесты падают на первом же клике.
2. **Файкстура ничем не защита.** ID `test-tenant-readiness-*`, пользователи и
   сущности не встречаются ни в `prisma/seed.ts`, ни в `seed-test-data.ts`, ни в
   `scripts/*seed*`. Записи с нужными shift/handover/permit/equipment в БД
   некому создать.
3. **Селекторы и тексты разошлись с кодом.** Из ~20 локаторов реально
   существует едва ли четверть; ключевые (testid `tech-readiness-tabs`,
   `current-snapshot`, `shift-<id>`, `handover-<id>`, `permit-<id>`, кнопки
   «начать смену / принять передачу / создать допуск / одобрить», label «риск»,
   «объём работ», «сводка», текст «действующий наряд-допуск обязателен») в
   текущих экранах отсутствуют или заменены.

Вывод по Блокам: **Блок 1 и Блок 2 устарели относительно кода — «включается
как есть» невозможно; проще переписать на фактические экраны, чем чинить по
фрагментам.** Ниже — матрица селекторов и что именно требуется для возврата.

Всего находок: критично 7, важно 8, мелочь 10.

## Выводы по блокам

### Блок 1 «Tech Readiness production role journeys» (spec:26-117)

**Статус: устарел, проще переписать.** Список шагов:
1. operator видит вкладки готовности и не имеет механик/диспетчерских команд (30-33);
2. bypass-проверка: оператор НЕ может принять передачу через API → 403 (35-45);
3. механик создаёт NORMAL допуск, диспетчер одобряет (50-62);
4. механик передаёт смену, диспетчер принимает (64-75);
5. механик+админ двойное согласование ELEVATED (78-92);
6. два диспетчера конкурентно принимают одну передачу → у второго 409 (-recovery) (94-116).

Причины «не включить как есть»:
- блокеры №1-3 (нет аутентификации заголовков, нет фикстуры в БД, вымышленные роли/пользователи) бьют по всем 6 шагам;
- шаг 2 семантически устарел: по capability-defaults.ts:76-94 оператор с 20.08.2026 имеет `readiness.handover.decide` и `shift.authorize` → 403 неверен;
- шаги 3-6 целиком построены на отсутствующих селекторах (см. №8-21, 24-25): «допуски»-вкладки в readiness нет, приёмка/передача называются иначе, ввод полей другой;
- конкурентный 409-флоу (шаг 6) в текущем UI показывает обычный тост (№15), а не открытый «уже принята» dialog.

### Блок 2 «Tech Readiness critical blocker» (spec:119-135)

**Статус: устарел, проще удалить или переписать.** Список шагов:
1. механик открывает вкладку «смены», кликает смену `shift-<id>` (122-123);
2. жмёт «начать смену» и «подтвердить» (124-125);
3. ждёт dialog с текстом «действующий наряд-допуск обязателен» (127-130);
4. ждёт статус «Запланирована» на строке смены и `current-snapshot` = «заблокирована» (131-133).

Причины:
- шаг 2 невозможен: кнопки «начать смену» в коде нет, запуск — «Допустить» у диспетчера (shifts-screen.tsx:202);
- шаг 3: dialog не открывается этим путём, искомый текст отсутствует (№16);
- шаг 4: `shift-<id>` и `current-snapshot` не существуют (№9, 19, 25);
- семантика блокировки при нехватке наряда для оператора (который пускает чистую готовность сам) требует пересборки сценария.

## Не проверено

- Точный HTTP-результат неаутентифицированного обращения к `/admin/to` (401/302/редирект): Playwright не запускался по условию задачи; вывод сделан по отсутствию любого потребителя `X-Test-*`-заголовков (grep 0) и по факту обязательной `user.tenantId`-проверки в bootstrap (src/app/api/readiness/bootstrap/route.ts:23-28).
- Фактический footer-контракт CommandDialog внутри **permits**-экрана (текст подтверждающей кнопки) не проверялся построчно; для shifts-диалога он «Подтвердить действие» (shifts-screen.tsx:311).
- Флага `readiness_shifts_v1/readiness_permits_v1` в инфраструктуре не нашёл в явном виде (bootstrap тянет их из контекста тенанта) — на каких условиях они включены для тестового тенанта, не подтверждено.
- От чего именно редиректит `/admin/to` без сессии (middleware отсутствует) — только предположение на основе права `user.tenantId`.
