## Итог

1. Главное: блок «Проверка» (`deploy-prod.sh:124–139`) не роняет скрипт — при любом исходе печатается «✔ выкачено» (`:141–142`). Нездоровый контейнер и непримененная миграция отчёту об успехе не мешают.
2. Второе по важности: новые миграции определяются по git-HEAD сервера (`deploy-prod.sh:72,76–80`), а не по состоянию БД; после частичного прогона (git pull прошёл, барьер упал) миграция молча выпадет из сборки — ровно та ловушка, о которой предупреждает сам скрипт (`:78`).
3. Третье: у барьера смены поколения нет персистентного маркера — он ставит `restart=no` и останавливает старое поколение (`replace-worker-generation.sh:111,115`) до старта нового (`:129–130`); если процесс убьют жёстко или пропадёт питание, сайт останется лежать, автовозврат не сработает.
4. Четвёртое: серверный `:latest` переключается на новый образ (`deploy-prod.sh:119`) ДО барьера; при обрыве между этими шагами «аварийная» команда из `replace-worker-generation.sh:52–53` поднимет новое поколение без барьера.
5. Пятое: пути выкладки зовут `docker compose` без `-f`/`COMPOSE_FILE` (`deploy-prod.sh:113`, `deploy.yml:83,101`) — применяется ли оверлей `docker-compose.prod.yml` (закрытие портов БД/Redis/MinIO, лимиты) — не проверено, зависит от боевого `.env`.
6. Счёт по severity: критично 3, важно 14, мелочь 10 (всего 27). Отдельный риск — «что остаётся в промежуточном состоянии» (раздел ниже), он частично не покрыт находками, потому что это про отсутствие устойчивого состояния процесса, а не про строку.

### Промежуточные состояния при обрыве (сеть / диск / таймаут / kill)

- **Между шагами 8 и 9** (откатные теги проставлены и старые удалены, образы ещё не переданы): сервис работает на старом образе; откат к текущему поколению возможен, но более старый набор откатных тегов уже удалён (`deploy-prod.sh:100–101`).
- **Во время шага 9** (обрыв передачи/`docker load`): на сервере остаются неполные/безымянные слои, контейнеры не тронуты; чистки нет (`deploy-prod.sh:108`, находка 24).
- **Между `:119` и стартом барьера**: `latest` = новый образ, контейнеры = старые. Обрыв SSH здесь оставляет это состояние неконсистентным; любой последующий `docker compose up -d` поднимет новое поколение без барьера (находка 6).
- **Внутри барьера между STOP и START**: `docker update --restart=no` (`replace-worker-generation.sh:111`) + `compose stop` (`:115`) уже выполнены, контейнеры не перезапустятся сами; восстановление живёт только в памяти процесса (`old[]`, `policies[]`, `recover()` `:8–46`). SIGKILL контейнера-скрипта/хоста или потеря питания — сайт лежит, маркера для восстановления нет (находка 3).
- **После барьера, до конца проверки**: сервис уже новый и работает, а скрипт может умереть — состояние успешной выкладки, о которой никто не узнал; файла-«состояние выкладки» нет нигде.

### Где нет проверки

- Нет проверки, что `migrate` реально применил миграции (`deploy-prod.sh:135–138` только печатает вершину; находка 9).
- Нет проверки состояния `health/deep` по компонентам — печатается только HTTP-код (`:134`; находка 1/10).
- Нет автоматического post-deploy `prod-smoke.mjs` (находка 10).
- Нет гейта по свободному месту до `docker save`/`docker load` (`:104,108`; находка 5).
- Нет проверки, что образ на сервере — тот же, что собран локально (только по тегу `:108,119`; находка 16).
- Нет проверки, что внешние (standalone/systemd/pm2) воркеры остановлены — флаг человеческий (`:52`; находка 12).
