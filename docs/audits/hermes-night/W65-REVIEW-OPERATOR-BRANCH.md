# W65-REVIEW-OPERATOR-BRANCH — независимая проверка правок экранов машиниста

Проверяемая ветка: `owner/operator-flow-0707` (4 коммита над `main`), чтение через `git show <branch>:<path>`, рабочее дерево не переключалось и не менялось.

## Итог

Топ-5:
1. **важно** — простой в списке «Последние записи» на экране машиниста всё ещё печатается в минутах (`operator-work-overview.tsx:61`), хотя правка объявлена «простой только в часах».
2. **важно** — тест `operator-work-overview.test.tsx:21` утверждает «простой в часах, а не в минутах», но фикстура без записей: ветка со минутами не отрисовывается, проверка `queryByText('мин')` проходит вхолостую.
3. **важно** — тест `production.test.ts` («выработка после «Завершить работу» не отвергается») ослаблен до «ошибка не про закрытую смену»; что запись `pileWork.create` реально произошла, больше не проверяется.
4. **важно** — в v2 смена в `HANDOVER_PENDING` даёт шаг `closed` (`shift-flow.ts:187`): сразу после «Завершить работу» оператор видит «Смена успешно завершена, отчёт отправлен», кнопка «Завершить смену» новой панели выключена, дописать выработку негде — цель правки для v2 не достигнута.
5. **важно** — `closeShift` считает итоги отчёта без блокировки смены/отчёта, а выработка теперь принимается и в `HANDOVER_PENDING`: параллельная запись может не попасть в итоги отчёта, остаться в БД со `reportId` уже сданного отчёта.

Дедлок новой блокировки `Equipment ... FOR UPDATE` (пункт задания) не подтверждён: разбор в «Не проверено» — порядок захвата замков не образует цикла ни с одной найденной транзакцией.

## Не проверено

1. **Прогон проверок §6 AGENTS (tsc / lint / test:unit / playwright --list / build) — не выполнен.** Причина: ветку нельзя выполнить без checkout или `git worktree add`, а правило задания — «не менять существующие файлы, создать только отчёт». Все выводы — статический разбор текста ветки через `git show`. Числа тестов и их зелёность не подтверждены.
2. **Дедлок `Equipment ... FOR UPDATE` (пункт задания) — не подтверждён, но и не опровергнут экспериментом.** Что проверено текстом: (а) все транзакции, захватывающие строку Equipment, делают это первым среди строковых замков — `meter-reading.ts:191` (Equipment → MeterReading insert → Equipment update → OutboxEvent insert), `equipment-command.service.ts:25` (Equipment → метаданные), `equipment-metadata.ts:113-123` (Equipment update → тот же путь); (б) обратный порядок дают только `equipment-maintenance.ts:251-266` (MaintenanceRecord → … → Equipment) и `inspection-commands.ts:380-432` (advisory по ключам дефектов → Inspection → MaintenanceRecord → Equipment) — Equipment всегда последний, цикла нет; (в) потребитель снимка готовности (`projection/*`, `snapshot-repository.ts`) строку Equipment не блокирует, поэтому «Equipment → OutboxEvent-insert» против «OutboxEvent FOR UPDATE → … » (`event-handlers.ts:659`, `durable-alert-delivery.ts:44`) цикла не даёт — вставка новой строки не ждёт чужих блокировок. Отдельно замечу: `FOR UPDATE` держится всю транзакцию, а та теперь включает вставку события готовности (и, через карточку, полную правку карточки) — окно блокировки выросло, это риск конкуренции, но не дедлок. Живой проверки на двух параллельных транзакциях не делал.
3. **Геометрия панели шагов в браузере** (наложение с вкладками, `--sb-h/--tb-h`, sticky в v5/v7/v10) — не смотрел; вывод только по CSS.
4. **Полный список e2e, сломанных правкой пяти форм.** Нашёл один конкретный (`e2e/qa-ac/operator-walk.spec.ts`); `e2e/qa/operator-versions.spec.ts` и `e2e/qa/roles-clickthrough.spec.ts` не читал.
5. **`npm run build` и типы Next-маршрутов** — не проверены (нет прогона).
