Статус: предложение для выбора владельцем, задача I, 23.10.2026. Основа исследования: `064e2402dfddaa1a0b4ce6842fa1f113eec4b65e`. Изменений приложения, правил, прав, БД и экранов оператора нет. Это статическое исследование исходного кода; поведение браузера и производственная частота причин здесь не проверялись.

## 1. Вывод и границы

Рекомендуется вариант 1: дополнить существующие подсказки проверяемым результатом действия и ссылкой на нужную запись. Каркас цепочки уже есть: `blocker-guidance.ts` содержит роль и вкладку для всех пяти настраиваемых причин; `ReadinessCentre` показывает подсказку первой блокировки и разрешённый переход, журнал отчётов использует `describeBlockers`. Утверждение «ответственного и следующего действия вообще нет» было бы неверным.

Недостаёт назначенного человека вместо общего названия роли, одинакового представления цепочки для всех причин, связи исправления с новым снимком и явного различения «факт устранён» и «выдано исключение». Эти улучшения не требуют менять решение о допустимости запуска. Для пяти сценариев ниже приоритет предложен по тяжести последствий и полноте процесса; это гипотеза для продуктового планирования, не пять статистически самых частых причин.

## 3. Все причины и кто может устранить факт

Роли в таблице — **существующие значения по умолчанию**, не назначение конкретного работника. Действующая опубликованная матрица организации, ограничения ресурса и режим «Действую как» проверяются сервером; текст роли не даёт полномочие. У администратора при замещении остаются права исполняемой роли. `FOREMAN` и `SAFETY_ENGINEER` сохранены намеренно; у владельца их функции сейчас исполняет администратор. Новых ролей этот документ не вводит.

| Код и человеческий текст | Когда срабатывает; текущая политика по умолчанию | Кто и как устраняет причину сейчас |
| --- | --- | --- |
| `CRITICAL_DEFECT` — «Критический дефект» | Открытый критический дефект **или** открытая заявка `FAULT/REPAIR` с приоритетом `CRITICAL` в авторитетном расчёте. Системное `DENY_START`, нельзя выключить настройкой | `readiness.defect.manage`: ADMIN, DISPATCHER, MECHANIC, SAFETY_ENGINEER по умолчанию — разобрать и закрыть дефект, обоснованно изменить критичность при разборе или отклонить допустимый неразобранный дефект. Открытую критическую заявку тоже нужно завершить по её процессу; закрытие только дефекта не гарантирует исчезновения причины |
| `INSPECTION_BELOW_80` — «Нет осмотра за сегодня» | `inspectionProgress < 0.8`; авторитетный сборщик выдаёт 1 / 0.5 / 0 по наличию сегодняшнего / прежнего / отсутствующего осмотра. Это **не процент ответов**. Включено, `RETURN_TO_OPERATOR` | Завершить подходящий осмотр текущих производственных суток/смены. OPERATOR с `readiness.inspection.manage` — только ЕО своей установки; MECHANIC, SAFETY_ENGINEER, ADMIN имеют это полномочие по умолчанию с ограничениями соответствующего API. Источник — журнал `Inspection` либо предсменный `OperatorChecklistExecution`; новое доказательство должно сохранить тип |
| `MAINTENANCE_OVERDUE_50H` — «ТО просрочено более 50 м/ч» | Строго `maintenanceOverdueHours > 50`, не `>=50`; календарная просрочка отдельно снижает балл, но не запускает это условие. Включено как `WARN_ONLY`, поэтому по умолчанию работу **не блокирует** | MECHANIC / ADMIN с правами обслуживания — выполнить и закрыть ТО с реальными работами и показанием счётчика, проверить следующий срок. Приёмка наряда `/api/maintenance/:id/accept` отдельно требует ADMIN и `maintenance.manage`; не обещать её механику только по readiness-матрице |
| `VALID_WORK_PERMIT_REQUIRED` — «Действующий наряд-допуск обязателен» | `permitValid !== true` либо просрочка; правило по умолчанию **выключено**, действие при включении `DENY_START` | Редактор с `readiness.permit.edit`: MECHANIC, SAFETY_ENGINEER, ADMIN — оформить/передать на согласование. Подписывают DISPATCHER и/или ADMIN согласно политике вида работ и соответствующим approve-правам; редактор не получает право подписи автоматически. При нескольких подписях нужны разные люди |
| `PERMIT_EXPIRED` — «Просроченный наряд-допуск» | `permitExpired`; по умолчанию **выключено**, задано `WARN_ONLY`. Применяется там, где наряды участвуют в правилах | Те же редакторы и согласующие — оформить действующий документ на новый срок и собрать требуемые подписи. Нельзя показывать «продлить в один клик» как существующую функцию |
| `READINESS_RULES_NOT_PUBLISHED` — «Правила готовности не опубликованы» | Нет опубликованного набора: отдельный отказ `DENY_START`, `DENIED`, score 0. Не элемент `BLOCKER_CONDITIONS` | ADMIN с `readiness.rules.manage` — проверить и опубликовать правила; затем дождаться новой авторитетной оценки. Обычный механик/диспетчер не публикует их по умолчанию |

Дополнительно:

- `WORK_PERMIT_MISSING_OPTIONAL` — «Наряд-допуск не оформлен (по правилам не обязателен)», либо текст о закрытии после работ. Выдаётся только если наряды учитываются, обязательность не включена, действующего нет и просрочка уже не объясняет ситуацию. **Не препятствует запуску**, не требовать устранения как допуска. При нынешнем весе PERMIT=0 и выключенных правилах нарядов не появляется.
- Активное условие с `WARN_ONLY` переносится оценщиком из blockers в warnings с тем же кодом condition. Для остальных действий различаются `DENIED`, `RETURN_TO_OPERATOR`, `CONFIRMATION_REQUIRED`. Балл ниже 85 задаёт тон, но сам по себе не создаёт дополнительный запрет.
- `OPERATOR_NOT_CLEARED` — отдельный отказ запуска по документам человека из `application/shifts/commands.ts`, **не** reason code доменного оценщика машины. Администратор/ответственный за документы исправляет документы, затем сервер снова проверяет допуск. `SHIFT_START_BLOCKED` — оболочка ответа с перечисленными выше причинами, не новая причина.
- Существующее письменное исключение `readiness.shift.waive` (ADMIN/DISPATCHER по умолчанию) разрешает пуск при покрытии кодов текущих препятствий, **не устраняет их**. Оно не обходит отдельную проверку документов оператора. Код не исключает из waiver системный `CRITICAL_DEFECT`; это текущее поведение, а не рекомендация расширить полномочия. Само правило безопасности настройками по-прежнему не отключается.

## 4. Что показывается сейчас и где остаются пробелы

Общее: центр готовности показывает авторитетный вердикт, балл, пять этапов, блокировки/замечания, время оценки, версию правил, источники и карточки ролей. Первая блокировка получает подсказку «кто/куда»; переход проверяется на доступность вкладки. «Отчёты» выводят текст причин и общую роль через `describeBlockers`; это история, не очередь назначений. Парк (`fleet-screen.tsx` + `fleet-evidence-panel.tsx`) показывает оценку и источники, отдельно текущие записи, предупреждает, что они могли измениться после оценки. «Смены» предлагает следующий шаг и показывает серверные причины отказа. Это наблюдения из кода, не результат визуального QA.

| Причина | Что уже есть в экранах | Что добавить в выбранном варианте |
| --- | --- | --- |
| Критический дефект | Подсказка «механик → Обслуживание → закрыть/понизить критичность», панель дефектов с разбором/закрытием, связь с нарядом ТО | Отдельно перечислить все блокирующие дефекты и критические заявки; общая роль не отражает всех существующих прав. Показать конкретную запись, выполненное исправление и новый снимок; не предлагать понижение критичности как штатный обход |
| Нет осмотра сегодня | «оператор → Смены → провести осмотр за сегодня»; в центре этап осмотра, в парке журнал механика и история чек-листов машиниста | Сохранить установку/смену при переходе; различить новый/вчерашний/чужой смене осмотр. `INSPECTION` имеет `/inspections/:id`, у `OPERATOR_CHECKLIST` отдельной страницы нет: нельзя строить ложную ссылку с этим id |
| ТО >50 м/ч | «механик → Обслуживание → закрыть наряд», этап обслуживания, заявки/планы и исходные записи | В warnings тоже показать цепочку, фактический перебег, нужный наряд и обновлённый следующий срок; предупреждение не перекрашивать в запрет |
| Нет обязательного наряда | «инженер ОТ → Наряды-допуски → оформить и согласовать», реестр нарядов, этап допуска | Разделить автора и согласующих, показать недостающую подпись. Ссылка доказательства сейчас ведёт в общий `/admin/safety?view=permits`, а не гарантированно в выбранный документ |
| Наряд просрочен | «инженер ОТ → Наряды-допуски → переоформить», срок и состояние в реестре | Показать конкретный истёкший и новый документ, подписантов и момент нового расчёта. Для необязательных нарядов сохранить информационный статус |
| Правила не опубликованы | Авторитетный отказ с русским текстом; карточка администратора ведёт в настройки правил | В `GUIDANCE` для этого кода записи нет. Дать прямой доступный путь «Настройки → Правила», роль ADMIN, публикацию и последующий снимок |

Ни `BlockerGuidance`, ни текущая форма `TriggeredBlocker` не содержат назначенного пользователя, срока исполнения или ссылки «эта причина снята этим событием». История сущностей и аудит уже содержат часть доказательств; не следует утверждать, что подтверждения действий вообще отсутствуют. Пробел — их сборка в единую цепочку конкретной причины. Снимок неизменяем: исправление подтверждается **следующим** снимком и исходной записью, а не редактированием старого.

## 5. Пять приоритетных цепочек и текстовые макеты

Приоритет P1–P5 — гипотеза; для статистического ранжирования отдельно потребуется обезличенный подсчёт reason codes по установке/смене с отделением повторных снимков и предупреждений. В этой задаче реальные данные не использовались. Все строки с именами ниже — условные синтетические примеры, не существующие назначения.

```text
P1  Критический дефект · запуск запрещён
    Причина: DEF-123 / критическая заявка MR-456 [Открыть основание]
    Ответственный: механик (назначенный человек пока не определён)
    Действие: устранить неисправность, закрыть дефект и связанную заявку
    Подтверждение: запись работ → автор/время → новый снимок без этой причины
    Если есть письменное исключение: «Пуск по исключению», причина остаётся видна

P2  Нет осмотра за сегодня · требуется действие оператора
    Установка / смена / производственная дата и часовой пояс
    Ответственный: машинист бригады (имя только из доступного справочника)
    Действие: завершить предсменный осмотр [Перейти к текущей смене]
    Подтверждение: OPERATOR_CHECKLIST или INSPECTION → время → новый снимок

P3  ТО просрочено на 63 м/ч · замечание, работа разрешена текущими правилами
    Ответственный: механик; основание: план / срок / показание счётчика
    Действие: выполнить ТО [Открыть нужный наряд]
    Подтверждение: закрытый наряд + следующий срок → новый снимок без перебега

P4  Нет обязательного наряда · запуск запрещён правилами организации
    Ответственный за оформление: инженер ОТ / замещающий администратор
    Следующий шаг: редактор отправляет документ; затем согласующий подписывает
    [Открыть документ] либо [Открыть реестр], если документа ещё нет
    Подтверждение: актуальная версия и требуемые подписи → новый снимок

P5  Наряд просрочен · серьёзность из опубликованного действия правила
    Ответственный: редактор наряда; ожидаются подписи: роли из вида работ
    Действие: оформить документ на текущий период, получить согласования
    Подтверждение: действующий новый документ → новый снимок без этой причины
```

Ни одна кнопка в макете не считается уже реализованной. При нескольких причинах показать все: первая строка по тяжести/следующему доступному действию не должна скрывать остальные. Для неизвестного кода — оригинальная подпись и безопасное «Обратитесь к администратору»; не придумывать действие. Для отсутствующего/повреждённого/старого снимка — «нет подтверждённых данных», не «причин нет».

Предлагаемые состояния строки: «требуется действие» → «действие записано, ожидаем оценку» → «условие больше не срабатывает» / «сохраняется, открыть основание». Последнее не означает готовность всей машины, если остаются другие причины. Исключение — отдельная пометка, а не состояние «устранено». Новая блокировка после выдачи исключения требует нового решения по существующим правилам покрытия кодов.

- `screens/fleet-screen.tsx`, `fleet-evidence-panel.tsx`, `authoritative-presentation.ts`: сохранить тип источника, установку/смену и момент оценки; точные ссылки только на существующие доступные маршруты.
- `screens/shifts-screen.tsx`, `shift-next-action.ts`: после отказа — действие для конкретной причины, после исправления — ожидание новой оценки и повторный запрос состояния. Не менять полномочия старта.
- `screens/defects-panel.tsx`, `maintenance-screen.tsx`, `permits-screen.tsx`, `settings-workspace.tsx`: адресация записи и возврат к исходной причине; использовать текущие команды и проверки версий.
- Читающий слой: `/api/readiness/current`, `/api/readiness/history`, `/api/readiness/bootstrap`, `/api/readiness/defects` и DTO `api/contracts.ts`; проверить достаточность существующих ссылок прежде, чем расширять ответ. Идентификаторы дефектов сейчас не входят в список `EvidenceReferenceType`, поэтому для точной причинной связи нужно отдельное проектирование контракта, а не угадывание id по тексту.
- Команды уже существуют: `/api/readiness/defects/:id/{triage,resolve,reject}`, `/api/inspections/:id/complete`, `/api/maintenance/:id`, `/api/maintenance/:id/accept`, `/api/readiness/work-permits` и `/:id/{submit,approve,close,revoke}`, `/api/readiness-rules/publish`, `/api/readiness/shifts/:id/start`, `/:id/waiver`. Наличие endpoint не гарантирует доступ любой роли. Осмотр машиниста имеет другой источник и замороженный модуль; расширение его потока — только отдельным решением владельца.
- Экран допуска человека `/admin/safety` остаётся отдельным маршрутом при `OPERATOR_NOT_CLEARED`; не привязывать его к waiver машины. `operator*`, ORION, auth/security, schema и миграции не входят в реализацию без нового разрешённого задания.

Риски: смешать свежие записи с историческим снимком; показать неподходящую сущность по id осмотра; объявить WARN_ONLY запретом; перепутать исполнителя с подписантом; закрыть один источник критической причины и забыть второй; назвать исполнителя без проверки опубликованных прав; ошибочно считать исключение ремонтом. Минимальная приёмка будущего варианта 1: табличное покрытие всех шести причин плюс warning/unknown, тесты доступности действия по effective capabilities, два источника осмотра, несколько причин одновременно, сохранение старых снимков, новое состояние после перерасчёта. Отдельно браузером проверить недоступные ссылки и возврат к выбранной установке; такие проверки здесь не проводились.

## 8. Вопросы к владельцу с ответами по умолчанию

1. С какого варианта начать? **По умолчанию: 1**, без персональных назначений и новых обязанностей.
2. Кто отвечает за технические причины? **По умолчанию: механик**, за осмотр — оператор своей бригады; текст роли показывает ответственность, а кнопки определяются действующими правами. Не снимать текущие права DISPATCHER/SAFETY_ENGINEER молча.
3. Кто оформляет и кто подписывает наряд при отсутствии отдельных пользователей ОТ? **По умолчанию: администратор в соответствующем режиме оформляет**, подписывают реальные разные люди согласно текущей политике вида работ. Не создавать новых пользователей/полномочий из этой спецификации.
4. Нужна ли обязательная вторая проверка ремонта? **По умолчанию: нет**. Сохранить решение 17.10.2026: закрытие критического дефекта одним человеком допустимо, факт отсутствия второго проверяющего остаётся в аудите.
5. Нужно ли ужесточать ТО и обязательность нарядов? **По умолчанию: нет**. Сохранить опубликованную политику; в примерах P4/P5 явно писать, что причина действует только при соответствующих правилах организации.
6. Что считать подтверждением снятия? **По умолчанию: исходная запись действия + новый авторитетный снимок**, где условие больше не срабатывает. Одна зелёная кнопка/успешный HTTP-ответ недостаточны; остальные причины проверяются отдельно.
7. Как показывать письменное исключение, в том числе для критической причины? **По умолчанию: сохранить текущее поведение и отдельную заметную пометку «Пуск по исключению», без слова «устранено»**. Любое изменение допустимости исключения — отдельное решение владельца и отдельная задача с тестами, не изменение правил в этом документе.
8. Кто подхватывает задачу, если механик не назначен? **По умолчанию: показывать «Ответственный не назначен — обратитесь к диспетчеру»**, не назначать автоматически и не обещать уведомление. Персональное назначение отложить до варианта 2.
9. Как ранжировать пять причин? **По умолчанию: использовать предложенную гипотезу тяжести**, затем отдельным согласованным исследованием проверить частоту; не извлекать production-данные ради этого документа.
