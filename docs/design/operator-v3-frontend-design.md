## 1. Решение

`/operator/v3` реализуется как единое рабочее место оператора внутри существующей оболочки PilingTrack. Экран получает один авторитетный снимок рабочего места из `GET /api/operator/v3/workplace`, показывает семь фаз маршрута и отправляет отдельные деловые команды. Клиент не вычисляет этап, техническую готовность, критичность дефекта, разрешённость действия или итог передачи.

Основной принцип клиентской реализации:

> сервер определяет, что разрешено и почему; клиент надёжно показывает решение, собирает доказательства и доставляет команды.

Для каждой изменяющей операции применяется порядок «сначала защищённая локальная запись, затем отправка». Идентификатор команды, номер устройства, фактическое время, ожидаемая версия и тело команды фиксируются до первого сетевого запроса. Потеря ответа после успешного серверного сохранения поэтому не создаёт двойную запись: повтор использует те же данные и тот же ключ повторной отправки.

Производственный код `/operator`, `/operator/v2` и общих компонентов этим документом не изменяется. Они рассматриваются только как источник проверенных взаимодействий и известных ошибок.

## 2. Проверенное текущее состояние клиента

### 2.1. Общая оболочка

`src/app/(app)/layout.tsx` уже предоставляет оператору:

- проверку и восстановление сеанса;
- верхнюю область PilingTrack;
- баннер режима «Действую как»;
- границу непредвиденной ошибки;
- общую нижнюю навигацию роли оператора;
- уважение настройки уменьшенного движения.

`v3` не рисует вторую шапку продукта, второе меню роли или собственную копию выхода. Он добавляет только внутреннюю область установки, маршрут смены, рабочую карточку и действия безопасности.

Текущая оболочка специально скрывает общую нижнюю навигацию для `/operator/v2`. Для `/operator/v3` это решение не переносится. Общая навигация сохраняется, а закреплённая область действий v3 размещается выше неё через одну переменную высоты оболочки. Одновременно исправляется определение активного пункта «Смена» для вложенного адреса `/operator/v3`.

### 2.2. Действующий `/operator`

`src/components/piling/operator-dashboard.tsx` переиспользует реальные серверные команды и `getOperatorShiftFacts`, но определяет текущую фазу функцией `resolveShiftPhase` на клиенте. Для v3 это запрещено: после обновления вкладки, смены устройства или изменения правила клиент не должен выводить другое состояние, чем сервер.

Полезно переиспользовать смысл существующих взаимодействий:

- выбор только из назначенных установок;
- создание смены;
- проверки до и после работы;
- показания моточасов;
- начало смены с повторной серверной оценкой;
- отчёт и передача.

Не переиспользуются как источник решения:

- `src/components/piling/operator/shift-phase.ts`;
- клиентская сборка препятствий из отдельных фактов;
- показ балла готовности;
- скрытие постоянных действий по номеру этапа.

### 2.3. Незавершённый `/operator/v2`

`/operator/v2` доказал полезность одного последовательного экрана и полноэкранных форм, но его `resolveV2State` принимает временные признаки `accepted`, `zoneChecked` и `finishing`. Получение установки, рабочая зона и намерение завершить работы живут только в памяти вкладки. После перезагрузки они теряются и могут изменить показанный шаг без серверного факта.

В v3 запрещено переносить:

- `accepted`, `zoneChecked`, `finishing` и аналогичные флаги как деловое состояние;
- собственную нижнюю навигацию `BottomTabs`;
- локальное завершение шага последней отметкой;
- сообщение об успехе без подтверждённой серверной записи;
- поиск отчёта только по объекту и дате;
- выбор оператором критичности дефекта;
- завершённый экран, который называет смену закрытой до фактического принятия передачи.

Из v2 допустимо переиспользовать после переработки только приёмы представления: крупные области нажатия, одна главная кнопка, полноэкранная форма на телефоне, ввод количества крупными кнопками и возвращение на тот же шаг.

### 2.4. Существующая клиентская инфраструктура

В проекте уже есть:

- `authFetch` для запросов с текущим сеансом;
- Zod для проверки ответов на границе;
- компоненты shadcn/Radix для диалогов, вкладок, полей и предупреждений;
- `sonner` для кратких уведомлений;
- токены `background`, `card`, `signal`, `success`, `warning`, `destructive`, `info`;
- `pt-safe`, `pb-safe`, `hit-target` и поддержка уменьшенного движения;
- `PilingIcon` и общий набор русских обозначений;
- Vitest, Testing Library и Playwright.

В проекте нет библиотеки запросов и библиотеки для IndexedDB. Для первого выпуска новая общая зависимость не требуется: состояние экрана ведётся локальным поставщиком React, а IndexedDB закрывается малым типизированным адаптером. Если объём миграций локальной базы станет больше двух версий, выбор отдельной библиотеки оформляется самостоятельным решением.

## 3. Границы ответственности

### 3.1. Клиент обязан

- проверить входной снимок и ответы команд по схеме;
- показывать серверные русские названия, объяснения и действия;
- никогда не выводить технический код человеку;
- создать устойчивую команду до первой попытки отправки;
- сохранить разрешённую локальную команду и вложения зашифрованно;
- соблюдать срок, область и перечень действий ограниченного разрешения;
- показывать подтверждённое, ожидающее и противоречивое состояние отдельно;
- после подтверждения команды получить или принять новый авторитетный снимок;
- после `409` и `422` перечитать рабочее место и предложить серверное действие восстановления;
- оставить дефект, опасное событие и фотографию доступными на каждой фазе;
- возвращать фокус после закрытия формы;
- не терять локально подтверждённый ввод при перезагрузке и восстановлении связи.

### 3.2. Клиент не имеет права

- вычислять техническую готовность из отдельных фактов;
- определять фазу смены по `Shift.state`;
- объявлять действие разрешённым только по роли из Zustand;
- подставлять резервную организацию, пользователя или установку;
- расширять перечень разрешённых без связи команд;
- самостоятельно разрешать противоречие перезаписью сервера;
- считать уведомление или изменение React-состояния доказательством делового успеха;
- показывать проценты и баллы готовности;
- сохранять токен, секрет разрешения или незашифрованное вложение в `localStorage`;
- изменять закрытую историю вместо создания исправляющей команды.

## 4. Архитектура клиентского модуля

```text
Страница /operator/v3
└── Граница рабочего места
    ├── Поставщик состояния рабочего места
    │   ├── Клиент снимка
    │   ├── Исполнитель команд
    │   ├── Защищённое локальное хранилище
    │   ├── Очередь отправки
    │   └── Наблюдатель связи и других вкладок
    └── Экран рабочего места
        ├── Область установки и обмена
        ├── Маршрут из семи фаз
        ├── Карточка текущего шага
        ├── Техническая готовность
        ├── Главное действие
        ├── Постоянные действия безопасности
        ├── Журнал смены
        ├── Сведения об установке
        ├── Очередь отправки
        └── Область сообщений
```

### 4.1. Разделение слоёв

| Слой | Ответственность | Не делает |
|---|---|---|
| договор | проверяет форму серверного ответа и преобразует её во внутренний тип | не исправляет отсутствующие деловые факты догадкой |
| доступ к данным | выполняет чтение и команды, собирает заголовки | не показывает уведомления и не выбирает экран |
| хранилище | шифрует снимок, команды, черновики и вложения | не принимает деловые решения |
| согласование | сопоставляет очередь, ответы и новый снимок | не переписывает противоречие |
| состояние экрана | хранит загрузку, открытые панели, ввод и состояние команд | не хранит этап как независимый клиентский факт |
| представление | отображает нормализованную модель и отправляет намерения | не знает адресов запросов и технических кодов ошибок |

### 4.2. Владение состоянием

Глобальный Zustand остаётся только источником текущего сеанса и общих настроек приложения. Снимок смены не помещается в глобальное хранилище: он принадлежит маршруту `/operator/v3`, содержит чувствительные рабочие сведения и должен очищаться при смене пользователя.

`OperatorWorkplaceProvider` использует `useReducer` для конечного набора состояний:

```ts
type WorkplaceViewState =
  | { kind: 'initial-loading' }
  | { kind: 'ready'; snapshot: OperatorWorkplace; refreshedAt: string }
  | { kind: 'refreshing'; snapshot: OperatorWorkplace; refreshedAt: string }
  | { kind: 'stale'; snapshot: OperatorWorkplace; refreshedAt: string; error: UserFacingError }
  | { kind: 'fatal'; error: UserFacingError }
  | { kind: 'identity-required' };
```

Открытая форма, активная вкладка, раскрытые доказательства и положение прокрутки являются временным интерфейсным состоянием. Этап, рабочий режим, решение готовности, список допустимых действий и итог передачи всегда читаются только из `snapshot`.

## 5. Единый серверный договор

### 5.1. Каноническое чтение

Единственный источник экрана — `GET /api/operator/v3/workplace?equipmentId={назначенная установка}`. Организация и оператор не передаются в параметрах. Ответ соответствует разделу 5 серверного проекта и разделу 12 спецификации интерфейса.

На границе используются два типа:

1. `OperatorWorkplaceWire` — точная форма ответа маршрута, проверяемая Zod;
2. `OperatorWorkplace` — нормализованная клиентская модель с техническими именами полей.

Преобразование выполняется один раз в `normalize-workplace.ts`. Компоненты не читают необработанный ответ. Если сервер использует русские имена полей договора, нормализатор переводит их во внутренние технические имена. Это не меняет пользовательский язык: все видимые названия, пояснения, причины и действия остаются русскими строками сервера.

Минимальная внутренняя модель:

```ts
interface OperatorWorkplace {
  snapshotId: string;
  stateVersion: number;
  serverTime: string;
  operator: OperatorIdentity;
  assignments: EquipmentAssignment[];
  equipment: EquipmentSummary | null;
  shift: ShiftSummary | null;
  phase: ShiftPhasePresentation;
  phases: ShiftPhasePresentation[];
  workMode: WorkModePresentation;
  readiness: ReadinessPresentation;
  primaryAction: AllowedAction | null;
  persistentActions: AllowedAction[];
  inspections: InspectionPresentation;
  workZone: WorkZonePresentation;
  meters: MeterPresentation;
  activeInterval: ActiveWorkInterval | null;
  production: ProductionSummary;
  defects: DefectSummary[];
  safetyIncidents: SafetyIncidentSummary[];
  report: ShiftReportSummary | null;
  handover: HandoverSummary | null;
  exchange: ExchangePresentation;
  responsibleContacts: ResponsibleContact[];
}
```

Схема отклоняет отсутствующие обязательные поля. Для расширяемых массивов доказательств неизвестные дополнительные поля допускаются, но неизвестное значение решения, состояния оценки, состояния обмена или действия не выводится напрямую. Экран показывает «Состояние пока не поддерживается», сохраняет безопасный режим без производственного действия и отправляет диагностическое событие без личных данных.

### 5.2. Справочник действий

Сервер возвращает допустимые действия кодами и русскими названиями. Клиентский `action-registry.ts` содержит только привязку известного кода к типу формы и исполнителю:

```ts
type ActionDefinition = {
  kind: 'command' | 'form' | 'navigation' | 'device';
  open?: OperatorFormId;
  command?: OperatorCommandName;
  requiresConfirmation?: boolean;
};
```

Справочник не определяет, разрешено ли действие. Кнопка появляется только при наличии действия в серверном снимке. Поле `разрешено: false` сопровождается серверной причиной и не заменяется проверкой роли на клиенте.

Неизвестный код не приводит к универсальному запросу. Он становится безопасно недоступным элементом «Действие пока не поддерживается» с кнопкой «Обновить состояние».

### 5.3. Командный конверт

Каждая команда хранится в локальном конверте:

```ts
interface StoredOperatorCommand {
  commandId: string;
  commandName: OperatorCommandName;
  routeTemplate: string;
  method: 'POST' | 'PUT' | 'PATCH';
  aggregateId: string;
  expectedVersion: number;
  deviceId: string;
  deviceSequence: number;
  occurredAt: string;
  createdAt: string;
  offlineAuthorization: string | null;
  body: unknown;
  bodyDigest: string;
  attachmentRefs: string[];
  dependsOn: string[];
  state: 'draft' | 'ready' | 'sending' | 'confirmed' | 'retryable' | 'conflict' | 'rejected' | 'waiting-attachment';
  attempts: number;
  lastError: UserFacingError | null;
}
```

При отправке используются заголовки из серверного проекта:

- `Idempotency-Key` = `commandId`;
- `If-Match` = сильная метка из `aggregateId` и `expectedVersion`;
- `X-Device-Id`;
- `X-Device-Sequence`;
- `X-Occurred-At`;
- `X-Offline-Authorization` только для созданного без связи действия.

Поле `expectedVersion` не дублируется в новом теле запроса. Если временный серверный адаптер требует его, значение формируется только внутри адаптера API и обязано совпасть с `If-Match`.

### 5.4. Ответ команды

Ответ команды проверяется отдельно от снимка. После результата `выполнено` или `уже выполнено` клиент:

1. сохраняет серверный результат рядом с командой;
2. помечает команду подтверждённой;
3. применяет новый снимок только если сервер вернул полный снимок и его версия не ниже текущей;
4. иначе запрашивает `GET /api/operator/v3/workplace`;
5. удаляет зашифрованное тело команды после подтверждённого чтения, сохраняя только безопасную квитанцию до конца смены.

Пользовательский успех показывается только после пункта 2. Для локальной очереди применяется отдельная формулировка «Сохранено на устройстве».

## 6. Загрузка и обновление

### 6.1. Первичная загрузка

1. Общая оболочка подтверждает сеанс.
2. `OperatorWorkplaceProvider` открывает локальную базу пользователя и устройства.
3. Если есть последний проверенный снимок той же организации и пользователя, он может быть показан как устаревший с явной датой.
4. Параллельно отправляется `GET /api/operator/v3/workplace` без идентификатора пользователя и организации.
5. Новый ответ проходит Zod, нормализацию и проверку монотонности версии.
6. Снимок сохраняется зашифрованно и становится текущим.

Первые две секунды виден каркас с объявлением «Загружаем текущую смену». После двух секунд появляется текст «Загрузка занимает больше времени», но запрос не дублируется.

Если свежего ответа нет, а локальный снимок существует, показывается состояние `stale`: «Показано состояние на 08:14. Проверяем обновления». Производственное главное действие недоступно, если снимок или ограниченное разрешение не доказывают его допустимость.

### 6.2. Повторное чтение

Снимок обновляется:

- после каждой подтверждённой команды;
- после восстановления связи;
- после возвращения вкладки в видимое состояние, если последняя проверка старше 30 секунд;
- после сообщения другой вкладки о подтверждённой команде;
- по явному действию «Обновить»;
- не чаще одного фонового запроса за 30 секунд и только при видимой вкладке.

Повторные причины объединяются одним `AbortController` и одним выполняющимся обещанием. Более старый ответ не заменяет снимок с большей `stateVersion`. Выбор другой назначенной установки отменяет запрос предыдущей и загружает новый снимок.

### 6.3. Межвкладочная согласованность

`BroadcastChannel('pilingtrack-operator-v3')` передаёт только безопасные сигналы: пользователь, установка, номер версии и факт изменения очереди. Тела команд, комментарии, фотографии и разрешения не передаются. Получив большую версию, вкладка перечитывает серверный снимок. Одновременно отправляет очередь только вкладка, владеющая краткой блокировкой в IndexedDB.

## 7. Выполнение команд

### 7.1. Общий поток

```text
Намерение оператора
  → проверка формы
  → создание commandId и номера устройства
  → шифрование и атомарная запись команды
  → попытка отправки
  → серверная квитанция
  → обновление снимка
  → подтверждение человеку
```

Кнопка блокируется после первой активации и показывает конкретный глагол: «Сохраняем», «Начинаем смену», «Передаём установку». Повторное касание не создаёт новую команду. Повтор после сетевой ошибки использует существующую команду.

### 7.2. Подтверждения

Подтверждение обязательно для:

- начала смены;
- завершения производственных работ;
- безопасной остановки;
- возобновления после остановки;
- передачи установки;
- закрытия без принимающего;
- исправления подтверждённой записи.

Текст повторяет следствие: «После подтверждения производственные записи будут закрыты, и начнётся проверка после работ». Общая формулировка «Вы уверены?» не используется.

Производственная запись, фотография и некритичное наблюдение сохраняются без второго подтверждения. Доступное исправление приходит в следующем серверном снимке.

### 7.3. Сопоставление ошибок

`api-error.ts` проверяет серверный объект `ошибка` и создаёт `UserFacingError`. Поля `заголовок`, `объяснение`, `условие` и русское название действия используются без замены техническим текстом браузера.

| Ответ | Поведение клиента |
|---|---|
| `401` | остановить отправку, сохранить очередь, запросить повторный вход |
| `403` | показать серверное ограничение, не предлагать повтор без изменения условий |
| `404` | не раскрывать существование чужой сущности; обновить назначения |
| `409 STATE_VERSION_CONFLICT` | пометить команду «Обнаружено противоречие», перечитать снимок, показать обе квитанции |
| `409 IDEMPOTENCY_KEY_REUSED` | остановить команду как повреждённую, не создавать новый ключ автоматически |
| `409 COMMAND_IN_PROGRESS` | оставить тот же ключ и повторить чтение квитанции с задержкой |
| `422 REQUIRED_ACTION_INCOMPLETE` | обновить снимок и открыть серверное действие устранения |
| `422 READINESS_BLOCKED` | показать «Работа запрещена», условие и следующее действие |
| `422 OFFLINE_AUTHORIZATION_EXPIRED` | запретить производственное действие, сохранить данные, предложить безопасную остановку |
| `5xx` или нет ответа | оставить команду в очереди и показать «Данные не потеряны» |
| неверная схема ответа | перейти в безопасное состояние, показать номер запроса и не использовать частичные данные |

Клиент не заменяет серверное объяснение собственным предположением. Локальный словарь нужен только для доступного названия неизвестной технической ситуации и никогда не меняет серверное решение.

## 8. Защищённая локальная очередь

### 8.1. Хранилище

Используется отдельная база IndexedDB `pilingtrack-operator-v3`, разбитая по организации, пользователю и устройству. Версия 1 содержит:

| Хранилище | Содержимое |
|---|---|
| `metadata` | версия схемы, текущий пользователь, устройство, блокировка отправителя |
| `snapshots` | последний проверенный снимок и серверное время |
| `drafts` | незавершённые формы с временем изменения |
| `commands` | командные конверты и квитанции |
| `attachments` | зашифрованные части файлов, контрольная сумма, состояние загрузки |
| `authorizations` | подписанные ограниченные разрешения и срок действия |

`localStorage` не используется ни для одного делового факта. Хранилище проектируется с явными миграциями, транзакциями и тестом восстановления после прерывания записи.

### 8.2. Шифрование

При регистрации доверенного устройства создаются:

- непереносимый ключ подписи устройства Web Crypto;
- непереносимый ключ шифрования AES-GCM;
- случайный вектор и контекст целостности для каждой записи.

Ключи хранятся как `CryptoKey` в IndexedDB и не экспортируются приложением. Контекст целостности включает организацию, пользователя, устройство, тип записи и её идентификатор, чтобы зашифрованное тело нельзя было незаметно переставить между областями.

Это защищает данные на диске и от случайного чтения другим пользователем устройства, но не является защитой от выполняющегося в том же источнике вредоносного сценария. Поэтому обязательны строгая политика загрузки сценариев, отсутствие сторонних сценариев на экране оператора, отзыв устройства и очистка подтверждённых данных.

### 8.3. Вложения

Фотография сжимается только до разрешённых сервером размера и формата, затем получает контрольную сумму SHA-256 и сохраняется зашифрованными частями не более 1 МиБ. Оригинал не удаляется до подтверждения локальной транзакции. Перед сохранением клиент проверяет доступную квоту и запрашивает постоянное хранилище браузера, когда оно поддерживается.

Загрузка выполняется отдельно по выданной сервером ссылке. Команда с обязательной фотографией остаётся `waiting-attachment`, пока контрольная сумма вложения не подтверждена. Успех делового события до этого не показывается.

### 8.4. Очистка

- подтверждённые тела команд и вложения удаляются после серверного чтения, доказывающего эффект;
- безопасные квитанции хранятся до закрытия смены и ещё 24 часа;
- устаревшие снимки удаляются после получения нового;
- выход пользователя блокирует отображение данных и удаляет расшифрованные значения из памяти;
- непереданные команды не удаляются при выходе и доступны только тому же пользователю после повторной проверки личности;
- отзыв устройства запрещает отправку и требует передачи устройства ответственному сотруднику; автоматическая подмена новым устройством запрещена.

## 9. Работа без связи

### 9.1. Состояние связи не равно полномочию

`navigator.onLine` используется только как сигнал для попытки связи. Право продолжать действие определяется действующим подписанным разрешением сервера, его областью, сроком и перечнем команд.

Экран различает:

- «Все данные переданы»;
- «Есть данные для отправки: N»;
- «Отправляем данные»;
- «Нет связи»;
- «Обнаружено противоречие»;
- «Срок разрешённой работы без связи истёк».

### 9.2. Разрешённые локальные действия

Без ограниченного разрешения можно безопасно сохранить проверку, фотографию, дефект, опасное событие, производственную запись и черновик отчёта, как допускает серверный проект. Это поздние факты, а не подтверждённые серверные переходы.

Пуск, снятие препятствия, возобновление, передача и закрытие недоступны без явного разрешения и необходимых серверных фактов. Истечение срока не удаляет данные. Главное производственное действие исчезает, а при требовании правила показывается «Подтвердить безопасную остановку».

Если подписанный пакет разрешает переход без связи, клиент показывает только предусмотренный пакетом предварительный результат с подписью «Сохранено на устройстве, подтверждение сервера ожидается». Клиент не выводит новую фазу из `Shift.state` и не расширяет результат. Окончательной становится только версия из последующего снимка.

### 9.3. Синхронизация

`QueueSynchronizer` отправляет до 100 команд или 2 МиБ без вложений в `POST /api/operator/v3/sync` строго по возрастанию `deviceSequence`.

Алгоритм:

1. получить межвкладочную блокировку отправителя;
2. проверить действующий сеанс и регистрацию устройства;
3. сначала загрузить обязательные вложения, готовые к отправке;
4. выбрать непротиворечивую последовательность команд;
5. отправить пакет;
6. записать независимый результат каждой команды одной транзакцией IndexedDB;
7. остановить зависимую критическую цепочку после противоречия или ожидаемого вложения;
8. перечитать рабочее место;
9. сообщить другим вкладкам только новую версию и размер очереди.

Повтор номера устройства допустим только с той же контрольной суммой. Новый ключ для отвергнутой команды автоматически не создаётся.

### 9.4. Предварительное представление

Очередь не изменяет авторитетный снимок. В журнале поверх снимка показывается отдельный раздел «Сохранено на устройстве» с непереданными событиями. Допустимый предварительный переход отображается только если подписанное разрешение содержит серверно определённое представление результата. Он визуально отделён пунктирной рамкой и никогда не называется «выполнено» или «закрыто».

После синхронизации предварительная запись заменяется серверным событием по `commandId`. Если сервер отклонил действие, обе записи сохраняются в очереди и журнале до решения ответственного.

## 10. Состояния интерфейса

### 10.1. Каркас и медленная загрузка

Каркас повторяет геометрию верхней области, текущего шага, маршрута и технической готовности. Он не содержит фиктивной кнопки. Текст для программы экранного доступа обновляется с «Загружаем текущую смену» на «Загрузка занимает больше времени».

### 10.2. Последний снимок без свежего ответа

Последний снимок остаётся читаемым, но получает общую метку времени. Действия фильтруются только по подписанному разрешению; отсутствие ответа не превращает вчерашний список действий в разрешение сегодня.

### 10.3. Нет назначенной установки

Показываются точные русские тексты спецификации, контакт ответственного при наличии и одно действие «Обновить». Произвольный ввод идентификатора установки отсутствует.

### 10.4. Смена на другом устройстве

Показываются установка, время начала и разрешённые сведения об устройстве. «Продолжить существующую смену» отправляет отдельную команду повторной проверки личности; создание второй смены недоступно.

### 10.5. Безопасная остановка

При серверном требовании остановки:

- производственные формы и кнопки убираются;
- правая колонка и мобильная панель безопасности раскрываются;
- единственным главным действием становится «Подтвердить безопасную остановку»;
- инструкция остаётся видимой до серверного подтверждения;
- возобновление появляется только после новой актуальной оценки.

### 10.6. Непредвиденная ошибка представления

Граница ошибки сохраняет общую оболочку и показывает «Не удалось показать текущий шаг», номер запроса, «Повторить» и постоянно доступное «Сообщить о проблеме», если личность и установка известны. Она не очищает очередь и не утверждает, что действие не сохранилось.

## 11. Компонентная структура

### 11.1. Корневые компоненты

```text
OperatorV3Page
└── OperatorWorkplaceBoundary
    └── OperatorWorkplaceProvider
        └── OperatorWorkplaceScreen
            ├── EquipmentHeader
            ├── DesktopPhaseRail / MobilePhaseSummary
            ├── CurrentStepCard
            ├── ReadinessPanel
            ├── PersistentSafetyActions
            ├── RecentShiftEvents
            └── OperatorActionDock
```

`CurrentStepCard` выбирает компонент фазы по `phase.number`, полученному с сервера. Выбор отвечает только за форму представления. Он не проверяет факты и не продвигает фазу.

### 11.2. Компоненты фаз

| Фаза | Компонент | Основные формы |
|---|---|---|
| 1. Допуск оператора | `OperatorClearanceStep` | просмотр документов и действия устранения |
| 2. Получение установки | `EquipmentAcceptanceStep` | выбор назначения, доказательства получения, принятие передачи |
| 3. Проверки до работы | `PreWorkChecksStep` | проверка установки, рабочей зоны, моточасы |
| 4. Подготовка и допуск | `WorkAuthorizationStep` | условия, доказательства, подтверждение замечаний, начало смены |
| 5. Работа | `ActiveWorkStep` | производственная запись, перерыв, простой, обслуживание |
| 6. Завершение смены | `ShiftCompletionStep` | завершение работ, проверка после работ, конечные моточасы, отчёт |
| 7. Передача установки | `EquipmentHandoverStep` | передача, ожидание принятия, итог фактического закрытия |

Прерывание `SafeStopPanel` располагается над компонентом фазы и заменяет его главное действие, но не добавляет восьмую фазу.

### 11.3. Формы

На телефоне формы открываются полноэкранным `Dialog` с закреплённым заголовком и действием над клавиатурой. На настольном экране используется боковая панель шириной до 560 точек. Один и тот же компонент формы получает вариант компоновки из контейнера; деловой код не дублируется.

Каждая форма разделена на:

- схему локального черновика;
- поля наблюдаемых фактов;
- подготовку тела команды;
- состояние вложений;
- серверные ошибки полей;
- итоговую квитанцию.

Форма дефекта не содержит выбора критичности. Она собирает наблюдаемые признаки. Форма опасного события первой показывает инструкцию безопасного поведения. Фотография всегда содержит понятную подпись назначения и состояние загрузки.

## 12. Компоновка

### 12.1. Телефон, 320–480 точек

Порядок:

1. существующая глобальная шапка;
2. область установки, объекта и связи в две строки;
3. компактное решение о продолжении;
4. карточка текущего шага;
5. раскрываемые причины и доказательства;
6. свёрнутый маршрут «Допуск — Работа — Передача»;
7. закреплённая область одного главного действия и кнопки «Безопасность»;
8. существующая нижняя навигация роли оператора.

Переменная `--app-bottom-nav-height` задаётся общей оболочкой. `OperatorActionDock` использует её в нижнем отступе и добавляет `env(safe-area-inset-bottom)` только один раз. Последнее поле получает прокрутку с запасом под обе нижние области.

Маршрут по умолчанию свёрнут. Полный список семи фаз открывается в панели и позволяет просматривать только уже доступные доказательства. Горизонтальная карусель не используется.

### 12.2. Промежуточный экран, 768–1023 точки

Две колонки:

- слева маршрут 240 точек;
- справа текущий шаг;
- техническая готовность, безопасность и журнал идут ниже текущего шага.

При увеличении текста до 200 процентов компоновка переходит в одну колонку без потери действия.

### 12.3. Настольный экран, от 1024 точек

Три зоны:

- 240–280 точек — маршрут;
- 560–760 точек — текущий шаг и единственное главное действие;
- 280–360 точек — техническая готовность, связь, безопасность и краткий журнал.

Ширина центральной зоны ограничена ради читаемости. Карточка не растягивается на весь монитор. Общая операторская навигация остаётся частью оболочки, административная боковая панель не добавляется.

## 13. Визуальная система

Используются существующие токены `globals.css`:

- `signal` — единственное главное действие;
- `success` — подтверждённое выполнение и разрешение;
- `warning` — замечание и приближение срока;
- `destructive` — опасное событие, запрет и безопасная остановка;
- `info` — нейтральная проверка или состояние обмена;
- `card`, `background`, `border`, `muted` — поверхности и иерархия.

Цвет не является единственным носителем смысла. Каждое состояние имеет знак и русский текст. Синие, зелёные и фиолетовые самодельные значения v2 не переносятся. Новая тёмная тема не вводится: действующая система рассчитана на читаемость на улице и уже явно отключает автоматическую тёмную схему.

Одна заполненная акцентная кнопка разрешена только в `OperatorActionDock`. Остальные действия используют контурный или текстовый стиль. Красная заполненная кнопка применяется только для подтверждения опасного действия или безопасной остановки.

## 14. Русские пользовательские термины

Все видимые строки находятся в `operator-v3-labels.ts` либо приходят с сервера в русских полях. Технические перечисления не используются как резервный текст.

Обязательные соответствия:

| Внутренний смысл | Видимый текст |
|---|---|
| готовность допускает | Работа разрешена |
| готовность допускает с условиями | Работа разрешена с замечаниями |
| готовность запрещает | Работа запрещена |
| решение отсутствует | Недостаточно данных |
| блокирующее условие | Препятствие |
| предупреждающее условие | Замечание |
| список проверки | Проверка |
| источник подтверждения | Доказательство |
| действие без сети | Работа без связи |
| очередь пуста | Все данные переданы |
| есть очередь | Есть данные для отправки |
| конфликт версий | Обнаружено противоречие |
| список событий | Журнал смены |

Проверка текста запрещает попадание на экран `ALLOW`, `DENY`, `STALE`, `SYNC_CONFLICT`, `OFFLINE`, `checklist`, `workflow`, `score`, `percent` и названий внутренних состояний. Название продукта PilingTrack, обозначения модели установки и нормативные маркировки сохраняются как собственные имена.

## 15. Доступность

- на странице один `h1` — «Смена оператора»; фазы и панели имеют последовательные `h2` и `h3`;
- предусмотрена ссылка «Перейти к текущему шагу» перед общей шапкой содержимого;
- загрузка, успех, ошибка, изменение фазы и состояние обмена объявляются через отдельные области `role="status"` и `role="alert"`;
- `aria-busy` ставится на рабочую карточку, а не на всю страницу;
- препятствие связано с главным действием через `aria-describedby`;
- текущая фаза получает `aria-current="step"`;
- состояние отметки задаётся нативным `checkbox`, а не только рисунком;
- все кнопки имеют текстовое имя без зависимости от пиктограммы;
- минимальная область касания на телефоне — 48 × 48 точек;
- диалог удерживает фокус, закрывается клавишей Escape только при сохранённом черновике или подтверждении потери ввода и возвращает фокус на открывшую кнопку;
- после серверной ошибки фокус переходит к сводке ошибок, а каждое поле связано с сообщением;
- порядок клавиатуры совпадает с визуальным;
- при 200 процентах нет двухмерной прокрутки и потери закреплённого действия;
- `prefers-reduced-motion` отключает переходы и изменение масштаба;
- режим повышенной контрастности проверяется отдельно; знак и рамка сохраняют смысл без фонового цвета;
- таймер не объявляется каждую секунду: программа экранного доступа получает обновление не чаще одного раза в минуту.

## 16. Производительность и устойчивость

- первоначальный снимок загружается одним запросом;
- тяжёлые формы, журнал, сведения об установке и очередь загружаются динамически после открытия;
- фотографии не декодируются в основном потоке в полном разрешении;
- список журнала виртуализируется только после 200 записей; до этого используется обычный семантический список;
- фоновое обновление не выполняется в скрытой вкладке;
- одна вкладка владеет отправкой очереди;
- снимок и ответы не сериализуются повторно в `localStorage`;
- телеметрия не содержит комментарии, фотографии, документы, личные коды и точное местоположение;
- обработчик `beforeunload` не пытается отправить деловую команду; надёжность обеспечивает предварительная запись в IndexedDB;
- служебный работник первого выпуска не выполняет деловые команды без активного подтверждённого сеанса. Фоновая отправка может быть добавлена только с отдельной моделью полномочий.

## 17. Телеметрия интерфейса

Разрешённые события:

- открытие текущего шага;
- длительность фазы;
- открытие формы и отказ от неё;
- вид причины отказа команды;
- повтор отправки;
- количество и возраст команд очереди;
- восстановление после потери связи;
- требование безопасной остановки;
- время от препятствия до новой актуальной оценки.

Событие содержит версию интерфейса, номер фазы, код вида действия, состояние связи и длительность. Свободный текст, имя, фотография, документы, координаты и полное содержимое серверной ошибки исключаются. `requestId` допустим только в диагностической записи ограниченного доступа.

## 18. Стратегия испытаний

### 18.1. Модульные испытания

Проверяют:

- строгий разбор полного снимка;
- безопасный отказ на неизвестном решении или действии;
- нормализацию русских полей договора;
- невозможность получить главное действие из локальных фактов;
- монотонность версии снимка;
- сохранение идентификатора при повторе;
- возрастание номера устройства;
- контрольную сумму команды;
- шифрование, расшифрование и невозможность перестановки записи в другую область;
- миграцию IndexedDB и восстановление оборванной транзакции;
- порядок очереди и остановку зависимой цепочки;
- истечение разрешения без удаления данных;
- русские пользовательские обозначения.

### 18.2. Испытания компонентов

Testing Library проверяет:

- каркас, медленную загрузку, последний снимок и фатальную ошибку;
- ровно одно главное акцентное действие;
- постоянную доступность трёх действий безопасности во всех семи фазах;
- отсутствие административных действий;
- препятствие, объяснение и переход к устранению;
- форму дефекта без выбора критичности;
- безопасную остановку вместо производственного действия;
- очередь, противоречие и ожидающее вложение;
- удержание и возврат фокуса;
- области живых сообщений и связь ошибок с полями;
- отсутствие технических английских кодов в видимом тексте.

### 18.3. Договорные испытания

Для каждого маршрута v3 фиксируются успешная схема, русская ошибка, код HTTP, обязательные заголовки и повтор. Отдельно проверяются:

- один ключ и одно тело возвращают ту же квитанцию;
- один ключ с другим телом не получает новый ключ автоматически;
- `If-Match` соответствует снимку;
- `401`, `403`, замаскированный `404`, `409`, `422` и `5xx` не теряют команду;
- неизвестные поля доказательства не ломают весь снимок;
- отсутствующее обязательное поле переводит экран в безопасное состояние;
- старый `/api/operator/shift` не вызывается страницей v3.

### 18.4. Интеграционные испытания клиента

С реальной IndexedDB браузера и подменяемой сетью проверяются:

- разрыв до отправки;
- разрыв во время отправки;
- сервер сохранил команду, но ответ потерян;
- перезагрузка с непереданной командой и фотографией;
- две вкладки и один отправитель;
- команды от двух устройств с конфликтом версии;
- частичное принятие пакета;
- обязательное вложение задерживает зависимую команду;
- отзыв устройства;
- перевод часов назад;
- смена пользователя на общем телефоне;
- недостаточная квота хранения.

### 18.5. Браузерная приёмка

Playwright проходит семь сценариев раздела 21 интерфейсной спецификации под настоящей ролью оператора и проверяет серверные эффекты после каждого действия.

Размеры телефона: 320 × 568, 360 × 800, 390 × 844, 430 × 932.  
Размеры настольного экрана: 1024 × 768, 1366 × 768, 1440 × 900, 1920 × 1080.

Для каждого размера проверяются отсутствие горизонтальной прокрутки и перекрытия, касания 48 × 48, клавиатура, возврат из камеры, увеличение текста до 200 процентов, клавиатурное управление, русские строки и чистая консоль.

Сквозное испытание считается успешным только при одновременных доказательствах:

1. правильный экран;
2. ровно один сетевой или локально разрешённый эффект;
3. ожидаемая запись сервера;
4. увеличение версии;
5. аудит и исходящее событие;
6. тот же этап после обновления страницы;
7. отсутствие доступа к чужой организации и чужой установке.

## 20. Последовательность реализации

Каждый срез включает настоящий серверный эффект, клиент, повтор команды, русскую ошибку, аудит и браузерное доказательство. Временный клиентский успех запрещён.

### Срез 0. Авторитетное чтение

- маршрут страницы и общая оболочка;
- схемы и нормализация `GET /api/operator/v3/workplace`;
- каркас, ошибка, отсутствие назначения;
- семь фаз только для просмотра;
- отрицательная проверка другой организации;
- прямой адрес `/operator/v3`, без переключения главной навигации.

### Срез 1. Получение, проверки, готовность и пуск

- выбор назначенной установки;
- серверно сохранённое получение;
- проверка установки и рабочей зоны;
- моточасы;
- объяснимая готовность без балла;
- начало смены через единую команду;
- повтор и конфликт версии.

### Срез 2. Работа

- производственные записи;
- перерыв и простой как интервалы;
- рабочие показатели;
- журнал смены;
- устойчивые идентификаторы дочерних строк.

### Срез 3. Безопасность

- дефект по наблюдаемым признакам;
- опасное событие;
- обязательная фотография;
- безопасная остановка;
- независимая проверка устранения;
- новая оценка и возобновление.

### Срез 4. Завершение и передача

- завершение работ;
- проверка после работ;
- конечные моточасы;
- отчёт, связанный со сменой;
- передача, принятие другим пользователем и фактическое закрытие;
- исправляющие события.

### Срез 5. Безопасный сбор без связи

- IndexedDB, шифрование, черновики, команды, фотографии;
- очередь и квитанции;
- восстановление после перезапуска;
- пакетная отправка и частичные ответы;
- противоречия без перезаписи.

### Срез 6. Ограниченная работа без связи

- доверенное устройство и ключи;
- подписанное разрешение;
- проверка времени, области и перечня команд;
- предварительное представление;
- отзыв устройства и истечение срока;
- реальная браузерная проверка на поддерживаемом телефоне.

### Срез 7. Выпуск

- все размеры и семь обязательных сценариев;
- чистая консоль;
- доступность;
- наблюдаемость;
- включение чтения и команд по организациям;
- после доказанной приёмки — перевод пункта «Смена» на `/operator/v3`.

## 21. Условия готовности клиентской части

Клиентская часть не готова к выпуску, пока не доказано каждое условие:

1. `/operator/v3` использует общую оболочку без второй шапки и второй ролевой навигации.
2. Страница не импортирует `resolveShiftPhase`, `resolveV2State` и клиентские временные флаги v2.
3. Единственным источником этапа, готовности и действий является проверенный снимок v3.
4. На основном экране ровно одно главное акцентное действие.
5. Дефект, опасное событие и фотография доступны во всех семи фазах.
6. Пользовательский интерфейс не показывает баллы, проценты и технические английские коды.
7. Команда записывается локально до отправки и повторяется с тем же ключом.
8. Обновление страницы восстанавливает подтверждённый серверный этап и непереданную очередь.
9. Противоречие не приводит к автоматической перезаписи сервера.
10. Без разрешения клиент не позволяет пуск, возобновление, передачу и закрытие без связи.
11. Критическое событие убирает производственные действия и выводит безопасную остановку.
12. Фотография не считается принятой до подтверждения вложения сервером.
13. Закрытие смены показывается только после принятия передачи или отдельной уполномоченной команды.
14. Настоящий оператор не видит административных действий и чужих назначений.
15. Все обязательные телефонные и настольные размеры, клавиатура, 200 процентов и программа экранного доступа проверены.
16. После каждого действия доказаны запрос, одна деловая запись, версия, аудит, исходящее событие и повторное чтение.
17. В консоли нет ошибок основного сценария.
18. Старый `/api/operator/shift` не является резервным источником v3.

## 22. Риски и меры

| Риск | Уровень | Мера |
|---|---|---|
| серверный снимок неполон, и клиент начнёт восстанавливать этап | критический | обязательная схема; безопасный отказ; вертикально расширять сервер, не добавлять вычисление в React |
| временные признаки v2 проникнут в v3 | критический | запрет импортов в тесте архитектуры; серверный эффект для получения, зоны и завершения |
| две нижние области перекроют действие | высокий | единая переменная высоты общей навигации и браузерные проверки 320 × 568 с клавиатурой |
| ответ потерян после серверного сохранения | высокий | очередь до запроса, постоянный ключ и повтор той же команды |
| две вкладки отправят одну очередь | высокий | блокировка IndexedDB, BroadcastChannel и серверная идемпотентность |
| локальная база будет прочитана другим пользователем телефона | высокий | область пользователя и организации, непереносимые ключи, блокировка после выхода, отзыв устройства |
| XSS получит доступ к расшифрованным данным | высокий | строгая политика сценариев, отсутствие стороннего кода, минимальное время расшифрованных данных; шифрование на диске не объявляется защитой от XSS |
| квота браузера удалит фотографию | высокий | запрос постоянного хранилища, проверка квоты, части по 1 МиБ, явное сообщение до делового подтверждения |
| часы устройства продлят разрешение | критический | серверная временная опора, монотонное время сеанса, запрет при недопустимом расхождении |
| неизвестный серверный код станет кнопкой | высокий | закрытый справочник исполнителей; неизвестное действие безопасно недоступно |
| устаревший снимок покажет разрешение | критический | явная актуальность; критические действия только по свежему снимку или подписанному разрешению |
| частично принятый пакет нарушит порядок | высокий | независимые квитанции, `dependsOn`, остановка зависимой цепочки |
| английские внутренние термины попадут человеку | средний | единый русский словарь и испытание видимого текста |
| выпуск v3 сломает действующий `/operator` | высокий | отдельный адрес, независимые файлы, позднее переключение навигации и возможность отключить чтение/команды по организации |

## 23. Итог

Полноценный `/operator/v3` — не новая раскраска v2 и не локальная машина шагов. Это клиент авторитетного рабочего места, который:

- сохраняет существующую глобальную оболочку PilingTrack;
- показывает маршрут, готовность и следующее действие из одного серверного снимка;
- собирает факты крупными и понятными русскими формами;
- сначала надёжно сохраняет команду, затем отправляет её;
- ясно различает серверное подтверждение и локальную очередь;
- ограничивает работу без связи подписанным разрешением;
- не скрывает безопасность ни на одном этапе;
- после перезагрузки, другого устройства и восстановления связи возвращается к тому же авторитетному состоянию.

Критерий реализации: любой показанный деловой результат должен быть доказан серверным снимком или явно называться сохранённым на устройстве ожиданием. Третьего состояния — «мы переключили экран и надеемся, что сервер согласится» — в v3 нет.
