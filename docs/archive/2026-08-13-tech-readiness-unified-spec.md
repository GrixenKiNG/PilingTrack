1\. Назначение

Модуль отвечает на один вопрос перед началом смены:

Можно ли пускать эту установку в работу, и если нет — кто и что должен сделать?

Система должна давать проверяемый ответ на четыре уточняющих вопроса:



Можно ли безопасно открыть смену на выбранной установке?

Какие условия уже подтверждены и какими доказательствами?

Что препятствует запуску, кто отвечает и какое следующее действие?

Кто, когда и на основании каких данных разрешил или запретил работу?



Главный принцип: балл готовности и допуск к работе — разные сущности.



Балл показывает полноту и качество подтверждений.

Допуск определяется одновременно:

итоговым баллом;

отсутствием активных критических блокеров;

действующим нарядом-допуском (если правило включено);

актуальностью доказательств;

предсменным допуском диспетчера;

наличием условий смены.





Установка с баллом 95/100 и критическим дефектом должна быть BLOCKED / недоступна к старту.

Точка входа: /admin/to

Границы модуля (не входит в scope):



склад запчастей и закупки;

стоимость владения;

зарплата, табели, кадровые смены;

телематика реального времени и автоуправление техникой;

замена производственного отчёта по сваям;

произвольный BPMN-конструктор согласований;

электронная / квалифицированная подпись.

5\. Основные понятия

5.1. Готовность единицы техники

Центр модели — оборудование и его текущая готовность, а не отдельный «кейс на всё».



CurrentReadiness — последнее состояние готовности (продвигается только вперёд по calculatedAt).

ReadinessScoreSnapshot — неизменяемый снимок: факты, версия правил, score, blockers, warnings, evidence, factsHash.

Триггеры снимка: осмотр, дефект, моточасы, ТО, наряд-допуск, команды смены, решение о запуске, публикация правил.



Не вводится отдельный write-model агрегат ReadinessCase в текущем baseline.

«Кейс на смену» при необходимости — read-model / проекция (Shift + evidence + current readiness).

6\. Машины состояний

Три ортогональные машины. UI показывает единую «цепочку готовности», но переходы выполняются только в своих domain-сервисах.

6.1. Смена (Shift)

textPLANNED

&#x20; → request → PENDING\_ACCEPTANCE

&#x20;     → start → STARTED

&#x20;         → handover → HANDOVER\_PENDING

&#x20;             → accept → CLOSED

&#x20;             → rework → STARTED

&#x20;     → decline → PLANNED



Отмена: PLANNED | PENDING\_ACCEPTANCE | STARTED → CANCELLED

Правила:



Не более одной активной смены на единицу техники (STARTED | HANDOVER\_PENDING).

Прямой старт из PLANNED запрещён: оператор запрашивает допуск, пускает диспетчер.

Тип смены обязателен: DAY | NIGHT.

Производственная дата — в timezone тенанта.



6.2. Передача смены (ShiftHandover)

textDRAFT → submit → SUBMITTED

&#x20; → accept → ACCEPTED

&#x20; → rework → REWORK\_REQUIRED → submit → SUBMITTED



Accept ровно одним DISPATCHER.

Optimistic concurrency (expectedVersion / If-Match).

Конфликт / повтор → 409.



6.3. Наряд-допуск (WorkPermit)

textDRAFT → submit → PENDING\_APPROVAL

&#x20; → approve\* → APPROVED

&#x20;     → revoke → REVOKED

&#x20;     → expire → EXPIRED



NORMAL: достаточно подписи диспетчера; автор может подписать.

ELEVATED: диспетчер и админ, разные люди; автор подписать не может.

Правка содержательных полей → новая версия, DRAFT, старые подписи valid=false.



6.4. Дефект и ТО



Дефект: OPEN → IN\_WORK → CLOSED (+ REJECTED).

Критический OPEN/IN\_WORK блокирует старт.

ТО: PLANNED → ASSIGNED → IN\_PROGRESS → DONE (+ ON\_HOLD, CANCELLED).

7.1. Центр готовности (эталон)

Три колонки:



Слева: выбор установки, статус, балл, метрики парка.

Центр: цепочка из 5 шагов (осмотр → моточасы → наряд → ТО → предсменный допуск), чек-лист смены, следующее действие с указанием роли.

Справа: доказательства (ссылки на первоисточники), журнал передач, входящие диспетчера.



Правило визуала: цветом залито только выполненное; текущий шаг обведён; будущие — контур.

Next action считается на сервере. Приоритет:



критический риск / блокер;

обязательный незавершённый этап;

действие, ожидающее конкретную роль;

ближайший срок;

рекомендуемое улучшение.



Кнопка ведёт к месту выполнения, не к «модулю вообще».

8\. Архитектура

8.1. Раскладка

textsrc/modules/readiness/     domain · application · infrastructure

src/modules/equipment/

src/modules/inspections/

src/app/api/readiness\*/

Домен не знает Prisma и HTTP. Страницы — тонкие.

8.2. Командный конвейер

Каждая мутация:



Контекст: актор, tenant, correlationId, requestId

Идемпотентность (Idempotency-Key, TTL 7 суток)

Optimistic locking (If-Match / expectedVersion, ETag)

Проверка перехода состояния

Запись + outbox-событие в одной транзакции

Звено audit hash-chain



8.3. Снимки

textкоманда → запись + Outbox(ReadinessSnapshotRequested)

&#x20;      → worker → evaluateAuthoritativeReadiness

&#x20;      → ReadinessScoreSnapshot (immutable)

&#x20;      → CurrentReadiness (latest)

Часы захвачены временем события, не временем обработки воркера.

8.4. Аудит

texthash = SHA256("PILINGTRACK-AUDIT-V1" ⏎ tenantId ⏎ sequence ⏎ prevHash ⏎ canonical(event))



Append-only; update/delete запрещены прикладной роли.

ПДн и секреты маскируются до хеша.

Проверка цепочки — фоном; разрыв → security alert, история не переписывается.

Это не электронная подпись.



8.5. Изоляция тенантов



Tenant только из серверной сессии.

FORCE RLS, составные ключи (tenantId, id).

Запрос без tenantId падает, не расширяется на всех.

Паттерн IS NULL OR tenantId запрещён.



8.6. Часовой пояс

Производственная дата — в TenantSettings.timezone (default Europe/Moscow).

Timestamps в БД — UTC + использованный timezone.

13\. Критерии приёмки (сводка)



Ровно 7 вкладок в заданном порядке, текущая оболочка.

Старт смены только через допуск диспетчера; параллельный второй старт → один успех, один 409.

Критический дефект при любом балле блокирует старт; прямой API → 422/409 с кодом, событие в аудите.

Preview score ≡ authoritative на одних facts.

Next action указывает роль и конкретный шаг (после реализации P1).

Handover accept — один диспетчер; конкурент → 409.

ELEVATED: два разных человека; NORMAL: допускается подпись автора.

Публикация правил не меняет прошлые snapshots.

Cross-tenant: нет чтения/записи чужих данных.

Audit append-only, hash-chain проверяема; CSV безопасен от formula injection.

Фильтры в URL, reload/back/reset согласованы с API и CSV.

Acting-as только у ADMIN и всегда в аудите.
